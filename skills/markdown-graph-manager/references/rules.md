# Rules (single source)

Each rule below is stated here and nowhere else. SKILL.md, the other references, the README and the evals point to a rule by its section name and do not restate it. A script docstring or comment may name another script as a cross-reference but does not define a rule for it. To change a rule, change it here only.

## Drafts
The skill does not guess which pages are drafts: it asks the user whether the graph holds draft pages once per session, before the first audit, fix, write/create or edit step that reads or writes the pages (including the title uniqueness check). Only `graph_audit.py` can leave named pages out (`--exclude "NAME,NAME"`, matched by file name without `.md`, not by `title::`; a name containing a comma is split and cannot be excluded, so tell the user). The other audit and fix scripts have no exclude option and read every page. So when the graph holds drafts:
- ask whether drafts may be read before running the other scripts, and write nothing to a draft without the user's yes;
- if drafts may be read but not written, treat it the same way as not read for every fix script (they cannot skip pages): give the audit report only;
- if drafts may not be read at all, run nothing and say so;
- if drafts may be parsed but not reported on, run only `graph_audit.py` with `--exclude`: tell the user first that it still parses the draft files to index link targets, say the other audit scripts were not run, and run no fix script over the graph (give the audit report only);
- on a no-schema graph the only script cannot leave pages out: if drafts may not be read or reported on, say so and run nothing; if they may be read but not written, run the `--links-only` audit (it never writes) and no fix.
An excluded draft is still a link target, but its own links are not counted, so a page linked only from a draft shows as an `orphan`.

## Unattended run (weekly routine)
A routine the user asked for cannot ask questions, so it follows these rules and reports only:
- With a schema: it runs only `graph_audit.py`, excluding the draft names the user gave when asking for the routine; if the user gave none and did not say there are no drafts, it runs nothing.
- Without a schema: its only script cannot leave pages out, so it runs only if the user said the graph holds no drafts; otherwise it runs nothing.
- SKILL.md Step 0 asks nothing: if the graph cannot be resolved without asking (no registry path, an `unknown` status, an ambiguous graph), it runs nothing and says so.
- SKILL.md Step -1 asks nothing: a version gap or documentation change goes into the report as plain text.

## Pre-fix report
This rule is for the schema route; the no-schema route has its own gate (rule Safe fixes, no-schema graph), because `--links-only` never strips bold. Stripping `**` (the `bold-markdown` safe-fix) destroys the signal `schema-lint.py`'s `inline-bold-heading` check looks for, so a heading candidate would report clean without having been restructured. Before `graph-link-audit.py --apply-safe-fixes`:
1. Show the user the full pre-fix audit report, including the `inline-bold-heading` findings, the file list of the `schema-pass.py` dry run, and a note that it also rewrites lines no audit report shows (a `Source::` name, generic-type drops and the configured global replacements), so genuine candidates are restructured first (`graph-heading-extract.py` finds a candidate only while its `**` is still there). The report lists only the bold-label-plus-dash form; `graph-heading-extract.py` also finds bold labels followed by a colon or no separator, so offer its dry run (it writes nothing) alongside the report.
2. Wait for the user's reply before applying. A request that already says to apply the fixes without restructuring any bold-labelled bullet counts as that reply.
3. Save the report to a new scratch file `${TMPDIR:-/tmp}/mgm-prefix-report-<id>-<n>.md` (`<id>` the registry entry's `id`, `n` the next unused number) before applying anything; never overwrite an older one.
4. After a lost context, read every such file of that graph (a re-audit after the strip no longer lists the heading candidates; the dry run of `graph-heading-extract.py` shows which are still bold). Delete them once the fix has been reported or declined.
5. Pages under `GRAPH_ROOT/journals` are stripped too. `graph-heading-extract.py` does not scan them when the journals folder lies outside the pages folder (the usual graph, whose pages folder is named `pages`); then search them for lines starting with `- **` and add those to the report.
When an audit report holds `inline-bold-heading` findings next to `bold-markdown` findings, say that the safe-fix would erase the heading candidates.

## Safe fixes
Only these categories are ever written, and everything else stays report-only.
- `graph-link-audit.py --apply-safe-fixes` (also walks `GRAPH_ROOT/journals`): existence-verified bracket wraps (`should-be-linked`); unbracketing of dangling bracketed links in body prose and in any property value (a URL is left alone; a namespaced `/` link is left to `schema-lint.py`); deletion of valueless property lines, except a blank `writer::` (reported by `graph_audit.py` as `blank-writer`) and every blank property line on a template page; stripping of `**` bold.
- `schema-pass.py` (dry-run first, then `--apply`): `type::` and `status::` values mapped through the schema config (an unmapped `type::` value is Title-Cased unless it is already in the schema's type vocabulary, which keeps it as it is); `Source::` to `source::`; a `Status::` name to `status::` even when its value is unmapped; retired `block-type::`/`item-type::` lines to `type::` (a Zotero item type in `item-type::` is left alone; a page can end with two `type::` lines, left for the user to merge); a plain-writer or bracketed `author::` to `writer::` (not on a Reading Notes or Primary Source page); the configured generic-type drops and global string replacements (which run over the whole file text, fenced code included).
- Order: run `schema-pass.py` before `graph-link-audit.py --apply-safe-fixes`, because a `global_replacements` rename of a bracketed link target would otherwise be unbracketed first.
- Every script that writes pages or files in place (`schema-pass.py`, `graph-link-audit.py`, `graph-heading-extract.py`, `graph-colon-label-fix.py`, `property-normalize.py`, `assets-audit.py`): before it writes (`--apply`, `--apply-safe-fixes`, or `assets-audit.py` itself), ask the user to confirm the graph is backed up or under version control.
- A `schema-lint.py` line counts as safe-fix when `schema-pass.py` would rewrite it (a `type::` or `status::` vocabulary line, or an `author::` line it turns into `writer::`) and the graph's `pages_dir` is `pages`; every other `schema-lint.py` line is report-only. The dry run (without `--apply`, it writes nothing) lists only the files it would change, so judge each line from its value: a `type::` line is rewritten when its value is not already canonical (mapped through the schema config, or Title-Cased when unmapped and not in the type vocabulary); a `status::` line only when the schema config maps its value.
- Exception: `graph-heading-extract.py` and `graph-colon-label-fix.py` (the judgment-gated scripts in SKILL.md) write report-only categories; they are run manually, one at a time, only after the judgment work in SKILL.md's Output contract, and never as part of the fix subcommand's safe fixes. `property-normalize.py` writes only the type mapping that `schema-pass.py` also writes, as an occasional cleanup.
- `graph_audit.py` has no fix mode: each of its findings is fixed by hand, as an edit (SKILL.md, the `edit` subcommand), only after the user's yes for that one finding, then the same check is re-run on that page.
- No-schema graph: skip `schema-pass.py`; the only fix is `graph-link-audit.py GRAPH_ROOT assets/example-schema.json --pages-dir DIR --links-only --apply-safe-fixes` (dangling-link fixes only). A plain vault may reach pages through YAML `aliases:` that the script does not read, so show the report first and apply only after the user's yes.

## Bracket rule
A link-property value is bracketed only when its target page exists (checked case-insensitively against titles, filenames and aliases, graph-wide); a nonexistent target stays plain so no phantom page is created. A `[[bracketed]]` link whose target does not exist is unbracketed, wherever it appears. Left alone: a URL, a namespaced `/` link (reported by `schema-lint.py`), a same-page `[[#Heading]]` link and an attachment link such as `[[photo.png]]`. A link `[[Page|alias]]` or `[[Page#Heading]]` counts as existing when the page exists.

## Read-back after a write
After a write made by the write/create or edit subcommand, run `graph_audit.py PAGES_DIR --schema SCHEMA_CONFIG --checks placeholders,format,properties --only-pages "<page>"` and read the page; without `--schema` the properties check is skipped. `<page>` is the page's file name without `.md` and contains no comma (the option splits names on commas, so for such a page read the page and run the same check without `--only-pages`); a name that matches no page prints 0 findings, the same as a clean page. Do not exclude the page just written, even when it is a draft written with the user's yes; `--only-pages` already limits the report to that page. If the Drafts answer was that drafts may not be read at all, do not run it: read the written page yourself and say the audit script was not run. Report anything left: a leftover placeholder in what was written is a failed write; a finding that was already on the page before the write (for example a blank page-level `writer::` left alone under rule Writer attribution) is reported as pre-existing.

## Exit codes
- `schema-lint.py` and `graph-link-audit.py` exit with the number of files that have findings, capped at 255. Read stderr before trusting the count:
  - an `error:` line or a Python traceback (bad graph root or unreadable schema file) is a failed run that exits 1;
  - an `error:` line from argparse (a missing argument) is a usage error that exits 2, the same number as two files with findings;
  - a 255 together with a stderr line "!! 0 files scanned" or "!! 0 files linted" means target discovery is broken and the report is not trustworthy;
  - otherwise a nonzero exit means findings; on an `--apply-safe-fixes` run it still counts the files that had findings before the fixes were written, so read the printed line "APPLIED n safe fix(es); m finding(s) left for judgment" for the result.
- `graph_audit.py`: 0 clean, 1 findings, 2 bad input.
- `graph-discovery.py`: see SKILL.md, Step 0: resolve the graph, for the statuses.

## Pages-folder-only scripts
`schema-pass.py`, `property-normalize.py` and `assets-audit.py` work on the folder named `pages` under `GRAPH_ROOT` only and cannot be pointed at another pages folder. They do not apply to a graph whose `pages_dir` is not `pages` (a flat vault or any other folder name).

## What each audit script reads
- `graph_audit.py` skips folders named `assets`, `copilot`, `logseq`, `bak` and any hidden folder, and reads every `.md` file under the pages folder it is given (plus, when that folder is named `pages`, the `assets` folder beside it for attachment names). `schema-lint.py` and `graph-link-audit.py` skip the fixed list `.obsidian`, `assets`, `copilot`, `logseq`, `.recycle`, `bak`, `.trash` only.
- `graph-link-audit.py` also reads `GRAPH_ROOT/journals`; `graph_audit.py` reads it only when it lies under the folder it is given, which a folder named `pages` does not contain. In that case a link that appears only in a journal page is not counted by `graph_audit.py`: a page linked only from journals shows there as an `orphan`, a target cited only in journals is not a `dead-end-link` hit, and a link to a journal page is reported missing. Check the journals before acting on such a finding.
- Links inside fenced or inline code are ignored by `graph_audit.py` and `graph-link-audit.py` alike; `graph_audit.py` also ignores image embeds, URL property values and placeholder wording shown in inline code.

## Templates and the blank writer
A page in a folder named `Templates`, or with a name ending ` Template`, is a template. Templates keep `writer::` blank and carry no `writer::` attribution. On a template page `graph_audit.py` skips the placeholder, blank-title and missing-`type::` checks and `graph-link-audit.py` keeps every blank property line. A template's links are placeholders: neither audit script reports or unbrackets a link on a template page. A blank `writer::` in the leading property block of a non-template page is the `blank-writer` placeholder finding. `graph-link-audit.py` never deletes a blank `writer::` at any indentation, and `graph_audit.py` does not report one below the leading block, so read such a block-level line yourself and ask the user.

## Writer attribution
- Creating a page, or writing or replacing its whole content, sets the page property `writer:: Claude`, except on a template page (rule Templates and the blank writer).
- Adding or editing blocks within an existing page leaves the page-level `writer::` alone. Add a block-level `writer:: Claude` property on just the blocks added, per the graph's existing type/writer promotion rule (block-level values only for blocks that diverge from the page's dominant value). This holds whether the page's `writer::` is someone else's, missing or blank; when the page-level `writer::` is already Claude, the added blocks need no block-level line; a blank page-level `writer::` on a template stays blank.

## Equivalent codes across scripts
A defect that two scripts both report is listed once. Equivalences:
- `type-vocab` = `schema-lint.py`'s "type:: ... not in vocab"; `required-properties` = its "missing required property"; `status-vocab` = its "status:: ... not in status vocab"; `writer-vocab` = its "writer:: ... not a known writer/entity"; `zotero-only-property` = its "reserved for Zotero pages"; `md-heading` and `yaml-frontmatter` = its markdown-heading and YAML checks.
- `name-collision` = `graph-link-audit.py`'s `title-collision`; `bracketed-missing` = its `dangling-bracketed-link`; `plain-existing` = its `should-be-linked`; `dead-end-link` = its `dangling-link` for a body link or for a link in a property that is not a link-type property; for a link inside a compound link-type value the same defect is reported by graph_audit.py as bracketed-missing; `blank-title` = its `empty-property-value` on a `title::` line.
- In the merged report a code equal to a safe-fix category of `graph-link-audit.py` (`plain-existing`, `bracketed-missing`, `dead-end-link`, `blank-title`) takes that marking. `type-vocab`, `status-vocab` and a Zotero-reserved finding on an `author::` line take safe-fix only where `schema-pass.py` would rewrite the value and the pages folder is named `pages`. `writer-vocab` is report-only: `schema-pass.py` rewrites no writer value. Every other code is report-only.
- Where the scripts disagree about one page, read the page and report what it shows. Known disagreements: schema-lint.py reads the type, writer and status vocabulary lines at any depth while graph_audit.py reads only the leading property block, and schema-lint.py matches markdown headings at column 0 only while graph_audit.py also matches bullet headings; a link-type property line below the leading property block (block-level) is reported as a dangling bracketed link by graph-link-audit.py and as a dead-end link by graph_audit.py; when the schema names no link-type properties, `graph_audit.py` uses its fallback list (rule Roles fixed in the format contract) and `graph-link-audit.py` an empty list, so the two classify the same property differently; `schema-lint.py` reads the head block up to the first `- ` bullet and `graph_audit.py` the first contiguous run of property lines; `schema-lint.py` reports a missing required property on a template page and `graph_audit.py` skips it; `schema-lint.py` treats a page as Zotero-made when its `source::` names Zotero, it has a `citekey::` property or it has no `type::`, while `graph_audit.py` exempts only Reading Notes and Primary Source pages from `zotero-only-property`.

## Roles fixed in the format contract
The scripts themselves fix only these, and everything else in the vocabulary comes from the schema config JSON:
- the page types Reading Notes, Primary Source and Note, and `writer:: Claude` (`graph_audit.py`); the page types Reading Notes and Primary Source, which keep their `author::` property (`schema-pass.py`);
- the task-keyword list TODO, DOING, DONE, WAITING, CANCELLED, with LATER and NOW also recognised by the single-colon check, and the Zotero-page test (`schema-lint.py`; the Zotero-page test is described under Equivalent codes across scripts);
- the placeholder wording TBD, FILL IN, INSERT HERE, PLACEHOLDER and the template variables {{title}}, {{date}}, {{citekey}}, {{module}}, {{name}} (`graph_audit.py`);
- the link-property fallback `related`, `project`, `lens`, `period`, `thread`, used by `graph_audit.py` when the schema names no link-type properties.
