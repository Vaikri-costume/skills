## 1. The note: Signpost Summary layout

The summary becomes a Zotero note only after the user approves it with the plan at the gate (`SKILL.md` step 10, The gate). The note stays a Zotero note; the user moves into the graph whatever they want. The layout follows the user's `Reading Notes` pages so conversion is direct, with the type changed. `scripts/note_html.py` prints the properties in the order related, type, writer, citekey, author; if the template the profile's `graph_notes_template` names is readable and orders them differently, reorder the property lines in the printed HTML's first `<p>` (the lines are joined by `<br>`, with none after the last, before `</p>`; keep that shape after reordering) to match it before the note is written; the read-back is then compared with that reordered HTML. The layout:

```
related:: [[<module>]]
type:: Signpost Summary
writer:: Claude
citekey:: <from the item, never invented>
author:: <as on the item>

Notes / Summary
<the approved summary, in short paragraphs>
```

- `related::` is the module: copy the `related::` value of the graph page that lists this reading (the profile's `graph_reading_pages`, or the path the project's instructions name). If the profile names no graph path or no page lists the reading, write `related::` with no value (keeping the property order; not the banned placeholder) and say so. Write `[[ ]]` as HTML entities (`&#91;&#91;...&#93;&#93;`); `note_html.py --related` takes the bare module name, without brackets, and adds them itself.
- `citekey::` comes from the item, never invented; if none exists, omit the line and say so.
- The user's Annotations headings and Connections stay the user's and are not created or filled.
- Simple HTML only (p, strong, em, ul, li, a, code, br), the summary in short paragraphs. The property lines go in one `<p>` joined with `<br>`, `Notes / Summary` is a plain `<p>`, and each summary paragraph is its own `<p>`, for example:

  ```
  <p>related:: &#91;&#91;Module name&#93;&#93;<br>type:: Signpost Summary<br>writer:: Claude<br>citekey:: authorYear<br>author:: Author Name</p><p>Notes / Summary</p><p>First summary paragraph.</p><p>Second summary paragraph.</p>
  ```

  No week or date line, no bibliography line, no placeholder. `scripts/note_html.py summary.md --related <module> --citekey <key> --author <author>` prints exactly this HTML from the approved summary (leave out `--related` or `--citekey` where the rules above say the value is empty or omitted).
- The note lists no pages read; the chat report does, and those can be wider than the pages the highlights use.

## 2. Anchoring a quote

- Copy the quote from the page text actually read, not from memory; repair the page reader's artefacts (`inter- pretation`, `?` for a ligature) to the real wording. Fix (`plan_check.py` flag NOT PLACED): copy the quote again from the page's own text, OCR marks included (`and_`), and check it with `anchor_check.py`.
- Check it with `scripts/anchor_check.py` against the page's saved text (`pages/p<N>.txt`, `SKILL.md` step 5, Read the real pages). Where that text will not anchor a quote, extract the page with `pdftotext` in its default and `-raw` order (and PyMuPDF if installed) and save the order that finds it as the page's text; then check every other quote on that page again with `anchor_check.py` against the new text (and save each new printed span to `plan.json`); say which order found each quote. The script normalises soft hyphens, line-end hyphenation, ligatures, quotes, dashes and whitespace, and flags a case difference. A scan's OCR layer may drop spaces or scramble lines.
- On any `found` line (`found:`, `found (ignoring hyphens, dashes and spaces ...)`, and under `--allow-repeat` the two `found (N matches ...)` lines, which print the first copy) the quote exists and the script prints the page's own span (it can differ from the planned quote in ligatures, quotes, line breaks and, on `found (ignoring hyphens, dashes and spaces ...)`, in hyphens, dashes and spaces). The quote given to the highlight tool is that printed span, which the script prints in quoted form; the tool gets the text it denotes (a `\n` is a line break, escapes are not typed).
- A quote must be unique on its page, copied with the page's own letter case. Run `anchor_check.py` on one page's text at a time, without `--allow-repeat` except for a sentence over 100 characters that the page repeats word for word, highlighted at its first copy (below): it treats its whole input as one text, so a longer file would count repeats across pages and find a quote that crosses a page break.
- A passage that crosses a page break is highlighted per page: one highlight on each page, each anchored on its own page (the create tool works on one page per call); both parts carry the phrase's comment and share its number in the plan. A part that is only a lead-in with no point of its own needs no highlight. The phrase is never dropped for a page break.
- The highlight tool starts at the first place on the page where a quote's opening words appear and ends at the first place after that where its closing words appear. A sentence the page repeats (an abstract that repeats the introduction) is therefore highlighted at its first copy, in that copy's own words, so the point is kept, never dropped. This holds only for a quote over 100 characters: the tool highlights a shorter quote at every copy on the page, so a shorter repeat is lengthened past 100 characters, or its phrase keeps its point on another passage (`SKILL.md` step 7, Pass 2). Any other quote whose opening words appear earlier on the page, or whose closing words appear again before its own end, is lengthened or moved; otherwise the tool spans from the other copy, a wall of highlight. `anchor_check.py` flags this as EDGE REPEATS.
- If quotes will not anchor because the text layer is garbled or scanned, or a quote fails at creation: `references/cases.md` sections 3 (Scans and OCR) and 7 (Creation failures).

## 3. Pass 3: the understanding check and the tests

Pass 3 is run on the whole plan before it is shown. Every highlight is tested; the report gives the count that fails each test and a table, one row per highlight (highlight, comment, the passage's own wording for the comment, one column per check graded on a highlight, fix), plus one row per linking word or causal phrase in the summary ("because", "so", "since", "by design" and the like) with the passage that makes the link, or "no passage: removed". The passage-wording column shows any swap of the text's wording (Text's own words); a swap is fixed before the plan is shown. Worked examples of the tests: `references/cases.md` section 15 (Pass 3 worked examples), read only when a test is unclear.

The understanding check (the user's questions):
- **Not a copy** ("How many are basically the same?"). Is the comment the same words as the highlight, with a few swapped? Fails when the comment only shortens or re-words its quote so that the quote adds nothing beyond it, or is the whole quote or its opening words; a short phrase taken word for word from the quote (as Short label shortens it) passes when the quote carries more than the phrase (its reason, its evidence, where the part belongs). Fix (flag SAME CLAIM): make the comment the term or subject the quote is about, and let the quote carry the claim ("women's justice claims", not "yet to be clarified"); or grow the highlight to the neighbouring sentence that carries the reason or the purpose; or put the comment on the part that carries it (for example the purpose clause). Never swap words in the quote's own sentence.
- **Short label** ("Could it have been explained in easier words, so the annotation needs only a word or phrase?"). The comment is a short phrase of at most five words (a hyphenated compound or a number counts as one word), fewer is better, that keeps what its passage carries; the text's own wording is shortened by dropping words, never by swapping them. Fix (flag LONG COMMENT): keep the core words, name the subject rather than the claim, keep any "not" or hedge, and never swap words, only drop them.
- **Shows why** ("Does it tell me why, or show me how it is true, as the paper says it?"). The highlight carries the reason or the evidence, not only the claim. It does not fail because the text gives no why or how: then it passes as the claim the text makes (the table says "none in the text", as the order of work, step 1, records it), and fails only if the summary adds a reason the text does not give. A reason that sits in another highlight passes when the summary sentence joins the two into one point (the highlights are not merged). Fix, in this order: a reason in another highlight, join the two in one summary sentence; a reason in the next or previous sentence, or in the unhighlighted text the highlight points back to, grow the highlight to take it in while it stays one point (Whole passage), otherwise add a highlight on the evidence with its own phrase in the summary; no reason in the text, it passes as the claim and the summary adds none.

A highlight that fails the understanding check is fixed by growing or moving the highlight, not by re-wording its comment, except as the Not a copy, Short label and NEGATION fixes say (the MISSING and TANDEM fixes change the sentence, never the comment).

The user's other rules, graded with the questions:
- **Nothing added.** Every phrase of the summary has a passage that shows it is true; a phrase with none comes out of the summary, and is not kept as an inference. A claim stays with whoever the text gives it to: a point the authors take from a source ("As Butler (1990) demonstrated", "Coker notes") is that source's, and the summary names it; the authors' "but", "while" or "yet" stays a contrast. Where the text only reports someone else's critique ("critiqued, for example, for ..."), the phrase says "critics say", and the evidence is a separate highlight where the text gives it (an example, a case); where the text gives no evidence, the report says so. A link ("because", "so", "since", "therefore", "by design") is a claim too: it passes only where the text makes it, as its row in the table shows; where the text gives no cause, "and" is right. Fix (flag LINK): take out a claim with no passage behind it; where the text gives no cause, the link becomes "and" or the text's own "while".
- **Text's own words.** Where the text already says something plainly, the summary and the comments keep its wording exactly, hedges and quantifiers included ("may", "suggests", "seem to", "much of", "some", "most"); a synonym swap or a dropped hedge fails. Your own words are only for the connecting prose: where a summary sentence reuses the text's sentence apart from the comment phrases, say its point again in plainer words around them. If the text says nothing more about such a wording, its highlight is the whole clause that shows where it belongs, and the report says the text gives no more. Every other mention of the text's wording points to this check. Graded, not flagged by the script. Fix: put back the text's own word and its hedge ("may take different forms"); never a synonym.
- **Comment in summary.** Every comment appears word for word in the summary, once, and reads naturally in its sentence, not as a clipped label or a colon list; every summary sentence is a complete, grammatical sentence on its own. A comment never says the opposite of its passage: where it states the claim it keeps the negation ("not extraordinary events", never "extraordinary events"); where it names the subject and lets the quote carry the claim (the Not a copy and Short label fixes: "women's justice claims"), that is not a change of claim, unless the passage negates those very words (flag NEGATION), where the comment keeps the "not". Fix (flags MISSING, TANDEM): write the comment word for word into its sentence and change the sentence, not the comment, until it reads as ordinary prose. Fix (flag NEGATION): put the passage's "not" into the comment, so the comment keeps the claim's direction.
- **Whole passage.** A highlight starts at the clause that carries the claim, ends where the argument ends, and covers only what its phrase needs: never a bare preposition, an unfinished phrase or a fragment at either end. Size: the clause or sentence that carries the claim and, where the text gives it there, the sentence with its reason, as long as the point needs. A passage that lumps several separate points together is a wall, and the reader can no longer see which words support the phrase: split it into the highlights of its separate points (each with its own phrase in the summary), or cut it to what the phrase needs. A highlight may start mid-sentence when the words from there are all that is needed to make the point; it never starts on words that do not make the point without what comes before them. Two kinds of opening back-reference, handled differently: a bare connective that only links ("Thus,", "However,", "Consequently,", "In other words,", "With this knowledge in mind", "As the above discussion suggests", "It seems clear then that") is dropped, and the highlight starts at the clause it introduces; a back-reference that names what it rests on ("All these findings indicate that", "What both cases emphasise is that", "Recognising this means", "This means", "As such, they define") is the reason, so it stays, and what it points to is carried by this highlight or by a highlight the summary joins to it. A dangling start that refers to the highlight just before it passes when the summary joins the two. Fix (a wall): split the passage into the highlights of its points, or cut it to what the phrase needs. Fix (flag INSIDE, for an overlap): start at the clause that carries the claim; where the back-reference is the reason ("Recognising this means …", "All these findings indicate …"), extend the highlight back to what it points to; a passage across a page break gets one highlight per page (section 2).
- **Aids understanding.** The summary states the text's point in plainer words and adds nothing the text does not say. Each sentence says what role its point plays in the text's argument (what it supports, what it leads to next), never only restating its passage. A summary that strings the highlighted passages together in the text's own sentences fails, even when every sentence is pinned: the comments keep the text's words, but the sentence around them is the writer's, and says how the text uses the point (for a point about structural violence: not "the structural violence of poverty, marginalisation and exclusion shapes this violence too", but how the text uses structural violence in its argument, for example by linking it to the next point it makes). A reader who has not read the text can follow it: every person, name and term is introduced where it first appears (who or what it is, from the text), and a defined term is explained from its definition; a sentence that repeats an earlier point comes out unless it makes a new point with its own passage. It is a tool that helps the reader understand, not necessarily comprehensive: length or coverage alone is no fail. Fix: say what the point does in the argument, not what the passage says, and cut anything the text does not say; length or coverage alone needs no fix.
- **Every claim backed.** Every claim of the summary has a highlight behind it, the main claim of the first sentence included (where the text never states its main claim, the first sentence gives the argument through its stated points, `SKILL.md` step 9, Pass 3), and so does every source or person the summary names as saying something ("Gready and Robins define", "a word they take from Rose-Redwood"): extend the highlight to the words that name them; the summary carries no unpinned framing sentence. Fix (flag WORDING, a sentence with no highlight): give the claim its highlight, or take it out of the summary.

Not a copy, Short label, Shows why and Whole passage are graded per highlight; Aids understanding and Every claim backed on the summary; Nothing added, Text's own words and Comment in summary on both, each comment in the per-highlight table (its passage-wording column) and the summary's sentences again.

The other tests:
- **Compose the labels into a sentence.** The labels of related highlights join into one sentence. Compare it with the text and say where its wording goes beyond it.
- **Drop what repeats.** A phrase whose words sit inside another highlight, or whose words are a term that has its own highlight on its definition (Every defined word gets its definition), gets no highlight of its own. Its point is still carried by the highlight it sits in. Fix (flag INSIDE, for a phrase inside another highlight): drop that phrase's own highlight; its point stays in the summary sentence of the highlight it sits in.
- **Every defined word gets its definition.** Every term the summary uses (a word the text defines: a passage says what it is) is explained from that definition, not from general knowledge, and gets its own highlight on it (who or what it covers, what it is set against); where the summary sets two terms against each other (transformation rather than transition), each side gets its own. A word the text only names, uses or describes is a phrase, not a term: it gets the highlight that proves its phrase, and no definition is looked for. Fix (flag TERM): if the text has no passage saying what the word is, mark it a phrase, not a term, and give it the highlight that proves the phrase.
- **Quote edges.** Every quote lands on itself, as section 2 says (`scripts/anchor_check.py` flags EDGE REPEATS).
- **What cannot be simplified stays.** A part that cannot be made simpler without changing its meaning stays, listed with the reason.

Order of work (the grading is part of pass 3, done before the user sees anything, not after):
1. First check: run `scripts/context_check.py plan.json pages`, which prints the sentence before and after every highlight, and read each pair: where it gives the claim's reason or evidence, or the back-reference the claim depends on, the highlight or a joined highlight must carry it (Shows why). Record the decision for every highlight in the check table as one of: carried by highlight n, or none in the text; an empty entry is a fail. Then run the checks graded per highlight (as this section's grading-unit sentence lists them: the understanding check, Whole passage, and the comment side of Nothing added, Text's own words and Comment in summary) and the other tests on every highlight, and write the table to `checks.md`; the checks graded on the summary wait for step 4 (Second check), once the summary exists.
2. Rebuild the plan by each failing check's Fix, and save it over `plan.json` (and again after each later fix to the plan), so the scripts and a resume read the current plan.
3. Write the summary from the comments, so each comment is a phrase in it, in ordinary sentences, in the order their passages come in the text (`SKILL.md` step 9, Pass 3, The summary). Fix (flag ORDER): renumber the highlights by their position in the text and rewrite the summary in that order. Then write the sentence table into `checks.md`, one row per summary sentence: the comments it carries; every other claim it makes, each with the highlight that says it (a claim with none is a fail: Every claim backed); who the text gives each claim to (the authors, or a source they cite: "As Butler demonstrated" is Butler's, not the author's; Nothing added); its link to the sentence before ("and", "but", "so", the text's own) and the passage that makes it; the point of the argument (pass 1, `points.md`) the sentence serves and how, named in a few words: the claim itself, evidence for point N, the step from point N to point N+1, a definition point N uses, a contrast with point N (Aids understanding: a sentence that serves no point, or only repeats its passage, is rewritten to say how it serves one, in your own linking words around the comments); and each person, name, term or thing it refers to ("both extracts", "a passage in the middle of the novel") with where the summary introduced it (Aids understanding). A row with an empty cell where a highlight, a source or an introduction is needed is fixed before the second check: add the highlight, name the source, introduce the reference, or take the claim out.
4. **Second check: grade and run the script, then fix.** On the rebuilt plan and the summary, grade every highlight and the summary on the understanding check and the other rules, as each is graded above. Run `scripts/plan_check.py PLAN_JSON SUMMARY_FILE --pages DIR`: the plan as a JSON list of `n`, `comment`, `page` (physical), `quote` and, for a word the text defines, `"term": true`; a working copy of the summary with each comment followed by its number in square brackets (`informed by peacetime inequalities [1]`; the note itself carries no numbers); the page texts as `SKILL.md` step 5 saves them (`pages/p<N>.txt`). Fix each failing grade and each flag in the text's own words, changing nothing that passes. No failing grade, flag or table row is kept as a false alarm: each is fixed. Aids understanding is graded sentence by sentence from the sentence table: a sentence whose role is only to re-say its highlight fails, and is rewritten to say what its point does in the argument, or its restating words are cut and its comment joins a neighbouring sentence (every comment still appears once). The script leaves the wording of a sentence that cites a highlight free, so your own connecting prose can say what each point does; it flags only a sentence with no highlight behind it (Every claim backed). Your own words still add no claim (Nothing added), and a swap or dropped hedge still fails Text's own words, as graded. Then grade and run it again after each round of fixes, until nothing fails or a re-run fixes nothing new. What still fails then is not kept: it is listed for the user under "Could not fix", with what was tried and why it failed, and counts as failing. Re-check the word count against the suggested cap after any change; over it is reported, never fixed by cutting evidence, and every sentence over it carries evidence or a reason; a restating sentence loses its restating words, its comment joining a neighbouring sentence.
5. Re-check the word count against the suggested cap and every quote against its page; show the user the test table, the changed plan and the summary before anything is written, with the count failing each grade, and the "Could not fix" list, in the version shown. Never write to the library until the user approves (the OCR text-layer attachment excepted: `SKILL.md`, Rules, Approval before every Zotero write).
6. After writing, read every highlight back and compare comment, text and page with the plan (step 14, Verify).

## 4. Resuming a run

A folder without `report.md` is a resume (`SKILL.md`, Working folder and checkpoints). Read its files first and continue from the first missing one:
- `ocr.md` is missing only where step 2 or step 7 needed OCR; `pages/` counts as written once it holds a file for every page `scope.md` lists.
- Pass 3's files are taken in its order of work: `checks.md` with the first check's table comes before `summary.md`. `checks.md` counts as written once it holds the second check's table and the "Could not fix" list; with less, resume pass 3 at the first of its parts not yet done: the first check's table, then `summary.md` if it is missing, then the sentence table, then the second check.
- Where `checks.md` records a gate disagreement not yet marked acted on, resume from the stage it sent the run back to, rewriting every file from there.
- After the gate (an approval recorded in `checks.md`; with none recorded, show the gate again): first read the item's notes and annotations and continue from the first planned write not yet in Zotero, so no note or highlight is written twice. A planned highlight already in Zotero (on its page, in the signpost colour, with its comment, its key in no earlier run's record) has its key recorded in `checks.md` before going on (step 13). A covered annotation already holding the planned comment (above its `---` line, or as its whole comment where the user's had none) has its key recorded and is not combined again (step 12).
