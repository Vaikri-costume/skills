# zotero-reading-signpost

The deliverable is the reader's own summary, written afterwards in their own words from their own annotations; Claude's pass is preparation, not replacement. Claude reads the real PDF pages, states the argument the text makes, highlights the passage behind each phrase and term of it, and writes a plain summary from those phrases in the order the text makes them, "to help the reader understand the argument of the text". Once the reader approves the summary and the plan together, the note and the highlights are written, so the reader can trace each claim to its passage and agree or disagree while reading. The skill does not do the reading for the reader and adds nothing the text does not say. The summary is "not necessarily comprehensive but a tool aiding in understanding".

`scripts/` and `references/` paths are relative to this skill's folder; run scripts as `python3 -I <skill folder>/scripts/<script name>`. `references/cases.md` holds the case-only sections: where a step names one, find its heading (`## N.`) with Grep and read only that section (Read with offset and limit), not the whole file.

**Work alone: no subagents.** One source, one chapter at a time, in the main session; if the user asks for an agent anyway, its prompt must say "no subagents" and "cannot redelegate". **No artificial limits** on the number of highlights or the note's length (the summary has a suggested length, step 9); each highlight and its comment still keep the sizes `references/method.md` section 3 sets (Whole passage, Short label). **Runs only when asked**: no unasked offers of follow-up reading, extra questions or hand-off lines (the plan table, check table, profile questions and gate questions are not offers). **No purpose question**: a purpose named in the request chooses what to emphasise; otherwise state the argument plainly.

## The order of the work, and why

The order is the user's own process, taught step by step on a real article: state the argument as points; break each point into phrases and terms; highlight each one and drop what repeats; order everything by where its highlight sits in the text; only then write the summary from those phrases in that order; then grade it and fix only what fails. Writing the summary last, from highlighted phrases in the text's own order, is what keeps every claim pinned to a passage and keeps the summary meaning what the text does. Do the steps in this order and skip none.

## Working folder and checkpoints

Each run keeps its working files in `signpost-work/<attachment key>/` in the working folder (the session's current directory, or the path the project's instructions name). The key is that of the item's original PDF, found at step 2 before any OCR, and the folder keeps it when an OCR copy's key takes over for reading or highlights. For a book or volume run chapter by chapter, use `signpost-work/<attachment key>/<chapter or page range>/`, so chapters do not share files. A folder (or chapter subfolder) whose `report.md` is written holds a finished run: a new request on that item or chapter is a new run, kept in a subfolder named by the date and time it starts (`<YYYY-MM-DD>T<HHMM>/`) inside it, and the earlier run's files and recorded keys stay in place; a folder without `report.md` is a resume. The files: `scope.md` (step 4: the physical pages to read with their printed labels), `ocr.md` (only when OCR made a copy: its key, page range and time, written the moment it is attached; in a dry run, which attaches nothing, the local OCR output's path, page range and time, written when the OCR finishes; in a book or volume run it sits in `signpost-work/<attachment key>/` itself, shared by every chapter, so a later chapter reuses the copy; `references/cases.md` section 3 (Scans and OCR)), `pages/p<physical page>.txt` (the page texts read), `points.md` (pass 1), `plan.json` (pass 2, saved over each time pass 3 rebuilds the plan), `summary.md` and `checks.md` (pass 3) and `report.md` (the output contract). Write each file as its stage finishes, before the next stage starts, so a run that stops partway leaves real, inspectable work. On a resume, read these files first and continue from the first missing one; after an approved gate, read the item's notes and annotations first and continue from the first planned write not yet in Zotero, so no note or highlight is written twice. How each file counts as written, and the resume order: `references/method.md` section 4 (Resuming a run).

## First run: the profile

Everything specific to one person comes from a profile (`references/profile-template.md`), at `config/zotero-reading-signpost-profile.md` in the working folder or the path the project's instructions name. Read it before step 0. If it is missing, or a value this run needs is blank (for example colour, cap, library and lane for the item (not asked for an item in the user's own personal library, where `references/rules.md`, Write lanes, gives the default)), ask once, when the run first needs the value (library and lane at step 1, once the item's library is known), write the answers to the profile and go on; a value the run does not need stays blank, and a value whose template line says it is left blank when there is none (an AI-rules file, a note template, a patch log) is read as none, not asked. `#c9a27a` and 15% below mean the profile's `signpost_colour` and `summary_length_cap` (the template's prefilled values; a profile with either left blank is asked about like any other blank value).

## Step 0: module AI-rules gate (first, every time)

If the reading belongs to a taught module (the user names a module, week or assessment, or the item sits in the profile's `module_reading_list` or on a module's graph page), follow `references/cases.md` section 1 (Module AI-rules gate) before anything else (where the gate needs a Zotero read, such as finding the item in `module_reading_list`, step 1's tool check and item lookup run first, and nothing else does); it stops the run where the AI-rules record says so, and where a tie to an assessed piece cannot be ruled out. Read `references/rules.md` and apply it throughout.

## Books, edited volumes and module reading lists

Read `references/cases.md` section 6 (Books and reading lists) before working through a book, edited volume or reading list: a chapter or section at a time, with a checkpoint each time; reading lists one reading at a time.

## The workflow (one chapter at a time, in this order)

The step numbers are what cross-references use (`step N`).

1. **Check the live Zotero tool list.** List the Zotero tools you can actually call and take the current tool for each action from the capability table in `references/rules.md`; this skill names actions, not tools. If a needed action has no live tool, say so in one line and stop. Then find the item the user named (item key, citation key or title) with that table's find actions, and note its library. Apply the library check and write lanes of `references/rules.md`; in a group or shared library read `references/cases.md` section 10 (Shared or group library lanes). Confirm the library holding the item is active, and re-switch before every write. Where the item is in a shared or group library, tell the reader before the first write that collaborators will see it. A dry run writes nothing to Zotero (`references/cases.md` section 5 (Dry run); see Rules). Expected output: each needed action matched to a live tool, and the item's library active.
2. **Text check.** Identify the item's PDF attachment (key from the read-children action, local file path from the local-file-path action); with several, `references/cases.md` section 2 (Several PDF attachments); with none, say the item has no PDF to read or annotate and stop (a module reading list's items without one are listed for the owner, `references/cases.md` section 10). Check for a real text layer with what is installed (the page reader's garbled-page flag, `pdfinfo`, `pdftotext`, PyMuPDF). A scan, an OCR layer, or text that drops runs of words: `references/cases.md` section 3 (Scans and OCR). Expected output: the attachment key, and whether the text layer is readable.
3. **Confirm it is the right text, silently.** Read the first pages with the page-read action (and, for a chapter, the PDF outline or printed contents page step 4 needs) and compare them and the title with the item metadata, the reading-list entry and the user's message. Say something only if they do not match: then say in the chat what differs. This step neither stops nor asks; the gate and the user's replies do that.
4. **Reading scope.** The whole chapter or article by default; skim or skip only after the user says yes. Find the chapter with the PDF outline or printed contents page and map printed page labels to physical pages. Use the attachment key (Rules). Read the item's existing notes (raw HTML, no truncation) and annotations (that item only, every PDF attachment: read them by each attachment key, and count only those whose attachment key is one of this item's; a lookup by citation key can return another library's copy of the same work, which is not this item's); if it has any user annotation or a signpost from an earlier run (one whose key an earlier run recorded, or in the signpost colour), read `references/cases.md` section 4 (Existing annotations) now, before the plan table is built. Write the physical pages to read, with their printed labels, to `scope.md`. Expected output: the physical pages to read with their printed labels, and the user's existing annotations listed.
5. **Read the real pages** (physical, 1-indexed; as an image where a page garbles; a whole-text read: `references/cases.md` section 14 (Case-only Zotero actions)). Never summarise from metadata, the title or an existing note. Save each page's text to `pages/p<N>.txt`; these are the texts every later check runs against. The saved text is the PDF's text layer (or the OCR copy's), never a transcription of an image read, because the highlight tool matches the text layer; words the layer drops are restored only in square brackets (`references/cases.md` section 3 (Scans and OCR)), and a layer too garbled to anchor quotes goes to OCR at step 7. Expected output: every page `scope.md` lists read and saved.
6. **Pass 1: the argument, as points.** State the argument the text makes: its main claim, then each step it takes to reach it, one point each, in plain words, in the order of the argument (as many points as the text's argument has; the text decides). Find where the text states its argument (introduction, conclusion, headings) and let its own kind of argument set what a step is. If the author never states the claim, write "main claim not stated" and let the points carry the argument; never a guess. Each point says no more and no less than the text, its hedges kept (Text's own words, `references/method.md` section 3). No summary is written yet. Write `points.md`. Expected output: the main claim and the steps, each one line.
7. **Pass 2: phrases, terms and their highlights.**
   - **Break every point into its phrases and terms.** A term is a word the text defines: a passage says what it is. Anything the text only names, uses or describes is a phrase. For `political biases in ChatGPT-4o's interpretations of memoryscapes`, `political biases`, `ChatGPT-4o's interpretations` and `memoryscapes` are separate phrases.
   - **Pick one highlight for each phrase and term**: the passage that proves or explains it, as the Shows why and Whole passage checks describe (`references/method.md` section 3); for a term, its definition. Where a phrase is one part of a larger set (for example one strand of a package), cover the set so the reader sees where the part belongs, as Whole passage allows (one point, not a wall of several, `references/method.md` section 3). Never highlight a quote that only shares the phrase's words. A phrase that cannot be separated from its neighbour stays together, with the specific words named. The comment on a highlight is only its phrase or term, never a whole sentence or a lead-in, and carries no `writer::` line (Rules, Attribution).
   - **Drop what repeats** (`references/method.md` section 3, Drop what repeats): a phrase whose words are a term with its own highlight on its definition, or whose words sit inside another phrase's or term's highlight, gets no highlight of its own.
   - **Anchor each quote** with `scripts/anchor_check.py`, one page at a time, per `references/method.md` section 2 (Anchoring a quote): write that page's planned quotes to a parts file, one quote per line with any line break inside a quote written as a space (the script matches across line breaks), and pass it with the page's text. A passage that crosses a page break is highlighted per page, never dropped. A phrase whose passage cannot be anchored (unreadable in a partly garbled OCR layer, inside a restored run, or a repeated quote of 100 characters or fewer that cannot be lengthened past 100, `references/method.md` section 2) is dropped, but its point is kept: find another passage that makes the same point, highlight that instead and hold it in its place in the order; only where no passage makes the point does it come out (no inferences). A quote that fails only at creation is retried at step 13, then reported. If quotes will not anchor because the text layer is garbled or scanned, OCR into a new attachment (`references/cases.md` section 3 (Scans and OCR)).
   - **Order everything by highlight position** in the text: page, then place on the page, and number the highlights in that order.
   - Write `plan.json`: a list of `n`, `comment`, `page` (physical), `quote` (the page span `anchor_check.py` printed for it, the text step 13 gives the tool, `references/method.md` section 2) and, for a term, `"term": true`; the parts of a page-split passage share one `n`. Expected output: every phrase and term with an anchored quote, numbered in text order.
8. **The plan table** (kept up to date through pass 3 and shown to the user once, at the gate): the comment, exact quote, physical page, printed page label, and whether the quote lands on one of the user's own annotations (`covered` when the quote lies within the annotation or equals it; `partial overlap` when they share only part of the text, including a single annotation lying wholly inside the quote; mark every such case; the rules for them are in `references/cases.md` section 4 (Existing annotations), read at step 4). Report the highlight count; the summary's sentence count is reported at step 9. Expected output: the plan table with every row filled and the highlight count.
9. **Pass 3: write the summary, then grade and fix**, in the Order of work of `references/method.md` section 3: the first check on the plan; the summary written; the second check, graded and run through `scripts/plan_check.py`; what is shown to the user.
   - **The summary** is written from the phrases and terms in the order of their highlights, so it reads as the text's own sequence and means what the text does. Every comment appears in it word for word, once, in a sentence of your own that says how the text uses that point (what it supports, what it leads to next), never the passage re-said in the text's sentence (Aids understanding, `references/method.md` section 3). Introduce every person, name and term where it first appears. It answers one question: what argument is this text making? It is plain and easier to follow than the original, and gives no separate plain-words explanation. Its first sentence is the main claim where the text states it, otherwise the argument through the text's stated points, each highlighted, and names the subject. Section headings are the text's own, or none; a heading is a plain line of its own (no Markdown marks) with a blank line before and after it, which `note_html.py` prints as its own paragraph. Write `summary.md` with each comment followed by its number in square brackets (`informed by peacetime inequalities [1]`); the note itself carries no numbers. Report its sentence count.
   - **Length cap: about 15% of the word count of the pages summarised, as a guide** (the user's cap is suggestive, not a limit). Run `scripts/cap_check.py summary.md` with the page files of the pages summarised only (`pages/p<N>.txt` for each page `scope.md` lists, the chapter or article in step 4's scope; not pages read only to place it, such as a contents page or the next chapter's opening) and `--cap` set to the profile's `summary_length_cap` (15 by default), and report both counts (the summary's words and the cap in words, from the line `cap_check.py` prints). A summary over the cap is not a fail: cut restatements first, but never cut a highlight, its evidence or a step of the argument to fit the cap. Over the cap, every sentence must earn its place by carrying evidence or a reason the argument needs; a sentence that only restates its highlight is rewritten to say what the point does, or its restating words are cut and its comment joins a neighbouring sentence, so every comment still appears once (Aids understanding). Expected output: both counts, and, when over, the summary with no restating sentence.
   - **The sentence table**: one row per summary sentence in `checks.md`, giving every claim it makes with the highlight behind it, who the text gives the claim to, its link and the passage that makes it, the role it gives its point, and where each name or reference it uses was introduced (`references/method.md` section 3, Order of work, step 3). Every empty cell where a highlight, a source or an introduction is needed is fixed before the second check (the first sentence has no link to a sentence before).
   - **Grade and fix only what fails**, in the text's own words, changing nothing that passes. No failing grade or flag is kept as a false alarm; what still fails after the re-runs goes on the "Could not fix" list (Order of work, step 4, Second check). Write the check table and the "Could not fix" list to `checks.md`. Expected output: `plan_check.py` exits 0, or every flag still open is on the "Could not fix" list with what was tried.
10. **The gate: one approval of the summary and the plan together.** Show the summary (with both word counts), the plan table and the check table. Nothing goes into Zotero before the approval (Rules, Approval before every Zotero write). Record the approval in `checks.md`: the time and the user's exact words. If the user disagrees with how the argument was read (the points of pass 1), re-read the pages and redo the work from pass 1; if they say it is the wrong item or attachment, go back to step 1 or step 2 with the one they name; if the wrong pages, go back to step 4; if they disagree with the plan or the summary, revise and re-run pass 3. Record the disagreement in `checks.md` with the time and the stage it sends the run back to, and mark it acted on when the redone version reaches the gate. The gate records (approvals and disagreements) sit at the head of `checks.md` and stay there when pass 3 rewrites its own parts of the file. Either way, show the gate again: only an approval of the version shown is recorded. A dry run stops here. Expected output: the approval (time and exact words) recorded in `checks.md`, or a recorded disagreement and the stage it sends the run back to.
11. **Write the note** (after the gate). A Zotero note on the item as a Signpost Summary (`type:: Signpost Summary`; Reading Notes are the user's own and this skill never creates one), holding the approved summary, laid out by `scripts/note_html.py` per `references/method.md` section 1, with `writer:: Claude` once, in the header (Rules, Attribution). It lists no pages read (the chat report does). Read it back (raw HTML, no truncation). An existing Gemini or NotebookLM note is never replaced or deleted; if the item has one, read `references/cases.md` section 12 (Existing AI-summary notes; and section 13, Patch log, before any patch-log row). Expected output: the note key, and the read-back matching the approved summary.
12. **Existing annotations** (read in step 4; re-read before writing). The user's are never recoloured or deleted, and nothing the user wrote is edited or removed, only added to. Where the plan marks a quote as covered by one, combine by updating it in place (no new highlight for that phrase; the update tool is in `references/cases.md` section 14 (Case-only Zotero actions)); partial overlaps, several annotations and annotations on another attachment follow `references/cases.md` section 4 (Existing annotations). The plan approval covers the update of a covered annotation. Format of the combined annotation: Claude's comment, then a line `---`, then the user's comment verbatim; if the user has no comment, Claude's comment alone, with no divider. Write each combined annotation's key to `checks.md` as it is updated, as step 13 does for a created highlight, so a resume never combines it twice and step 14 counts it (a resume's check for a combination already made: `references/method.md` section 4 (Resuming a run)). Expected output: each covered annotation updated once, its key in `checks.md`.
13. **Create the highlights**, one per phrase or term (one per page for a page-split passage), except a row step 12 combined into an existing annotation and a row marked `earlier signpost` (`references/cases.md` section 4), in the signpost colour `#c9a27a`, on the attachment key steps 4 to 13 use (the PDF found at step 2, or the OCR copy recorded in `ocr.md` where OCR at step 2 or step 7 made one, `references/cases.md` section 3 (Scans and OCR)), on the exact verbatim words, with the comment from the approved plan (Claude creates highlights only with a comment). Never paraphrase, never anchor to a nearby passage, never accept the create tool's "did you mean" suggestion. If a quote does not match at creation, or a highlight lands on another page: `references/cases.md` section 7 (Creation failures: retry on a shorter run; a wrong-page highlight is a failure, leave it in place and report it). Write each created highlight's key to `checks.md` as it is created, so a resume and step 14 know this run's highlights (a resume's check for a highlight already created: `references/method.md` section 4 (Resuming a run)). Expected output: one highlight per plan row not combined at step 12 and not marked `earlier signpost`.
14. **Verify.** Re-read the item's annotations: every planned phrase and term has exactly one highlight (one per page for a page-split passage) in `#c9a27a`, on the planned page, with its comment; the count of this run's highlights (the keys steps 12 and 13 recorded in `checks.md`: created highlights and combined annotations) equals the plan, leaving out signposts from earlier runs or earlier chapters (`references/cases.md` section 4) and rows marked `earlier signpost`. Report as differences from the plan: a shortened run (step 13), with the approved quote beside it; a combined annotation (step 12), which keeps the user's colour and counts as the phrase's highlight; and any other difference. A partial overlap that the gate approved as a separate highlight counts as ordinary. Expected output: a verify result that matches the plan, or each difference listed.
15. **Checkpoint.** Write `report.md` (the Output contract) and stop after the chapter. When a module AI-rules file applies (step 0), record the use in that file's decisions and use log, in the format that file gives (`references/rules.md`, Order of work). Do not start the next chapter unless the user has said to run the whole book on (Rules). Expected output: `report.md` written and the chapter reported.

## Rules

- **Verbatim passages**: the anchor text matches the PDF's extracted text exactly; never paraphrase to make it fit.
- **One phrase or term, one highlight, tight** (one per page for a page-split passage): no wider than the passage that proves or explains it; never stretch a highlight over filler.
- **Signpost colour only**: `#c9a27a` (named Signpost in the user's Zotero colour list) on everything this skill creates. It means only "Claude's signpost for a phrase of the approved summary": no colour per claim, no other meaning encoded in colour, and kept separate from the user's annotation colours. Its place in Zotero's colour list (settings first): `references/cases.md` section 8 (Signpost colour), read before a test or when the colour does not show as Signpost. Whether the user's Zotero colour rule adds the Signpost tag is a profile value (`signpost_tag_by_colour_rule`); this skill never adds or edits a tag.
- **Attribution**: the note carries `writer:: Claude` once, in its header. Nothing else this skill creates carries a `writer::` line: a highlight comment is only the phrase or term, and the signpost colour marks it as Claude's. In a combined annotation (step 12) the user's colour stays, so the text above the `---` divider is Claude's. The author's wording is quoted or attributed, never passed off as Claude's. A note without `writer::` is the user's; never put `writer:: Claude` on the user's notes.
- **Attachment key**: reading, highlights and every call that takes an attachment key use the PDF attachment's key, never the parent item's (the Read children row of the capability table in `references/rules.md` lists the calls).
- **Dry run**: writes nothing to Zotero. It runs every step up to the gate (step 10) in one turn and stops there, marking steps 11 to 15 `not run: dry run`; the working files are still written, `report.md` included. The stops that still apply, the AI-use record a taught-module dry run still makes, and the report: `references/cases.md` section 5 (Dry run).
- **Run the whole book on**: lifts only the end-of-chapter stop of step 15; the gate still applies to every chapter.
- **Never touch tags, collections, plugins (install nothing), settings or the user's annotations** beyond step 12. Items stay where they are: signposting changes no collection (a collection change happens only as `references/cases.md` section 11 (Collections and tags) allows, on the user's per-item yes or a lane grant, never as part of a run). Never delete anything, stub or duplicate notes included: deleting one is the user's action in Zotero, on their per-item word.
- **Approval before every Zotero write** (the OCR text-layer attachment needs none); the step 15 use-log entry and the working files are not Zotero writes and need none; one source at a time.

## Examples

**Example: one article**
User says: "Signpost <citation key>."
→ reads every page and saves the texts → states the argument as six points → breaks each point into phrases and terms, highlights each, drops what repeats, anchors, orders by position → writes the summary from those phrases, checks the cap, grades and fixes → shows the summary, plan table and check table and waits → after approval writes the note, creates the highlights, verifies and stops at the checkpoint.

**Example: a dry run**
User says: "Signpost this reading as a dry run."
→ every step up to the gate, with the working files written and nothing written to Zotero.

## Troubleshooting

**Wrong or empty page text**
Cause: pages were read with the parent item key. → Fix: use the attachment key from the read-children action.

**A quote will not anchor**
Cause: the quote was copied from memory, or the text layer is garbled or scanned. → Fix: copy it again from `pages/p<N>.txt` (OCR marks included) and re-run `anchor_check.py`; for a garbled or scanned layer, `references/method.md` section 2 and `references/cases.md` section 3 (Scans and OCR).

**`plan_check.py` flags ORDER or MISSING on a page-split passage**
Cause: the two parts do not share one `n`. → Fix: give both parts the phrase's number and comment.

**The summary is over the cap**
Cause: the summary restates passages instead of saying what each point does, or the text needs that many highlights. → Fix: cut the restatements (Aids understanding, `references/method.md` section 3) and re-run `cap_check.py`; what is still over stays, with both counts reported (the cap is a guide).

**A note's structure is lost on edit, or its formatting or wikilinks break**
Cause: it was read without raw HTML or truncated, or Markdown was written. → Fix: read raw HTML, untruncated, and write the HTML that `note_html.py` prints.

**A highlight is on the wrong page**
Cause: the quote's words also occur on another page, or the layer differs from the page read. → Fix: `references/cases.md` section 7 (Creation failures).

**The write path differs from the read one** (the capability table in `references/rules.md`)
Fix: on the first write say which path was used.

## Output contract

For a dry run, `references/cases.md` section 5 (Dry run) lists the fields that change; every other field applies. For each chapter, one line per field, also written to `report.md`:

- pages read (physical pages, with the printed page labels beside them, and any not read)
- the attachment key used for reading and, where it differs (an OCR copy), the one used for highlights
- the argument as points (pass 1)
- the summary, with its word count against the suggested cap
- the count failing each question of the understanding check and each other rule (`references/method.md` section 3), and the "Could not fix" list (each grade or flag still failing, with what was tried)
- summary and plan approved
- note written (key)
- number of highlights created, each in `#c9a27a`, and any difference found at verify (including combined annotations)
- any phrase that could not be anchored, the passage that carries its point instead, and where the cause is an unreadable passage, that a text-layer copy would restore it
- where the text gives no evidence for a phrase, or no more than a label, that it says so
- the summary's sentence count and the plan's highlight count
- which extraction order found each quote
- which write path was used on the first write
- the conditional fields of `references/cases.md` section 9 (Conditional report fields, read at step 15 when a scan, an OCR copy, a text mismatch, a wrong-page highlight, a restored run, an empty `related::`, an omitted `citekey::`, a user annotation left uncombined on another attachment or a planned quote on an earlier signpost occurred)
- that the run has stopped at the checkpoint and the next chapter is not started, or, where the user said to run the whole book on, which chapter follows

Nothing beyond these fields.

## References

- `references/method.md` (every run): note layout, anchoring a quote, the pass 3 checks and their order of work.
- `references/rules.md` (every run): the Zotero workflow rules, write lanes and the capability table (Zotero actions matched to the live tools).
- `references/cases.md` (one section at a time, where a step names it): 1 module AI-rules gate, 2 several PDF attachments, 3 scans, OCR and restored runs, 4 existing annotations, 5 dry run, 6 books and reading lists, 7 creation failures, 8 signpost colour in Zotero, 9 conditional report fields, 10 shared or group library lanes, 11 collections and tags in detail, 12 existing AI-summary notes, 13 patch log, 14 case-only Zotero actions, 15 pass 3 worked examples.
- `references/profile-template.md`: the per-user profile.
- `scripts/anchor_check.py` (step 7): offline check that each planned quote exists verbatim (after normalising hyphens, ligatures, line breaks) in the page text.
- `scripts/plan_check.py` (step 9): one check of the plan and the summary together; its flags are listed in full in its docstring (not placed, order, overlaps, terms, comment length, same claim, negation, missing, tandem, wording, links).
- `scripts/context_check.py` (step 9): the sentence before and after each highlight, where a claim's reason or evidence usually sits.
- `scripts/cap_check.py` (step 9): the summary's word count against the length cap.
- `scripts/note_html.py` (step 11): the note's HTML from the approved summary and the item's properties.
- Tools only, not called by any step: `scripts/copy_check.py` (clauses that copy the source; it flags the text's own wording, which Text's own words keeps), `scripts/term_check.py` (summary words the source never uses: candidate swaps for the Text's own words grade, which is graded by hand), `scripts/tandem_check.py` (`plan_check.py` covers it), `scripts/pin_check.py` (summary stretches with no comment behind them).
