# Skill Creator

For creating new skills and iteratively improving them. Core loop: decide what the skill should do → write a draft → run claude-with-and-without-skill on test prompts → help the user evaluate qualitatively (via `eval-viewer/generate_review.py`) and quantitatively (drafted while runs are in flight) → rewrite based on feedback → repeat until satisfied → expand the test set at scale.

Figure out where the user is and jump in. "I want a skill for X" → walk the whole loop. Has a draft → go straight to eval/iterate. Wants to skip evals and vibe → do that. After the skill is done, optionally run the description-improver script to tune triggering.

Jargon calibration: users range from non-coders to engineers. "Evaluation"/"benchmark" usually OK; "JSON"/"assertion" only after the user shows they know them. When in doubt, define inline in one short clause.

---

## Portable mode and tiers

Every CCVW skill declares `metadata.tier`. The tier governs frontmatter rules, body content, and where eval/audit outputs live.

| Tier | Use for | Allowed | Forbidden |
|---|---|---|---|
| `personal` | iteration; your own setup | hardcoded user paths, local MCPs, your Claude Code config | — |
| `claude-users` | finished skills shared with Claude Code AND Cowork users | Claude-Code + Cowork extensions (Agent, dynamic injection, `$ARGUMENTS`), marketplace access | user-specific paths, assumed-local config |
| `model-agnostic` | non-Claude runtimes (Gemini CLI, Cursor, OpenCode, agentskills.io agents) | agentskills.io base spec only | Claude-Code extensions; storage must use runtime APIs |

Full per-tier rules, Claude-extension blocklist, and path-mapping in `references/portability-spec.md`.

`scripts/portability_lint.py` runs at scaffold and every tier transition. At `personal` it's informational; at `claude-users`/`model-agnostic` the orchestrator proposes fixes and confirms before applying. Tier changes only on explicit user request — never auto-bump.

## Creating a skill

### Capture Intent

Start by understanding the user's intent. The current conversation might already contain a workflow the user wants to capture (e.g., they say "turn this into a skill"). If so, extract answers from the conversation history first — the tools used, the sequence of steps, corrections the user made, input/output formats observed. The user may need to fill the gaps, and should confirm before proceeding to the next step.

While capturing intent, identify which **skill use-case category** this is — Document & Asset Creation, Workflow Automation, or MCP Enhancement — or flag it as "other" if none fit cleanly (see `references/build-planning.md` "Skill use-case categories" for the full taxonomy and the "other" escape). The category tells you which authoring techniques and patterns to reach for at draft time.

1. **What should this skill enable Claude to do — as 2–3 concrete use cases?** Don't settle for one vague "it helps with X." Name 2–3 specific use cases the skill must enable, each as a `{name, trigger, ordered steps, end result}` quadruple — e.g. *"Sprint planning: user says 'plan this sprint' → fetch status, analyze velocity, propose priorities, create tickets → fully planned sprint."* Concrete use cases sharpen the description's trigger phrases (Q2) and define what "working" means later. **Capture these answers now — they are written to README.md when the file is scaffolded** at "### Write the three root files" below (README.md does not exist yet at this point; the same capture-now/write-later pattern as Step 3's author identity). The destination fields are `## What this skill does` + `## How to invoke` (the four-field form is in `references/readme-template.md`).

   **Then walk the ordered steps and mark the DETERMINISTIC ones for scripting.** As you enumerate each use case's steps, flag every step that is mechanical — same inputs always produce the same correct output (e.g. parsing, counting, formatting, validating, regex, date/string munging, JSON shaping, writing a structured row/file, enumerating files with an exclude list — the list is illustrative; the test is the criterion just stated, not membership in it). Those are candidates to **ship as a bundled `scripts/` helper with a stated input→output contract**, NOT prose the executor re-derives (and re-derives slightly differently) every run — "code is deterministic; language interpretation isn't." Leave genuine *judgment* steps as prose (examples — not an exhaustive list: is this a real bug? does this fix preserve intent? which category applies?). The deterministic test above is the decider: a step is scripted iff it meets the same-input→same-output criterion; any step that does not (whether or not it resembles the judgment examples) stays prose. Record the marked steps as a checklist (e.g., inline in the session as "deterministic steps: [step1, step2, …]") that you consult at "Write the three root files" — hold it using a visible note in your response (the primary mechanism for all captured values in this workflow) or `productivity:memory-management` if available — so the deterministic ones land in `scripts/` in the FIRST draft. (This is the design-time complement to the reactive "bundle repeated work" rule under "Improving the skill" — catch it at design, not after N eval runs each re-improvised it. Category-2 Workflow-Automation skills hide the most such steps — see `references/build-planning.md`.)
2. When should this skill trigger? (what user phrases/contexts — drawn from the use cases' triggers above)
3. What's the expected output format?
4. **Why this skill — what does it optimize for, what does it trade off?** (the design intent: "this prioritizes X over Y because Z"). This is load-bearing — it becomes the README.md `## Intent` section that skill-tracer's orchestrator reads to make considered-fix decisions later. A vague answer here weakens every downstream trace.
5. **What standing PREFERENCES should this skill always honor, and what DOMAIN EXPERTISE should it embed?** A skill's whole value is teaching Claude something once instead of re-explaining it every conversation — and "something" is exactly three things, not one: the *process* (the steps, captured in Q1), the user's *preferences* (formatting, tone, conventions, tools to prefer or avoid — the things the user keeps correcting Claude on), and *domain expertise* (the gotchas, rules-of-thumb, and hard-won knowledge a non-expert wouldn't know). Ask for all three. Preferences and short rules go into the SKILL.md body; substantial domain knowledge goes into a `references/<domain>.md` file the skill loads as needed. (A useful threshold: if the domain knowledge is more than ~10 rules or multi-sentence explanations, or forms a reference section the executor would load selectively rather than always, extract it to a reference file; a few short bullet points that always apply can stay inline.) A skill that captures only the steps, omitting preferences and domain knowledge, silently fails the "teach once" promise.
6. Should we set up test cases to verify the skill works? Skills with objectively verifiable outputs (file transforms, data extraction, code generation, fixed workflow steps) benefit from test cases. Skills with subjective outputs (writing style, art) often don't need them. Suggest the appropriate default based on the skill type, but let the user decide.
7. Intended audience? **Default `claude-users`** (Claude Code + Cowork users — shareable to friends/family/coworkers running Claude — applies unless the user says otherwise; matches `tier: claude-users`). Exceptions: `personal` (only this user — hardcoded paths OK; matches `tier: personal`), `model-agnostic` (Gemini/Cursor/OpenCode-portable from day one; matches `tier: model-agnostic`). Personal is the exception, not the default — sharing is implicit unless the user opts out. `intended-audience` and `tier` use the same value triplet and default the same way.

**Intent answers feed README.md + frontmatter.** Q1 → `## What this skill does` (use-case quadruples as bullets) + `## How to invoke` (use the Q1 trigger phrase as the natural-language trigger; use the end-result as the purpose description; construct the worked example from trigger → first ordered step → end result). Q2 → `## How to invoke` trigger phrases. Q3 (expected output format) → the skill's stated output contract in the SKILL.md body (not a distinct README section). Q4 → `## Intent`. Q5 → SKILL.md body + `references/<domain>.md`. Q6 → decision on whether to set up `evals/evals.json` (not a README section). Q7 → `metadata.tier`/`intended-audience` (not a README section). (`allowed-tools` frontmatter comes from the Interview "Which tools are needed" scoping question below, not from a Capture-Intent Q.) The README is mandatory (`references/readme-template.md`).

### Interview and Research

Proactively ask questions about edge cases, input/output formats, example files, success criteria, and dependencies. Wait to write test prompts until you've got this part ironed out.

Four scoping questions sharpen the build before drafting (they refine the Capture-Intent answers into buildable specifics):
1. **What does the user ultimately want to accomplish?** (the outcome behind the use cases)
2. **What multi-step workflows does that require?** (the ordered steps each use case decomposes into)
3. **Which tools are needed — built-in or MCP?** This directly drives the `allowed-tools` frontmatter: name the specific tools (`Bash`, `Write`, `Edit`, `Skill`, specific `mcp__*` servers) so the conservative default (`["Read"]`) is widened only as far as the skill actually needs.
4. **What domain knowledge or best practices should be embedded?** (the Q5 domain-expertise answer, made concrete — the rules, gotchas, and conventions to bake in).

Skim 1–2 existing skills as structural references before drafting — either similar skills surfaced by the marketplace check below, or the example skills installed by marketplace (at `~/.claude/plugins/marketplaces/claude-plugins-official/plugins/` if the marketplace plugin is installed). Seeing a real skill's shape (frontmatter, body sections, references layout) produces a better first draft than starting from a blank file.

Check available MCPs - if useful for research (searching docs, finding similar skills, looking up best practices), research in parallel via subagents if available, otherwise inline. Come prepared with context to reduce burden on the user.

If this is an MCP-enhancement skill (Category 3), read `references/mcp-enhancement-skills.md` — it covers what to elicit (happy-path call sequence, failure/empty-result handling, rate/ordering constraints, tool gotchas) and how to author the call-sequencing + error handling that make such a skill reliable.

### Decide: install, improve, or build

Now that intent + research are captured, choose a path before drafting anything:

**Step 1 — Marketplace check** (mandatory before every new build). Invoke `marketplace-discover` as a Skill tool, passing the captured intent + research as `$ARGUMENTS` (a prose string — at minimum name the target domain, the key action verbs from Q1 triggers, any tool/integration constraints from the Interview "Which tools are needed" answer, and the primary end-result; these are minimums, not a rigid template — write naturally. When Q1 answers are in the structured quadruple form {name, trigger, ordered steps, end result}, combine name + trigger + end result into natural-language prose; add domain constraints from Q5.). If `marketplace-discover` is unavailable (the skill is not installed), skip to Step 2 and proceed on Path 3. If it returns an error or zero results, proceed to Step 2. The check reads the live marketplace catalog and presents ranked recommendations.

- If a top recommendation is a strong match (a skill whose documented capabilities and trigger phrases closely align with the user's stated use case — one the user would likely adopt as-is or with minor configuration) and the user chooses to install it, run the install via `marketplace-discover`'s direct-install step and exit. **You took Path 1; you're done here.** If the user declines to install or evolve a strong match, proceed to Path 3 directly. If the user neither accepts nor explicitly declines (e.g. asks a follow-up question or defers), answer the follow-up and then re-present the choice — wait for an explicit accept or decline before routing to a path.
- If the user wants to evolve an existing installed skill that matches the need, switch to `references/improve-existing-skill.md` (start at Step 1 of that file). **You took Path 2; that reference takes over the workflow** and runs to its own completion (it ends with its own trace/ship handoff) — control does not return to the "Decide" step. You **may** use SKILL.md's "Running and evaluating test cases" section and the eval viewer/grader/aggregator steps while on Path 2 — those are shared infrastructure, not Path-3-only; use them when you want to measure whether your changes improved performance (compare old vs new skill versions via the benchmark workflow).
- Otherwise proceed to Step 2. **You're on Path 3.** (This covers all non-strong-match cases — weak matches, no results, or error from the marketplace check. The user-confirmation requirement differs by which sub-case you are in: a **declined strong match** needs NO further confirmation (the user already decided) — proceed to Path 3 directly; a **weak match** DOES need a confirm — briefly mention the near-misses to the user ("I found some related skills but none are a strong match: [names]") before proceeding to build new; **no results / error** needs no confirm — proceed silently. So the discriminator is the marketplace result you actually got, and only the weak-match sub-case pauses for a confirm.)

**Capture** the marketplace-check timestamp now; **write it to HISTORY.md** when that file is scaffolded at "### Write the three root files" below (same capture-now/write-later pattern as Q1 use-cases and Step 3 author identity — HISTORY.md does not exist yet). Hold the value as a visible response line (e.g. "marketplace timestamp: 2026-05-31T11:27") — the value spans a context boundary; use `productivity:memory-management` as a supplement for extended sessions. **To retrieve**: scan your prior responses for the label. If prior responses are unavailable (compaction / new session) and `productivity:memory-management` is also unavailable, ask the user to re-provide the timestamp before writing HISTORY.md. **When re-entering a build where HISTORY.md already exists**: skip if it already has a `checked-marketplace:` line. The value goes as a `checked-marketplace: <Runtime>` line in the Lineage notes so re-triggers don't re-ask. Format: a plain text key-value line (e.g., `checked-marketplace: 2026-05-31T11:27`) placed as the first line directly under the `## Lineage notes` heading — its own line, above the free-form prose, separated from the prose by a blank line — in the HISTORY.md markdown body (not YAML frontmatter). The Lineage notes section is the `## Lineage notes` freeform prose section defined in `references/history-template.md` — it is part of the HISTORY.md body, after the YAML frontmatter block. (`<Runtime>` = ISO-8601 UTC now, format `YYYY-MM-DDTHH:MM` — e.g. `2026-05-31T11:27`.) The value is **free-form** — write it bare and unquoted; no script parses it (the only consumer is the human-readable re-entry check "does a `checked-marketplace:` line already exist," a substring read), so the exact form is not load-bearing beyond starting the line with `checked-marketplace:`. (It's build-process provenance, not a runtime-contract field — it lives in HISTORY.md, not SKILL.md frontmatter.)

**Step 2 — Attribution category** (mandatory for Path 3; Path-2 executors have already exited above). Ask the user which of four categories applies:

- **A. Direct fork** — structurally derived from an existing skill
- **B. Derivative work** — uses a named pattern (cold-parallel dispatch, ralph-loop, etc.) reimplemented
- **C. Idea inspiration** — influenced by another skill, no structural overlap
- **D. Independent design** — no recognizable lift

The category drives the `HISTORY.md` attribution fields (`category`, `author.history[]`, `inspirations[]`) per `references/attribution-spec.md` (full thresholds, schemas, license-preservation rules, worked examples) and `references/history-template.md` (the HISTORY.md format). When in doubt between adjacent categories (A↔B, B↔C, C↔D — see `references/attribution-spec.md` "How to decide between categories — the squishy lines"), choose the more-attributing one. (Path 2 executors read the attribution category from the installed skill's existing HISTORY.md rather than choosing a new one here; improve-existing-skill.md handles that flow.)

**Step 3 — Author identity** (mandatory). Determine the user's actual identity — GitHub username or preferred attribution name — to become `HISTORY.md`'s `author.primary`. Never the literal placeholder `user`. Ask once if unknown; remember via `productivity:memory-management` so future scaffolds don't re-ask (if that skill is unavailable, hold the value inline in the session the same way as the marketplace timestamp above). Steps 1–3 are a decision phase — capture this value now (same capture-now/write-later pattern); write it to HISTORY.md when that file is scaffolded below.

**Attribution answers feed HISTORY.md, not SKILL.md frontmatter.** The category + author + inspirations land in `HISTORY.md`'s YAML frontmatter (top-level fields). SKILL.md frontmatter stays lean (runtime contract only). See `references/history-template.md`.

Once Steps 1-3 settle, proceed to "### Write the three root files".

### Write the three root files

Every CCVW skill ships three root markdown files (SKILL.md + README.md + HISTORY.md), three directories (scripts/ + references/ + assets/), and a glossary. The scaffold creates them with sensible defaults the user reviews and edits. Full structure: `references/skill-structure-spec.md`.

**SKILL.md** — the runtime workflow. Frontmatter is the lean runtime contract:
- **name** — skill identifier (1–64 lowercase alphanumeric + hyphens).
- **description** — when to trigger + what it does. Primary triggering mechanism; all "when to use" lives here. Lean pushy — Claude under-triggers.
- **license**, **compatibility**, **metadata** (required keys: `tier`, `created`, `created-by`, `parent-version`, `intended-audience` — runtime-relevant only), **allowed-tools**. See `references/skill-structure-spec.md`. Note: `version`, `author`, `inspirations`, `category`, `checked-marketplace` do NOT go here — they live in HISTORY.md.
- Body: the workflow instructions per `references/skill-writing-style.md` — pick the authoring pattern matching the skill's category, follow the body skeleton, and give the skill the reliability properties every skill should have (next-step guidance, embedded best-practices, a stated output contract). Keep it composable and single-scope (see the cross-cutting guidance there).

**README.md** — human intent (mandatory). Scaffold from `references/readme-template.md`. Populate `## What this skill does` (Capture-Intent Q1), `## Intent` (Q4 — the load-bearing design-intent section tracer reads), `## When to use / When NOT to use`, `## How to invoke` (Q2 triggers). Leave `## How to install` and `## Sibling skills` as placeholders — skill-publisher fills them at ship time. The remaining template sections (`# <Skill Name>` title and `## For developers`) carry the template's fixed boilerplate — keep them from `references/readme-template.md` as-is; this populate/placeholder split covers only the interview-driven and publisher-filled sections, not those two.

**HISTORY.md** — provenance + changelog (mandatory). Scaffold from `references/history-template.md`. YAML frontmatter: `version: "1.0.0"`, `category` (from attribution Step 2), `parent-version` (null for fresh), `author` (primary + history chain for Category A), `inspirations` (for Category B). Markdown body: initial changelog entry (`### 1.0.0 — <date>` + "Initial scaffold") + lineage notes.

**Required directories** (`.gitkeep` if empty): `scripts/`, `references/`, `assets/`. **Note: `evals/` is NOT scaffolded automatically** (it is created lazily when you first write evals.json, to avoid an empty directory in skills that do not reach the eval phase) — when you later write `<skill-path>/evals/evals.json` during test-case drafting, run `mkdir -p <skill-path>/evals` first (idempotent — safe to run even if the directory already exists from a prior recovered build). Into `scripts/` go the deterministic steps marked back in Capture-Intent ("mark the DETERMINISTIC ones for scripting") — ship them as bundled helpers with a stated input→output contract in this first draft, rather than leaving them as prose each eval run re-improvises. If re-entering after compaction and the checklist is unavailable, check the task tree plan first; if absent there too, ask the user which steps they intended to script before proceeding.

**Required reference file**: `references/glossary.md` — scaffolded from `references/glossary-template.md` (when copying, perform the template's own substitutions: replace `<SKILL-NAME>` in the heading, delete the "How to use this template" section and the `<example-term>` placeholder row, and add the skill's actual terms — do NOT ship the template's instructional scaffolding verbatim, because a shipped glossary still carrying the how-to text or the `<example-term>` row reads as unfinished and gets flagged by skill-tracer's cold read), inherits CCVW shared vocab from `references/ccvw-glossary.md`.

**LICENSE file at skill root**: required for Category A forks. See `references/attribution-spec.md`.

### Scaffold-time lint checks

Run exactly these three lints (the complete scaffold-time set — no other scripts from `scripts/` need to be run at scaffold time) the moment the scaffold's files exist (before the first eval). Capture the output of each lint by redirecting stdout. `portability_lint.py` and `attribution_lint.py` emit **JSON** — capture into a shell variable (any name works; `output=$(python3 scripts/portability_lint.py <skill-path>)` uses `output`) then inspect `would_fail_at_tiers`, `tier_violations`, `ccvw_mandatory_missing` programmatically. `quick_validate.py` emits a **plain string** (e.g., `"Skill is valid!"` or `"Name must be kebab-case"`) — do NOT try to parse quick_validate.py's output as JSON; just check its exit code (The correct interpretation: check the exit code as the pass/fail signal; still read and display the stdout message to the user or for diagnostics — the warning is against parsing stdout as JSON, not against reading it at all.) When you apply a tier change (edit `metadata.tier` from one tier to another — writing `metadata.tier` for the first time during initial scaffold is not a tier change; that case is covered by the initial scaffold-time lint run; testable condition: a tier change occurs when SKILL.md already exists on disk with a prior `metadata.tier` value and you are changing it to a different value), immediately re-run `portability_lint.py` as part of that operation — don't wait for the user to separately ask:

```bash
# run from ~/.claude/skills/skill-creator-ccvw/ (the scripts/ directory is relative to this skill's root)
python3 scripts/quick_validate.py   <skill-path>   # frontmatter parse + structural gate
python3 scripts/portability_lint.py <skill-path>   # CCVW structure + tier + name/folder/reserved checks (no --tier flag needed — the script reads metadata.tier from SKILL.md; pass --tier only to test hypothetical tier compatibility)
python3 scripts/attribution_lint.py <skill-path>   # HISTORY.md attribution well-formedness
```

**`portability_lint.py`** checks CCVW-mandatory structure (including README.md + HISTORY.md), tier-portability violations, personalization (cat 15 user-name leakage — anonymize prompt at `claude-users`/`model-agnostic`; cat 16 plan-document leakage — flagged at every tier), AND scaffold-time structural correctness that holds at every tier: the `name` is kebab-case (`name-format`), the `name` matches the skill folder basename (`name-folder-mismatch`), the `name` does not use a reserved `claude`/`anthropic` prefix (`reserved-name`), no XML-tag-shaped `<...>` content anywhere in frontmatter (`frontmatter-angle-bracket` — a prompt-injection surface, since frontmatter is injected into the system prompt; version operators like `>=2.0` are fine), the description is ≤1024 chars (`description-too-long`), `compatibility` is 1–500 chars (`compatibility-length`), and the main file is named exactly `SKILL.md` (`skill-md-misnamed` — the diagnostic compares real directory entries, so it catches a `Skill.md`/`skill.md` variant even on macOS's case-insensitive filesystem). The parenthetical is each rule's `violation type` in `references/skill-structure-spec.md`. Full rule list: `references/skill-structure-spec.md` "Scaffold-time structural rules".

**`quick_validate.py`** is the fast frontmatter gate (parses YAML, asserts `name`/`description` present, name kebab-case + ≤64 chars, description ≤1024 chars + no angle brackets at all in the **description field** (stricter than portability_lint's tag-shaped check — even `>=2.0` fails in description, so put any version constraint in `compatibility`, never the description; this rule is description-field-only; `portability_lint` applies a tag-shaped regex (not a bare-character check) to ALL frontmatter fields including description, so `>=2.0` passes portability_lint even in the description — but fails quick_validate), compatibility ≤500 chars, and that only allowed top-level keys appear). Run it first — a non-zero exit means SKILL.md's frontmatter itself is malformed. **Fix it before running the other lints:** `portability_lint.py` would parse an empty dict and produce spurious missing-field findings (noise); `attribution_lint.py` reads HISTORY.md so is unaffected, but it's cleanest to resolve all frontmatter issues first.

**`attribution_lint.py`** verifies HISTORY.md's attribution fields are well-formed for the declared category. **If HISTORY.md is missing entirely**, the script exits 1 with `{"error": "HISTORY.md not found at …", "note": "…"}` — a shape with only `error` and `note` keys (no `violations[]`, no `declared_category`); the note says to scaffold HISTORY.md via skill-creator-ccvw or skill-publisher's backfill. Handle this case separately from a well-formed lint result: create HISTORY.md from the template and re-run. A `declared_category` of `unknown` means HISTORY.md's `author` field exists but is **not a mapping** (e.g. a bare string) — no valid category could be inferred — treat it as a blocking attribution error. (Note: an explicit `category` field with an invalid value like `category: X` does NOT produce `"unknown"` — the lint falls through to shape inference and returns `"D"`. If you see `"D"` but suspect a bad explicit category, check whether HISTORY.md has a malformed `category:` field.) (A wholly *missing* `author` key instead infers category **D** and emits a `missing-primary-author` blocking violation — also fix-before-handoff.) Resolve either case by populating a well-formed `author` block plus an explicit A/B/C/D category, regardless of tier. (A `declared_category` of `"C"` is valid — it means the skill **explicitly set** `category: C` in HISTORY.md frontmatter (idea inspiration); this value is only returned when the field is explicit — the lint cannot infer Category C from shape alone (see-also references in the skill body are not detectable from frontmatter). A skill that omits the `category: C` field will receive `declared_category: "D"` even if it has see-also references. If you are building a Category C skill, ensure `category: C` is set explicitly in HISTORY.md. The lint output will have no blocking violations for a well-formed Category C result.)

Both lints exit **0** when clean. `portability_lint.py` exits **1** when `tier_violations` is non-empty OR `ccvw_mandatory_missing` is non-empty (these are two separate JSON keys — both are part of "ANY non-empty violations list" as the pre-handoff section says; the scaffold-time section names the specific keys for programmatic access; "combined findings list" refers to all four violation families within `tier_violations`). `tier_violations` holds **all four** violation families (structural like `name-format`/`skill-md-misnamed`, frontmatter-content, tier-portability, and personalization), not just tier findings — so a non-empty `tier_violations` triggers exit-1 regardless of which family the violations belong to. `ccvw_mandatory_missing` (a missing README.md/HISTORY.md/etc.) is a separate key that also triggers exit-1 but is NOT inside `tier_violations`. `attribution_lint.py` exits **1** only on a **blocking**-severity violation — an advisory-only finding (e.g. a missing see-also reference) still populates the `violations` array but exits 0, so branch on each entry's `severity`, not on the array being non-empty. Treat `portability_lint`'s findings per the tier rule below; treat any `attribution_lint` blocking violation as fix-before-handoff **regardless of tier** (attribution checks are tier-independent).

(`quick_validate.py`, `portability_lint.py`, and `attribution_lint.py` are this skill's **own independent copies**. skill-publisher carries its own copies of the same three; the two sets are no longer kept in sync and may freely diverge — there is no sync contract. ### Step 3: As runs complete, capture timing data

When each subagent task completes, you receive a notification containing `total_tokens` and `duration_ms`. Save this data immediately to `timing.json` in that run's directory (`<workspace>/iteration-<N>/eval-<descriptive-name>/<config>/run-1/timing.json`). If the harness did not supply `total_tokens` or `duration_ms` (e.g. a failed or killed subagent), write `timing.json` with zeros for the missing fields — write available fields with their actual values and 0 for absent ones (e.g. `{"total_tokens": 84852, "duration_ms": 0, "total_duration_seconds": 0.0}` if only total_tokens was supplied). Note: for `timing.json`, zero values are included as-is in mean calculations — NOT treated as "no timing data." Exception: for `grading.json`'s `total_duration_seconds`, a value of exactly `0.0` triggers fallback to `timing.json` (in `aggregate_benchmark`'s time_seconds-resolution logic); the "zero included" behavior applies only to `timing.json` zeros, not to grading.json zeros. Zero values will pull the mean time_seconds downward. **This "averaged-in" behavior is specific to time_seconds; a zeroed `total_tokens` behaves differently** — because a 0/falsy `total_tokens` triggers the `output_chars` fallback below, it is *replaced*, not averaged as zero. So writing `total_tokens: 0` for a failed run does NOT contribute a zero to the token mean; it yields whatever `output_chars` the run's grading.json holds (or 0 if none). The deliberate failed-run signal therefore lands cleanly in time_seconds (near-zero timing), not in the token column. This is the best available signal for a failed run; the user can visually identify runs with near-zero timing when reviewing benchmark.md. Compute `total_duration_seconds` as `duration_ms / 1000` (executor time only). Note: timing.json is the PRIMARY source of `total_tokens` — `aggregate_benchmark` reads it from timing.json, but when timing.json is absent OR its `total_tokens` is 0/falsy, it falls back to grading.json's `execution_metrics.output_chars` (in `aggregate_benchmark`'s token-value-resolution logic). So a failed run with a zeroed/absent timing.json shows `output_chars` in the token column, not a true token count — read the token column with that fallback in mind. For `time_seconds`, `aggregate_benchmark` uses grading.json timing first (executor+grader combined from the grader subagent) and timing.json as fallback (executor-only) — so the benchmark's time_seconds metric may mix semantics across runs. `aggregate_benchmark` reads `total_duration_seconds`, never `duration_ms`. Any float precision is accepted; the example shows 23.3 for 23332 ms but 23.332 is equally correct:

```json
{
  "total_tokens": 84852,
  "duration_ms": 23332,
  "total_duration_seconds": 23.3
}
```

This is the only opportunity to capture this data. **These two values are external-harness inputs, not anything the skill produces** — the harness (the Claude Code execution environment) surfaces `total_tokens` + `duration_ms` in each subagent's task-completion result (the Agent tool's return value, alongside the subagent's final text). Read them however your harness exposes that result; in current Claude Code they appear as a `usage` object (token counts) plus a `duration_ms` field on the task result, but the exact shape is harness-defined and may vary by version — so the skill does not pin a key path. **The guaranteed rule that makes this deterministic regardless of harness shape:** if you can read the two values, write them; if you cannot locate either one, write 0 for it per the zero-fallback above. The executor therefore always has a defined action and never blocks on a missing/renamed field. The timing.json keys themselves are always the three fixed names (`total_tokens`, `duration_ms`, `total_duration_seconds`) regardless of what the harness calls its source fields. No script produces these fields. They are not persisted elsewhere. Process each notification as it arrives rather than trying to batch them.

### Step 4: Grade, aggregate, and launch the viewer

Once all runs are done (in every command below, `iteration-N` is a **placeholder for the literal current-iteration integer** — substitute the actual number per the rule in the Workspace-location paragraph above; a literal `iteration-N` directory won't exist and `aggregate_benchmark` exits with `Directory not found`):

1. **Grade each run** — spawn a grader subagent when subagents are available (Claude Code / Cowork), or grade inline on runtimes without them (Claude.ai). If the VERY FIRST grader dispatch fails before any grading.json exists, grade all runs for that iteration inline. Each run's grading.json is written independently, so switching modes mid-iteration is acceptable as long as every run's grading.json ends up with the same field contract. Inline grading requires the same `grading.json` field contract — `summary{pass_rate,passed,failed,total}`, `timing{total_duration_seconds}`, per-expectation `text`/`passed`/`evidence` — as the grader subagent produces. `references/runtime-adaptations.md` (its Claude.ai specifics section) restates the same contract and points to schemas.md for the full shape — consult `references/schemas.md` for additional detail. Either way, **read `agents/grader.md` first** (to understand the grader's contract and required inputs; the grader receives the brief content in its dispatch prompt — either inline or as the instruction set passed via the Agent tool), then use its three data inputs: `expectations` (the eval's checks from `evals/evals.json` — that file has a top-level `evals[]` array; for a multi-eval skill, index into it and select the entry whose `id` field (the field name in evals.json) matches the `eval_id` value (the field name in eval_metadata.json) in this run's eval_metadata.json — these are different JSON key names on different objects that hold the same logical integer — then read that entry's `expectations` array; full structure in `references/schemas.md`), `transcript_path` (the `transcript.md` the run wrote to `<config>/run-1/`), and `outputs_dir` (`<config>/run-1/outputs/`). Include these as named fields in the grader's dispatch prompt text, e.g.: `"expectations: [...], transcript_path: /path/to/transcript.md, outputs_dir: /path/to/run-1/outputs/"`. **Before dispatching the grader**, check the outputs saved to `<config>/run-1/outputs/` to identify any non-text formats. If `outputs/` is empty (no files were written), note it in the grader dispatch ("no output files exist") and grade on transcript content only; if the transcript also indicates no substantive output, grade all expectations as failed and note the empty output in the evidence. If `transcript.md` itself is absent (a killed/failed executor subagent — the same failure mode `timing.json` handles with zeros at Step 3), do not dispatch the grader for that run; write a `grading.json` directly with all expectations `passed: false` and evidence "run produced no transcript (executor subagent failed)", so the run still aggregates as a failure rather than blocking the iteration. **For non-text outputs** (PDFs, images, spreadsheets, binary files, Office documents like .docx/.pptx, and any non-plain-text format), the grader dispatch must ALSO hand the grader the inspection tools/instructions it needs to open them — for example, include "use the Read tool to read the file" in the grader's dispatch prompt for files the model can read directly (images, PDFs); for spreadsheets, Office documents, or binary formats, include a conversion command or path to a helper script in the dispatch prompt. "Providing" a tool means including the instruction in the dispatch prompt text — the grader agent has access to the same tools the orchestrator has; the instruction enables the grader to use them. `agents/grader.md` assumes its prompt supplies these and is told not to trust the transcript alone; a grader given only the three data inputs has no way to read a non-text output. Write `grading.json` to the run directory — `<config>/run-1/grading.json`, the sibling of `outputs/` — whether you spawned a subagent or graded inline. (A dispatched grader writes it there itself: per `agents/grader.md` it derives the run directory as the parent of the `outputs_dir` you pass — `{outputs_dir}/../grading.json` — and likewise reads `timing.json` from that same parent. So of the grader's inputs you pass all three data inputs named above (`expectations`, `transcript_path`, `outputs_dir`) in the dispatch prompt, but you do NOT additionally pass the grading.json output path or the timing.json path — those two the grader derives from `outputs_dir` itself.) The grading.json expectations array must use the fields `text`, `passed`, and `evidence` (not `name`/`met`/`details` or other variants) — these three field names are **one contract across all three consumers** (the grader emits them, `aggregate_benchmark` validates them, the viewer renders them), so don't rename them in any one place. (A grader that *succeeds* but writes wrong field names is not caught here at sub-step 1 — it surfaces at sub-step 2, where `aggregate_benchmark` emits `Warning: expectation … missing required fields` and you re-dispatch that run's grader. You do not need a separate field-validation pass at sub-step 1; the aggregate warning is the catch.) For checks that can be verified programmatically, write and run a script rather than eyeballing it — scripts are faster, more reliable, and can be reused across iterations. (`grading.json` is the full per-run record, of which consumers read a subset: the viewer surfaces `summary` + `expectations`; `aggregate_benchmark` reads `summary`/`expectations`/`execution_metrics`/`timing` and folds `user_notes_summary` into each **run's** per-run `notes` field (runs[].notes in benchmark.json — distinct from the top-level benchmark.json["notes"] field which the analyzer fills via the merge step); `claims` stays in the file as a human-facing verification record; `eval_feedback` — the grader's eval-critique — is consumed by the recommendations payload in sub-step 4 of this same Step 4, below.)

2. **Aggregate into benchmark** — run the aggregation script:
   ```bash
   # run from the skill-creator-ccvw directory so the skill root is the cwd
   # (~/.claude/skills/skill-creator-ccvw/ — substitute the real path for python -m commands)
   # (run_loop.py and package_skill.py require -m because they import from scripts.*; aggregate_benchmark.py uses -m for consistency but has no cross-script imports)
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name> --skill-path <path-to-skill> --model <model-id-powering-this-session>
   ```
   Produces `benchmark.json` and `benchmark.md` with pass_rate, time, tokens per configuration (mean ± stddev + delta). Pass `--model` so `metadata.executor_model`/`analyzer_model` carry the real model id (omit it and they stay a `<model-name>` placeholder). To derive the model ID: look for it in the system prompt header, the session info, or the harness environment — in Claude Code it appears as the session model name; use the exact identifier string the API accepts (e.g. `claude-sonnet-4-20250514`); `runs_per_configuration` is computed from the actual run count. The viewer pairs configurations by grouping on each run's `configuration` field, so you do NOT need to hand-order the runs array. **Three gotchas:** (a) `delta` is computed as primary − baseline, where primary/baseline are matched BY NAME against a known vocabulary — `with_skill`/`new_skill` as primary, `without_skill`/`old_skill` as baseline (fixed 2026-08-11; config discovery is still alphabetical via `sorted(eval_dir.iterdir())`, but the delta calculation no longer trusts that order — it looks up the two roles by name instead of by position). Any combination of the four recognized names gives a correctly-signed delta regardless of which one sorts first alphabetically. Only custom config-dir names outside that vocabulary fall back to the old alphabetical-positional behavior, and the script prints a `Warning:` to stderr when it does — if you see that warning, read the per-config means directly rather than trusting the delta sign, or rename your config dirs to the recognized vocabulary and re-run. (b) The script exits 1 if the `<workspace>/iteration-N` directory does not exist (stdout: `Directory not found: …`); fix: substitute the correct path and re-run; for all other paths it exits 0 even on partial data (two exceptions that exit non-zero with a Python traceback: (1) an I/O exception writing `benchmark.json` or `benchmark.md` — check disk space and directory permissions; (2) a `run-*` directory with a non-integer suffix like `run-abc/` or a bare-hyphen suffix `run-` triggers a ValueError in `int(run_dir.name.split('-')[1])` — rename or remove the offending directory (e.g. `mv run-abc/ run-1/` or `rm -rf run-abc/`), then re-run aggregate_benchmark; check that run directory names follow exactly `run-<N>/`; note that `run-1-extra` silently parses as run 1 without crashing (split gives index 1 = "1") so it won't produce a ValueError but will be misidentified — avoid extra hyphens too. Note: `eval-*` directory names use an equivalent int() parse (line 99) but with a `try/except ValueError` that silently catches it and falls back to `eval_idx` — so `eval-chart-formatting/` without an eval_metadata.json is safe; only run-* names are unprotected.) — to distinguish (1) from (2): an OSError/PermissionError traceback mentions a file write or path; a ValueError traceback mentions `int()` from run-directory parsing. It runs in the foreground, so its stdout (the `Warning:` lines, interleaved with the `Generated:`/`Summary:` output) comes back to you directly in the command result; scan it for `Warning:` lines and act on each type distinctly: `Warning: grading.json not found in {run_dir}` → the grader never ran for that run; re-run the grader subagent. `Warning: Invalid JSON in {grading_file}` → the grader produced malformed output; re-run the grader. `Warning: expectation in {grading_file} missing required fields (text, passed, evidence): {exp}` (the actual message includes the malformed expectation dict) → the grader used wrong field names; fix the grader dispatch or the output format and re-run. The correct action: re-dispatch the grader subagent for only the affected run (identified by the file path in the warning message `{grading_file}`); do not manually edit benchmark.json or grading.json. After fixing, re-run aggregate_benchmark. (The malformed entry is **included** in result["expectations"] despite the warning, NOT dropped — the current benchmark.json already contains the malformed expectation; after fixing grading.json and re-running aggregate_benchmark, the new benchmark.json will have the corrected expectation.) (c) If the directory exists but has no `eval-*/` subdirs, the script exits 0 but prints `No eval directories found in … or …/runs` (`…` is shorthand for the actual benchmark_dir path values; grep for the prefix `"No eval directories found"` — the actual output uses real path values, not the `…` shorthand) and emits an **empty** benchmark — that means the wrong dir, or the runs weren't saved; treat it as a setup error, not a valid zero-result — `grep "No eval directories found"` in the command output to confirm this is the condition, then check that the path is correct and runs were saved to `iteration-N/eval-*/` subdirs, and re-run. Manual generation: see `references/schemas.md`.

3. **Do an analyst pass** — read the benchmark data and surface patterns the aggregate stats hide. Spawn the analyzer per `agents/analyzer.md` with its three inputs: `benchmark_data_path` = `<workspace>/iteration-N/benchmark.json` (the path aggregate_benchmark wrote to), `skill_path`, and `output_path` (supplying exactly these three inputs — and only these three; do not include any Mode A inputs like `winner`/`winner_skill_path`/`loser_skill_path`/`comparison_result_path`, which would switch the analyzer to Mode A — selects the analyzer's **Mode B** — the brief checks for positive presence of `benchmark_data_path`/`skill_path`/`output_path` per the **Mode selector:** inline bold paragraph in `agents/analyzer.md`) — use exactly `<workspace>/iteration-N/analyst-notes.json` (the analyzer brief writes to whatever `output_path` you pass, so passing this exact path is what makes the bare-filename merge command later in this same paragraph resolve); it writes a JSON array of observation strings there — non-discriminating assertions (always pass), high-variance evals (flaky), time/token tradeoffs. **Then merge that array into `benchmark.json`'s top-level `notes` field** (which `aggregate_benchmark` leaves empty precisely for this) — the viewer's Benchmark tab renders `benchmark.json`'s `notes`, so observations left only in the analyst's output file never appear. Wait for the analyst subagent to complete before running the merge. Check that `analyst-notes.json` is a **non-empty JSON array** before merging — if the file is valid JSON but not an array (e.g. `{}` from an aborted analyzer), treat it the same as sub-case (a) below and re-dispatch the analyst. An empty `[]` can mean (a) the analyzer aborted early because benchmark.json was absent or malformed, (b) benchmark.json exists but has 0 runs (no eval dirs were found), OR (c) the benchmark has runs but genuinely no interesting patterns. To distinguish: check benchmark.json — if `runs[]` is non-empty, `[]` is a valid zero-observation result (proceed to merge — nothing to add); if `runs[]` is empty or benchmark.json is absent, the runs are missing (see sub-case a or b). If benchmark.json exists but cannot be parsed (JSONDecodeError), you cannot read `runs[]` — treat it the same as absent and re-run aggregate_benchmark. If benchmark.json is valid JSON but has no `runs` key at all, treat it the same as empty-runs case (b). (`aggregate_benchmark` always writes a `runs` key, so this state only arises from external corruption or a manual edit, not from the script's own output — the branch is a defensive guard, not a state the documented write path produces.) For sub-case (a) or (b): if `runs[]` is empty, re-run `aggregate_benchmark` using the same command from sub-step 2 (the "correct inputs" means the identical command — no arguments need to change; this regenerates `benchmark.json` from the run data whether it was absent or was present but malformed by a prior write error — both sub-cases resolve the same way), re-dispatch the analyzer, wait for it to complete, then re-run the merge command before proceeding to sub-step 4. The analyst must have written `analyst-notes.json` to exactly `<workspace>/iteration-N/analyst-notes.json` (the `output_path` you passed in the dispatch above) — the merge command's bare `open('analyst-notes.json')` resolves relative to the `cd` directory (which is set by the `cd <workspace>/iteration-N/ &&` prefix) and **exits non-zero** with a FileNotFoundError traceback (in the Bash tool's return value) if a different output_path was used. The absolute path `<workspace>/iteration-N/analyst-notes.json` and the bare filename `analyst-notes.json` refer to the same file when `cd <workspace>/iteration-N/` succeeds — this is the same implicit equivalence the merge one-liner relies on. If the `cd` itself fails (directory does not exist), the entire Bash call exits non-zero before python3 runs — the error output is a shell error like `no such file or directory`, NOT a Python traceback; if you see a non-zero exit without a Python traceback, the `cd` likely failed. The fix is to verify `<workspace>/iteration-N/` exists — it is NOT created by aggregate_benchmark (the script only reads from it); the executor must create it first with `mkdir -p <workspace>/iteration-N/`, then re-run aggregate_benchmark. To detect merge problems BEFORE they happen, confirm `analyst-notes.json` exists at `<workspace>/iteration-N/analyst-notes.json` before running the merge — if absent, re-dispatch the analyst with the correct `output_path` (the correct value is `<workspace>/iteration-N/analyst-notes.json` as specified in the dispatch instruction above; if re-entering mid-build and workspace/N are unclear, see the **"Workspace location (CCVW fork — read this first)"** paragraph at the top of the "Running and evaluating test cases" section for `<workspace>`; to derive N run `ls -d <workspace>/iteration-*/` and take the highest-numbered iteration that contains a `benchmark.json` — that is the in-progress iteration; a directory without a benchmark.json was just created and has not been aggregated yet) and merge once it returns. If the merge Bash call exits non-zero for any reason (FileNotFoundError from absent file, JSONDecodeError from malformed JSON, or I/O error), the merge has failed — the non-zero exit and Python traceback appear in the Bash tool's return value (stderr text); read it to identify which file caused the error, fix the source file, and retry the merge. (Agent tool calls are blocking from the orchestrator's perspective — control does not return to the orchestrator until the subagent completes. When it returns, the output file is already written.) **On Claude.ai or other runtimes where the analyzer is skipped** (see `references/runtime-adaptations.md`), skip the merge and leave `benchmark.json`'s `notes` field as the empty array `aggregate_benchmark` writes; the viewer renders an empty Notes section, which is acceptable. Do the merge in a **single Bash call** combining `cd` and `python3` with `&&` — the working directory does NOT persist across separate Bash tool calls, so these two commands must be in the same call: `cd <workspace>/iteration-N/ && python3 -c "import json; b=json.load(open('benchmark.json')); b['notes']=json.load(open('analyst-notes.json')); json.dump(b, open('benchmark.json','w'), indent=2)"`

4. **Author the recommendations payload** — write `<workspace>/iteration-N/recommendations.md` per `references/recommendations-template.md` (three sections: did well / failed at / recommended next iteration; bullet counts are minimums — more is better, every observation saves an iteration cycle). Fold in each `grading.json`'s `eval_feedback` (the grader's eval-critique: weak/non-discriminating assertions, outcomes no assertion covers) when present — `eval_feedback` is optional (the grader omits it when it finds no issues), so if absent from a grading.json, skip that run's contribution to eval suggestions. If grading.json itself is absent for a run (the grader never ran), re-run sub-step 1 grading for only that run before proceeding — then fold in its eval_feedback if present. To fold: write recommendations.md first per the template (the three sections — did well, failed at, recommended next), THEN append a `## Eval Quality Recommendations` section for eval_feedback content (the heading contains "recommend" so the viewer renders its bullets in the **"Recommended next iteration"** sidebar bucket — this is expected behavior, not a separate section; note the viewer renders ONLY top-level `- ` bullets under a matched `## ` heading — it ignores `###` subheadings, so do not nest under them); for each grading.json where `eval_feedback` is present, extract its `suggestions[]` (each has `reason` and optionally `assertion` (when the suggestion relates to a specific expectation) — some suggestions about uncovered outcomes have no `assertion` field) and `overall` field and append as flat top-level `- ` bullets, one per suggestion, each prefixed inline with the eval name — `- <eval-name>: <suggestion>` (use `eval_name` from `eval_metadata.json` if available, otherwise the directory basename `eval-<descriptive-name>`). That critique is actionable input for the next iteration's evals, and this payload is its consumer.

   ```bash
   nohup python <skill-creator-ccvw-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     --recommendations <workspace>/iteration-N/recommendations.md \
     > <workspace>/iteration-N/viewer.log 2>&1 &
   echo $! > <workspace>/iteration-N/.viewer.pid   # persist the PID to a file — shell variables do NOT survive across the user-review turn boundary
   ```
   **Server mode (default):** After launching, read `<workspace>/iteration-N/viewer.log`. The server startup prints `  URL:       http://localhost:<port>` (with a two-space indent and `URL:` prefix) — `grep "  URL:" <workspace>/iteration-N/viewer.log` to extract the URL line, then strip the exact prefix `  URL:       ` (two spaces + `URL:` + seven spaces) to give the user the URL — or use `grep -oP 'http://\S+' <workspace>/iteration-N/viewer.log` to extract just the URL directly without counting spaces. If the grep returns nothing — the server is still starting — retry: `sleep 2 && grep "  URL:" <workspace>/iteration-N/viewer.log`; the URL line appears after the server binds to its port (repeat a few times if needed). Common failure outputs to watch for in `viewer.log` (all failure messages go to stderr which the `2>&1` redirect captures into viewer.log; this list covers the most likely cases but is not exhaustive — any Python traceback from an unhandled error also lands there; for any unlisted traceback: read it to identify the error type, diagnose the root cause in generate_review.py or its dependencies, fix and retry). **Exception:** if the `nohup` command itself fails to start Python (Python not on PATH, import error), viewer.log may be empty or missing. To diagnose: re-run the viewer launch command WITHOUT `&` (foreground mode) to see the error directly on your terminal; alternatively, check if Python is on PATH with `which python`/`which python3`. If only `python3` is available, substitute `python3` for `python` in the launch command and re-run. `Error: {workspace} is not a directory` (wrong workspace path — the pattern uses the actual path value, not a literal `<path>`), the bare `No runs found in {workspace}` (runs not saved — no `Error:` prefix on this one; the actual path is substituted for `{workspace}` in the output, not the literal string; grep for the prefix `"No runs found in"`), or a Python traceback — all cause the viewer to exit before starting. For workspace/runs errors: fix the path or verify runs were saved, then re-run. **Note on port handling:** in the normal case where the default port is occupied, the script automatically falls back to an ephemeral port (port 0) — no manual retry needed; the URL line in viewer.log will show the dynamically assigned port. A Python traceback from a port-related OSError only occurs in the extreme case where the OS refuses ALL port bindings; if you see such a traceback, wait for other processes to release ports and retry. The script picks a free port if the default is taken, so don't assume a fixed port. Note: generate_review.py unconditionally attempts to kill any existing process on the default port before binding — if another unrelated process is on that port, it may be terminated. **Static/headless mode (`--static`, used in Cowork):** Run the script without `nohup`/`&` (it exits immediately) and capture stdout:
```bash

  <workspace>/iteration-N \
  --skill-name "my-skill" \

  --recommendations <workspace>/iteration-N/recommendations.md \
  --static <workspace>/iteration-N/review.html)
```
The script prints (to stdout) `\n  Static viewer written to: <path>\n` — note the leading newline before the two spaces in the raw output; `grep` splits on newlines so the grep match line is `  Static viewer written to: <path>` (two leading spaces, no leading newline). Strip `  Static viewer written to: ` (two spaces + label + space) to extract the path — or use `grep -oP '(?<=Static viewer written to: )\S.*' <(grep "Static viewer written to:" <(echo "$output"))`; simpler: `echo "$output" | grep "Static viewer" | sed 's/  Static viewer written to: //'` (this sed depends on a two-space indent that is a bare string literal in generate_review.py's static-mode success print, with no formal API contract; if the indentation changes the sed would fail silently — so **verify the extracted path is non-empty before handing it to the user; if it is empty, fall back to the absolute `--static` path you passed into the command**, which is the same file). Note: the `grep -oP '(?<=Static viewer written to: )\S.*'` pattern uses `\S.*` which stops at the first space — a `--static` path containing a space (valid on macOS/Linux) would be silently truncated; use the `sed`-based form instead to avoid this. **Pass an absolute path for `--static`** (e.g., `<workspace>/iteration-N/review.html`) so the extracted path is directly usable by the user without needing the current working directory. If the command exits 1, check stderr for the failure message (errors always go to stderr in both modes; in server mode they are captured in viewer.log via 2>&1, while in static mode they appear on the shell stderr distinct from the stdout success line): `Error: {workspace} is not a directory` → fix the workspace path and re-run; `No runs found in {workspace}` → verify runs were saved and re-run; any other Python traceback → diagnose and fix the root cause. A non-traceback stderr message that does not match either named pattern indicates an unexpected error — inspect the script for the new error path.) Give the extracted file path to the user to open in their browser. For iteration 2+, also pass `--previous-workspace <workspace>/iteration-<N-1>` where N is the current iteration integer (the same N used in `iteration-N` throughout this section). Headless environments and Cowork-specific viewer behaviour: see `references/runtime-adaptations.md`. Use `generate_review.py` — don't write custom HTML. (Note: `run_loop.py` internally uses a separate `generate_html` from `scripts/generate_report.py` for its live-updating browser progress page — that is a different function from the eval-viewer's `generate_review.py`; the executor does not call either directly.)

### Step 5: Read the feedback

When the user tells you they're done, read `<workspace>/iteration-N/feedback.json` — **server mode only**: the server writes this file to the workspace on POST; in static/Cowork mode the browser downloads feedback.json to the user's Downloads folder rather than POSTing to the server, so `<workspace>/iteration-N/feedback.json` does not exist — see `references/runtime-adaptations.md` "Cowork specifics" section, **Feedback flow.** paragraph for where to read it. (if the file does not exist in server mode — the user may have submitted but a write error occurred — ask them to re-submit; if re-submit is not possible, collect inline feedback: ask what they liked and what they'd change for each eval run, and record their responses as `{"run_id": "…", "feedback": "…"}` entries — these substitute for the missing feedback.json in the next revision step):

```json
{
  "reviews": [
    {"run_id": "eval-chart-formatting-with_skill-run-1", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-1-with_skill-run-1", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-2-with_skill-run-1", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

Empty feedback *on an individual run* (a run's feedback string is empty) means the user thought that run was fine. A completely empty `reviews` array (`{"status": "complete", "reviews": []}`) means the user submitted without reviewing any runs — check whether the viewer displayed the runs correctly — verify the run directories under `<workspace>/iteration-N/eval-*/` exist and contain `run-1/outputs/`; if not, runs were not saved and you need to re-run Step 1. If the runs exist, re-launch the viewer. `"status": "complete"` is set browser-side by `viewer.html` when the user clicks "Submit All Reviews" — in server mode the browser POSTs to the server (the server is a pass-through; it writes whatever the browser POSTs); in static/Cowork mode the browser downloads a feedback.json file directly without any POST (see `references/runtime-adaptations.md`). Either way, the status field is always set browser-side. If `status` is `"in_progress"`, the user either is still reviewing (auto-save fires 800ms after the last keypress — a debounce, not a repeating interval) OR has already submitted and clicked "OK" on the done dialog (the viewer resets status back to `"in_progress"` on dismiss). To distinguish: if the user has told you they're done AND status is `"in_progress"`, treat it as submitted — check the reviews content rather than the status. Proceed as if status were `"complete"`: use the reviews content to author the improvement plan. If `status` is absent (unusual — produced only by a partial POST or manually-written feedback.json), the user hasn't submitted yet (re-ask them). A feedback.json written manually or from a partial POST will not have `status: "complete"` even if reviews are populated. Focus your improvements on the test cases where the user had specific complaints.

Kill the viewer server when you're done with it (**server mode only — skip this step in static/Cowork mode where no server was started and no `.viewer.pid` file was written**). Read the PID back from the `.viewer.pid` file written at launch (a shell variable would not survive the wait for the user's review, which spans separate Bash calls):

```bash
kill "$(cat <workspace>/iteration-N/.viewer.pid)" 2>/dev/null
```

## Improving the skill

The user reviewed the results; now revise the skill based on their feedback.

### How to think about improvements

1. **Generalize from the feedback.** Skills get used across many prompts, not just the test set. A skill that only handles the test examples is useless. If an issue is stubborn, try a different metaphor or working pattern instead of adding overfitty MUSTs.
2. **Keep the prompt lean.** Remove instructions that aren't pulling their weight. Read the transcripts (not just final outputs) — if the skill is making the model waste time, cut the parts causing that.
3. **Explain the why.** Direct imperatives + reasoning beat rote ALWAYS/NEVER. If you find yourself in all-caps or rigid structures, reframe and explain instead — the model has good theory of mind and uses it.
4. **Look for repeated work across test cases.** If multiple subagents independently wrote similar helper scripts, bundle the script in `scripts/` and tell the skill to use it. Saves every future invocation from reinventing the wheel.

Your thinking time isn't the blocker — draft a revision, re-read with fresh eyes, improve.

### The iteration loop

After improving the skill:

**Session-log marker (first action at the start of each iteration):** `echo "**[$(date +%H:%M:%S)] SKILL:skill-creator-ccvw RUN:<skill-name>-iter<N> STEP:iteration-<N>**" >> "${HOME}/.claude/session-logs/session-log-$(date +%Y-%m-%d).md"` — substitute the actual skill name and current iteration number (N = the new iteration being started). Non-blocking.

1. Apply your improvements to the skill
2. Rerun all test cases into a new `iteration-<N+1>/` directory, including baseline runs — **dispatch both with-skill and baseline runs in the same turn** (same-turn requirement — see Step 1). (Baseline choice at iteration 2+ is the inline rule under Step 1 — original `old_skill/` vs previous iteration, default previous.) If you're creating a new skill, always spawn a fresh `without_skill` subagent run for each new iteration unconditionally — don't copy or re-use a prior iteration's baseline directory. The config name stays `without_skill` across all iterations but each iteration needs its own new run to compare against the current iteration's skill version. If you're improving an existing skill, at iteration 2+ follow the inline Step 1 rule: original `old_skill/` vs previous iteration, default previous; no extra judgment needed beyond those two options. The "snapshot + old_skill/" path in Step 1 covers iteration 1 only.
3. Before launching the viewer, run the full Step 4 sub-steps 1–4 for the new iteration: grade all runs (sub-step 1), aggregate (sub-step 2), analyst pass (sub-step 3), recommendations (sub-step 4). ## Advanced: Blind comparison

For situations where you want a more rigorous comparison between two versions of a skill (e.g., the user asks "is the new version actually better?"), there's a blind comparison system. Read `agents/comparator.md` and `agents/analyzer.md` for the details. The basic idea is: give two outputs to an independent agent without telling it which is which, and let it judge quality. When dispatching the comparator, include `output_path` in the dispatch prompt (the path where the comparator should write its JSON result); if omitted, the comparator defaults to `comparison.json` in its working directory — an unknown path the orchestrator cannot retrieve. Then analyze why the winner won. **If the comparator returns `"TIE"` as the winner value** (see `agents/comparator.md`), there is no winner to analyze — skip the Mode A analyzer dispatch in this Blind Comparison (not the Mode B analyst pass in Step 4, which runs independently) and report the tie to the user; the two outputs are considered equivalent for this eval. **If `winner` holds any value outside `{"A", "B", "TIE"}` (a contract violation per comparator.md)**, treat it as a no-result — re-dispatch the comparator once; if it returns another invalid value, skip the analysis and report the issue to the user. When dispatching the analyzer here, supply its **Mode A** inputs (`winner`, `winner_skill_path`, `winner_transcript_path`, `loser_skill_path`, `loser_transcript_path`, `comparison_result_path`, `output_path` — all seven; the two transcript paths are what its Step 3 reads) — distinct from the benchmark analyst pass's Mode-B inputs in Step 4. The analyzer brief selects its mode purely from which inputs you pass: supplying the Mode-A discriminating inputs (`winner`/`winner_skill_path`/`loser_skill_path`/`comparison_result_path` — the four the Mode selector checks) selects Mode A; the three transcript/output inputs (`winner_transcript_path`, `loser_transcript_path`, `output_path`) are also required by analyzer.md Steps 3 and 8 respectively and must be included — without `output_path` the analyzer has nowhere to write its result (Step 8: `Save structured analysis to {output_path}`). The Mode selector fires on those four discriminating inputs (`winner`, `winner_skill_path`, `loser_skill_path`, `comparison_result_path`) to choose the mode, not all seven; but all seven are needed for Mode A to run to completion. This is distinct from Step 4's Mode-B selector which checks for `benchmark_data_path`/`skill_path`/`output_path` (three inputs, not a single `benchmark_data_path`). See the **Mode selector:** inline bold paragraph in `agents/analyzer.md`; the brief checks Mode B FIRST (benchmark_data_path/skill_path/output_path) and Mode A as the else-branch (winner/winner_skill_path/loser_skill_path/comparison_result_path). The two modes are mutually exclusive by design — never pass both input sets simultaneously.

This is optional, requires subagents, and most users won't need it. The human review loop is usually sufficient.

## Description Optimization

The description field in SKILL.md frontmatter is the primary mechanism that determines whether Claude invokes a skill. After creating or improving a skill, offer to optimize the description for better triggering accuracy.

### Step 1: Generate trigger eval queries

Create 16–20 eval queries — a mix of should-trigger (8–10) and should-not-trigger (8–10), totaling in that range. Save as JSON:

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

Queries must be realistic — what a Claude Code or Claude.ai user would actually type. Concrete, specific, with detail (file paths, job context, column names, company names, URLs, a bit of backstory). Mix lengths and casual/formal/typo registers. Focus on edge cases.

Bad: `"Format this data"`, `"Extract text from PDF"`, `"Create a chart"`
Good: `"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

- **should-trigger (8-10)**: vary phrasing (formal/casual), include cases without explicit skill/file names, throw in uncommon use cases and cases where this skill competes with another but should win.
- **should-not-trigger (8-10)**: near-misses are most valuable — same keywords/concepts but actually need something different. Avoid obviously-irrelevant negatives like "write a fibonacci function" for a PDF skill; they don't test anything.

```bash
python3 scripts/validate_eval_set.py <path-to-trigger-eval.json>  # = <workspace>/trigger-opt/eval_set.json
# exit 0 = shape valid (proceed);
# exit 1 = two cases:
#   (i) valid JSON but invalid shape or empty set → parse stdout JSON, read errors[], fix, re-run;
#   (ii) any uncaught OSError from p.read_text() (permission-denied, network filesystem disconnect, etc.) → Python traceback on stderr
#        (stdout is empty; no JSON to parse). Recovery: read the traceback to identify the specific OS error — check file permissions, file accessibility, or network connectivity as appropriate, and re-run.
#        Check the calling shell's stderr for the traceback. (validate_eval_set.py is called directly, not via nohup, so stderr goes to the terminal.)
# exit 2 has two sub-cases:
#   (a) not-found or not-a-file → stderr only (message: "ERROR: not found: <path>"); the check is p.is_file(),
#       so a directory, broken symlink, or missing file all produce this exit. Read the path from stderr.
#       Recovery cases: (i) wrong path → correct the path and re-run; (ii) file not yet generated
#       (user hasn't exported the eval set from the HTML viewer yet) → direct the user to click
#       "Export Eval Set" in the description-optimization viewer (Step 2), then re-run after download;
#       (iii) broken symlink → the symlink target no longer exists; re-export or re-save the eval set file at that path directly;

#   (b) not valid JSON → prints a JSON *object* to stdout: {"valid": false, "errors": ["not valid JSON: <details>"]}
#       Parse the stdout JSON object, read the errors[] array inside it for the specific parse error, then fix the file.
# Branch on the exit code FIRST (0, 1, or 2), THEN on stdout content within that exit code: at exit 0/1, check WHICH case — if stdout has JSON, parse it (cases 0 and 1(i)); if stdout is EMPTY (exit 1(ii) uncaught OSError traceback), skip JSON parsing and check stderr. At exit 2 check whether stdout has JSON (sub-case b) or is empty (sub-case a). Note: exit-1 case (i) also produces stdout JSON with `valid: false`, but the exit code (1 vs 2) distinguishes it from exit-2 case (b) — branch on exit code, not just stdout content. Any exit code outside {0,1,2} is a shell/environment error (127=command not found, etc.) — check that Python is on PATH and the script is accessible. The JSON warnings[] (present on exit 0/1) flags
# class balance outside 8-10/8-10 and unexpected keys — two distinct types with different implications:
# (1) class-balance: ADVISORY; the loop runs fine, proceed unless you want more balance.

To find the timestamped results subdir after the run completes, `grep "Results saved to:" <workspace>/trigger-opt/loop.log` rather than parsing the log by eyeball. That yields exactly three states, distinguished by (traceback?) × (results.json present?): (1) **traceback in loop.log** → crashed mid-run → results.json absent → apply nothing, diagnose. It re-evaluates each new description on both train and test, iterating up to 5 times. It opens a live-updating browser page immediately at start (auto-refreshes as iterations run) and writes the final static report to the same file when done — no second browser open. (This live page is `run_loop.py`'s own progress report via `scripts/generate_report.py`'s `generate_html` — a different artifact from the eval-viewer's `generate_review.py` "viewer" used in Step 4; the executor calls neither directly here — `run_loop.py` does it internally.) ### How skill triggering works

Understanding the triggering mechanism helps design better eval queries. Skills appear in Claude's `available_skills` list with their name + description, and Claude decides whether to consult a skill based on that description. The important thing to know is that Claude only consults skills for tasks it can't easily handle on its own — simple, one-step queries like "read this PDF" may not trigger a skill even if the description matches perfectly, because Claude can handle them directly with basic tools. Complex, multi-step, or specialized queries reliably trigger skills when the description matches.

How the eval harness *measures* a trigger: a run counts as **triggered** when the model's first action is to consult the skill — invoking the `Skill` tool or `Read`ing its `SKILL.md`; anything else scores **not-triggered**. The per-query "trigger rate" (3× per query by default) is the fraction that triggered. So eval queries should be substantive — simple one-step queries won't trigger skills regardless of description quality, so they don't test anything meaningful.

### Triggering signals from real use

The optimization loop above tunes against a synthetic eval set; real use surfaces signals the eval set missed. Watch for both directions and feed them back into the description (re-run the loop with the new real-world queries added):

**Under-triggering** — the skill doesn't load when it should. Signs: the user manually enables it, asks "why didn't the skill fire," or re-phrases to get it to trigger. Remedy: make the description more pushy and specific — add the real phrasings users tried, name the file types/contexts, lean into "use whenever…" — then re-run the Step-3 optimization loop with those phrasings added to the eval set (or, for a one-off, hand-edit the description and re-check with the zero-cost probe below). Under-triggering is the more common failure (Claude under-triggers by default).

**Over-triggering** — the skill loads for unrelated queries. Signs: the user disables it, or it fires on near-miss topics it shouldn't own. Remedies, in order of preference. These three levers address the causes of over-triggering — try them in order. If none resolves it, the issue is the description's domain scope itself, not a missing fourth lever; rethink the scope first:
1. **Negative-trigger clause** — add an explicit exclusion: *"Do NOT use for [X] (use [other-skill] instead)."* The most targeted fix.
2. **Narrow the domain** — replace a broad verb ("processes documents") with the specific one ("processes PDF legal contracts for clause review").
3. **Clarify scope** — state the boundary the skill operates within ("for online payment workflows, not general financial questions").

(`scripts/improve_description.py` may incorporate negative/exclusion clauses when proposing improvements.) **Zero-cost probe.** Ask Claude: *"When would you use the [skill-name] skill?"* — cheap sanity check that the description reads as intended.

**Post-deploy.** When the skill is in real use and you hit a query it mis-handled (fired when it shouldn't, or missed when it should), re-enter this optimization loop with that query added to the eval set. Description tuning is never "done" — real failures are the best eval queries.

### Step 4: Apply the result

**First check `exit_reason`.** The only values `run_loop.py` emits are: `"unknown"` (no iterations ran — loop-launch failure), `"all_passed (iteration N)"` (all queries passed on iteration N — success), and `"max_iterations (N)"` (hit the limit — partial optimization, apply best result). If it's `"unknown"`, this covers TWO distinct cases: (a) a mid-run crash (Python traceback in loop.log) OR (b) a clean no-iteration exit (--max-iterations 0 or empty history — no traceback, results.json IS written with best_description = original_description). In case (a): apply nothing and run diagnostics (check loop.log for the traceback to find the root cause). In case (b): apply nothing (the description was not optimized; --max-iterations 0 is the intentional sub-case, other causes require checking the launch command). In the third state (no traceback + no results.json): apply nothing and re-run. All three unknown sub-cases share the same primary action (apply nothing) — the distinction matters only for diagnostics. Distinguish: (a) has traceback; (b) has no traceback + results.json present; third state has no traceback + no results.json. For `"all_passed (iteration N)"` or `"max_iterations (N)"` (match via startswith: `"all_passed"` or `"max_iterations"`) — the only two non-failure values the script emits — take `best_description` (the three values listed are exhaustive in the current implementation — the list is closed; encountering any other value is a signal that something is wrong: apply nothing, report the unexpected value to the user, and re-run the loop after verifying the eval-set shape and launch arguments are correct (do not attempt to map it to sub-cases (a) or (b) of "unknown" — those sub-cases describe only the three documented normal outcomes).) from the `results.json` the loop wrote — to find the timestamped subdir path, `grep "Results saved to:" <workspace>/trigger-opt/loop.log` (as described in Step 3) — if this returns empty despite a successful exit_reason (e.g. process was killed before that line printed), the subdir still exists under `<workspace>/trigger-opt/`; list it with `ls -t <workspace>/trigger-opt/` and use the most recent timestamped directory. Note: the directory is created by run_loop.py `main()` BEFORE `run_loop()` is called, so even a crash that occurred in the first iteration would leave the directory present without a `results.json` — check that `results.json` exists inside the directory before reading it. Then read `best_description` from that subdir's `results.json` and update the skill's SKILL.md frontmatter. Show the user before/after and report the scores. (Note: `results.json` also contains a `final_description` field — this is the last description the loop tried, not necessarily the best; always use `best_description`, not `final_description`, when applying the result. The fields in `results.json` are: `exit_reason`, `best_description`, `original_description`, `final_description`, `best_score`, `best_train_score`, `best_test_score`, `iterations_run`, `holdout`, `train_size`, `test_size`, `history` — these are not in schemas.md but are stable fields in run_loop.py's return value. Note: `best_test_score` is `null` when no holdout test set was used (`holdout=0` or empty test set) — check for null before displaying to the user.)

If you do, package the skill and present the .skill file to the user:

```bash
# run from the skill-creator-ccvw directory (package module — needs the skill root as cwd)
python -m scripts.package_skill <path/to/skill-folder>
```

After packaging, direct the user to the resulting `.skill` file path so they can install it. The script prints `✅ Successfully packaged skill to: <path>` and exits 0 on success — capture the script's stdout and grep it: `output=$(python -m scripts.package_skill <path>); echo "$output" | grep "✅ Successfully packaged skill to:"` — then strip the prefix `✅ Successfully packaged skill to: ` from the grep result to extract the path: `echo "$output" | grep "✅ Successfully packaged" | sed 's/✅ Successfully packaged skill to: //'`. If stdout is empty and the command exited non-zero (import error or Python not found), check stderr directly: the error would be a Python traceback with no `❌` prefix (the script prints multiple lines before the success line). It defaults to the **current working directory of the process** — per the launch convention above, that is the skill-creator-ccvw directory; pass an `[output-directory]` arg to deposit the .skill file elsewhere). It exits 1 with the following prefixes — these are all current error output forms in the script: `❌ Validation failed: …` (quick_validate failed first — fix the frontmatter and re-run, not retry; note: this error also prints an advisory second line `   Please fix the validation errors before packaging.` without a ❌ prefix — that line is informational only). Other error exits also exit 1: skill folder not found / path not a directory / SKILL.md missing each print `❌ Error: <description>` (the `❌ Error:` prefix); a zip/archive failure prints `❌ Error creating .skill file: <exception>` (different prefix — scan for this too). For path/structure errors (`❌ Error: …`): fix the path or verify the skill directory structure, and re-run. For archive failures (`❌ Error creating .skill file: …`): check disk space, output directory write permissions, and that the output path is not a directory — then re-run.

This packager is a **build-time local-delivery convenience** — it zips the freshly-built skill (any tier) for immediate local install. It is *not* the distribution/release packager. When the user wants to **share or publish** the skill (tier transition, attribution/security/portability gates, version bump, PR), that's `skill-publisher`'s job — suggest running it rather than treating this `.skill` as a release artifact.
