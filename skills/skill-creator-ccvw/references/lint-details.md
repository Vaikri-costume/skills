# Scaffold-time lint checks: details

Moved out of SKILL.md. The three lints, their output shapes and exit codes.

Run exactly these three lints (the complete scaffold-time set — no other scripts from `scripts/` need to be run at scaffold time) the moment the scaffold's files exist (before the first eval). Capture the output of each lint by redirecting stdout. `portability_lint.py` and `attribution_lint.py` emit **JSON** — capture into a shell variable (any name works; `output=$(python3 scripts/portability_lint.py <skill-path>)` uses `output`) then inspect `would_fail_at_tiers`, `tier_violations`, `ccvw_mandatory_missing` programmatically. `quick_validate.py` emits a **plain string** (e.g., `"Skill is valid!"` or `"Name must be kebab-case"`) — do NOT try to parse quick_validate.py's output as JSON; just check its exit code (The correct interpretation: check the exit code as the pass/fail signal; still read and display the stdout message to the user or for diagnostics — the warning is against parsing stdout as JSON, not against reading it at all.) When you apply a tier change (edit `metadata.tier` from one tier to another — writing `metadata.tier` for the first time during initial scaffold is not a tier change; that case is covered by the initial scaffold-time lint run; testable condition: a tier change occurs when SKILL.md already exists on disk with a prior `metadata.tier` value and you are changing it to a different value), immediately re-run `portability_lint.py` as part of that operation — don't wait for the user to separately ask:

```bash
# run from ~/.claude/skills/skill-creator-ccvw/ (the scripts/ directory is relative to this skill's root)
python3 scripts/quick_validate.py   <skill-path>   # frontmatter parse + structural gate
python3 scripts/portability_lint.py <skill-path>   # CCVW structure + tier + name/folder/reserved checks (no --tier flag needed — the script reads metadata.tier from SKILL.md; pass --tier only to test hypothetical tier compatibility)
python3 scripts/attribution_lint.py <skill-path>   # HISTORY.md attribution well-formedness
```

**`portability_lint.py`** checks CCVW-mandatory structure (including README.md + HISTORY.md), tier-portability violations, personalization (cat 15 user-name leakage — anonymize prompt at `claude-users`/`model-agnostic`; cat 16 plan-document leakage — flagged at every tier), AND scaffold-time structural correctness that holds at every tier: the `name` is kebab-case (`name-format`), the `name` matches the skill folder basename (`name-folder-mismatch`), the `name` is not `claude`/`anthropic` or a name starting with one of them followed by `-` or `_` (`reserved-name`), no XML-tag-shaped `<...>` content anywhere in frontmatter (`frontmatter-angle-bracket` — a prompt-injection surface, since frontmatter is injected into the system prompt; version operators like `>=2.0` are fine), the description is ≤1024 chars (`description-too-long`), `compatibility` is 1–500 chars (`compatibility-length`), and the main file is named exactly `SKILL.md` (`skill-md-misnamed` — the diagnostic compares real directory entries, so it catches a `Skill.md`/`skill.md` variant on a case-insensitive filesystem such as the macOS default; on a case-sensitive filesystem a misnamed file gives the SKILL.md-not-found error described below instead). The parenthetical is each rule's `violation type` in `references/skill-structure-spec.md`. Full rule list: `references/skill-structure-spec.md` "Scaffold-time structural rules".

`portability_lint.py` reads one-line frontmatter values (a trailing ` # comment` after a value is ignored, and matching surrounding single or double quotes are stripped); a folded or literal block value is read as one character, so write the `description` on a single line. `quick_validate.py`, `portability_lint.py` and `attribution_lint.py` all read SKILL.md (and `portability_lint.py` and `attribution_lint.py` also HISTORY.md) with a leading byte-order mark dropped and Windows line endings turned into Unix ones, so such a file is read as the eval scripts read it.

**`quick_validate.py`** is the fast frontmatter gate (parses YAML, asserts `name`/`description` present, name kebab-case + ≤64 chars, description ≤1024 chars + no angle brackets at all in the **description field** (stricter than portability_lint's tag-shaped check — even `>=2.0` fails in description, so put any version constraint in `compatibility`, never the description; this rule is description-field-only; `portability_lint` applies a tag-shaped regex (not a bare-character check) to ALL frontmatter fields including description, so `>=2.0` passes portability_lint even in the description — but fails quick_validate), compatibility ≤500 chars, and that only allowed top-level keys appear: name, description, license, allowed-tools, metadata and compatibility, so a Claude frontmatter extension such as disable-model-invocation is rejected at every tier by this gate, even though `portability_lint.py` allows it below model-agnostic). Run it first — a non-zero exit with a validation message means SKILL.md's frontmatter itself is malformed (a Python traceback ending in `ModuleNotFoundError: No module named 'yaml'` instead means the validator cannot run because PyYAML is missing, which says nothing about the frontmatter; `portability_lint.py` and `attribution_lint.py` do not need PyYAML, and `package_skill.py` imports `quick_validate.py`, so it fails the same way). **Fix malformed frontmatter before running the other lints:** `portability_lint.py` would parse an empty dict and produce spurious missing-field findings (noise); `attribution_lint.py` reads HISTORY.md so is unaffected, but it's cleanest to resolve all frontmatter issues first.

**`attribution_lint.py`** verifies that HISTORY.md's `author`, any `author.history[]` and `inspirations[]` entries that are present are well-formed, that a LICENSE file exists when a history chain is present, and that `author.primary` matches the `gh` identity; it does not check that the declared category's fields are present, so confirm those yourself against `references/attribution-spec.md`. An `author.history[]` or `inspirations[]` key left with no value (as `references/history-template.md` ships both for the author to empty) counts as an empty list, not a violation. **If HISTORY.md is missing entirely**, the script exits 1 with `{"error": "HISTORY.md not found at …", "note": "…"}` — a shape with only `error` and `note` keys (no `violations[]`, no `declared_category`); the note says to scaffold HISTORY.md via skill-creator-ccvw or skill-publisher's backfill. Handle this case separately from a well-formed lint result: create HISTORY.md from the template and re-run. `portability_lint.py` likewise exits 1 with only an `error` key (no `tier_violations`, `ccvw_mandatory_missing` or `would_fail_at_tiers`) when SKILL.md is missing; restore SKILL.md and re-run. A `declared_category` of `unknown` means HISTORY.md's `author` field is **not a mapping** (e.g. a bare string) and no valid explicit `category` (A/B/C/D) is set; the blocking `author-not-dict` violation is raised whether or not the category is `unknown`, so treat it as a blocking attribution error. (Note: an explicit `category` field with a value outside A/B/C/D, like `category: X`, is ignored — the lint falls through to shape inference and returns `"A"` when an `author.history` chain exists, `"B"` when only `inspirations` exist, and `"D"` otherwise. Whenever the reported `declared_category` differs from the category the skill claims, check whether HISTORY.md has a malformed `category:` field.) (A wholly *missing* `author` key infers category **B** when `inspirations` is non-empty and **D** otherwise (the same shape inference as above), and emits a `missing-primary-author` blocking violation — also fix-before-handoff.) Resolve either case by populating a well-formed `author` block plus an explicit A/B/C/D category, regardless of tier. (A `declared_category` of `"C"` is valid — it means the skill **explicitly set** `category: C` in HISTORY.md frontmatter (idea inspiration); this value is only returned when the field is explicit — the lint cannot infer Category C from shape alone (see-also references in the skill body are not detectable from frontmatter). A skill that omits the `category: C` field will receive `declared_category: "D"` even if it has see-also references. If you are building a Category C skill, ensure `category: C` is set explicitly in HISTORY.md. The lint output will have no blocking violations for a well-formed Category C result.)

`portability_lint.py` and `attribution_lint.py` exit **0** when clean (`quick_validate.py` is judged by its exit code alone, as described above). `portability_lint.py` exits **1** when `tier_violations` is non-empty OR `ccvw_mandatory_missing` is non-empty (two separate JSON keys; either one non-empty makes it exit 1, at scaffold time and at the SKILL.md "Pre-handoff self-check" re-run alike; which findings block which tier is decided by the tier rule at the end of this file). `tier_violations` holds **all four** violation families (structural like `name-format`/`skill-md-misnamed`, frontmatter-content, tier-portability, and personalization) plus the advisory `tmp-cleanup-advisory` finding (a `/tmp/` path with no cleanup instruction; its `blocks_tier` starts with `none`, so it never adds a tier to `would_fail_at_tiers`), not just tier findings — so a non-empty `tier_violations` triggers exit-1 regardless of which family the violations belong to, and an advisory-only result exits 1 with `would_fail_at_tiers` empty. `ccvw_mandatory_missing` (a missing README.md/HISTORY.md/etc.) is a separate key that also triggers exit-1 but is NOT inside `tier_violations`. `attribution_lint.py` exits **1** only on a **blocking**-severity violation or when HISTORY.md is missing (the error/note case above) — an advisory-only finding (e.g. a missing see-also reference) still populates the `violations` array but exits 0, so branch on each entry's `severity`, not on the array being non-empty. Treat `portability_lint`'s findings per the tier rule below; treat any `attribution_lint` blocking violation as fix-before-handoff **regardless of tier** (attribution checks are tier-independent), except the author-identity case that SKILL.md Step 3 — Author identity names.

(`quick_validate.py`, `portability_lint.py`, and `attribution_lint.py` are this skill's **own independent copies**. skill-publisher carries its own copies of the same three; the two sets are no longer kept in sync and may freely diverge — there is no sync contract. Improve this skill's copies for this skill's needs; do not propagate to the publisher unless you specifically want to.)

At `personal` the lint emits no *tier-conditional* portability findings: its Claude-extension, user-data-path, system-path and compatibility checks run only at `claude-users` and `model-agnostic`, so at `personal` they cannot set exit 1 (pass `--tier` to preview them for another tier); a tier value outside the three valid ones is reported by the advisory `unknown-tier` finding described below. At `claude-users`/`model-agnostic` the orchestrator proposes fixes and confirms before applying. Decide from the JSON `would_fail_at_tiers` array, not the bare exit code (note: the array tells you WHICH tiers are blocked but not WHY — to explain the reason to the user you must also check `ccvw_mandatory_missing` and scan `tier_violations` for `blocks_tier` values): anything in `ccvw_mandatory_missing` (a missing README.md/HISTORY.md/glossary.md or a mandatory frontmatter field) blocks **every** tier including `personal`; so does any `tier_violations` finding whose `blocks_tier` begins with `all` (`would_fail_at_tiers` includes `personal` for these, they are NOT tier-conditional). Examples, not a closed list: the name/folder/reserved/SKILL.md-spelling checks (a malformed name or misnamed file breaks skill discovery on any runtime), `frontmatter-angle-bracket`, `description-too-long`, `compatibility-length`, and the cat-16 plan-code personalization violations. Resolve all of those regardless of tier. One exception to deciding from the array: a finding whose `blocks_tier` is `claude-users (warning)` (a body-level Claude extension, such as the phrase "Agent tool", in a `claude-users` skill's SKILL.md body, the only file the lint scans for these patterns) still adds `claude-users` to `would_fail_at_tiers`, but it is advisory at that tier and does not block it; only `blocks_tier` values without `(warning)` block a tier. `would_fail_at_tiers` is a plain list of tier-name strings with no per-finding entries (`compute_would_fail_at` adds `claude-users` for any `blocks_tier` that contains it, warnings included), so its `claude-users` entry alone does not say whether the tier is blocked. To know, scan `tier_violations` for a finding whose `blocks_tier` begins with `all` or names `claude-users` without `(warning)`, and check `ccvw_mandatory_missing`; if none is there, the array entry comes from warnings only.

A `metadata.tier` value outside personal/claude-users/model-agnostic (a typo such as `claude-user`) gets none of the tier-conditional checks; `portability_lint.py` reports it as an advisory `unknown-tier` finding (never blocks a tier) naming the three valid values, so fix the spelling.
