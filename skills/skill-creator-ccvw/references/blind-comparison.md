# Advanced: blind comparison

Moved out of SKILL.md. Optional; requires subagents.

For situations where you want a more rigorous comparison between two versions of a skill (e.g., the user asks "is the new version actually better?"), there's a blind comparison system. Read `agents/comparator.md` and `agents/analyzer.md` for the details. The basic idea is: give two outputs to an independent agent without telling it which is which, and let it judge quality. The run directories' own paths name the config (`with_skill/`, `old_skill/`, ...), so do not pass them as the comparator's two output-path inputs: copy each output directory to a neutral scratch path whose name carries no config or skill name, assign the two to A and B in an order you pick at random, and keep the A/B-to-config mapping yourself to read the result (the comparator brief forbids it to infer which skill produced which output, `agents/comparator.md` Guidelines "Stay blind"). The comparator and the Mode A analyzer have no template in `scripts/render_prompt.py`, so write each dispatch by hand and give it what the SKILL.md "Hard rules" rule that begins "Dispatch every eval helper" requires of every prompt: the framing line, the helper model, and no names. When dispatching the comparator, include `output_path` in the dispatch prompt (the path where the comparator should write its JSON result); if omitted, the comparator defaults to `comparison.json` in its working directory — an unknown path the orchestrator cannot retrieve. Then analyze why the winner won. **If the comparator returns `"TIE"` as the winner value** (see `agents/comparator.md`), there is no winner to analyze — skip the Mode A analyzer dispatch in this Blind Comparison (not the Mode B analyst pass in `references/eval-run-procedure.md` Step 4 (Grade, aggregate, and launch the viewer), which runs independently) and report the tie to the user; the two outputs are considered equivalent for this eval. **If `winner` holds any value outside `{"A", "B", "TIE"}` (a contract violation per comparator.md)**, treat it as a no-result — re-dispatch the comparator once; if it returns another invalid value, skip the analysis and report the issue to the user. When dispatching the analyzer here, supply its **Mode A** inputs (`winner`, `winner_skill_path`, `winner_transcript_path`, `loser_skill_path`, `loser_transcript_path`, `comparison_result_path`, `output_path` — all seven; the two transcript paths are what its Step 3 reads) and none of the benchmark analyst pass's Mode B inputs (`references/eval-run-procedure.md` Step 4 (Grade, aggregate, and launch the viewer)). Which paths those are: in improve mode the old side is the snapshot (`<workspace>/skill-snapshot/`) and the new side the live skill path; in create mode the without-skill side has no SKILL.md, so give the without-skill run's outputs and transcript only and pass no skill path for that side (`agents/analyzer.md` Step 2 says how a missing skill path is read). All seven are needed for Mode A to run to completion: the two transcript paths are read in its Step 3, and without `output_path` it has nowhere to write its result (Step 8). The analyzer picks its mode itself, by the **Mode router** note at the top of `agents/analyzer.md`, which is the one place that rule is stated (it keys on `winner` for Mode A and `benchmark_data_path` for Mode B, takes Mode B when both are present, and stops and reports when neither is).

This is optional, requires subagents, and most users won't need it. The human review loop is usually sufficient.
