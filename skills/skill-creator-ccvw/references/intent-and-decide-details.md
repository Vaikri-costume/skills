# Capture Intent and Decide: long-form notes

Moved out of SKILL.md. Each section below is the full text of a rule SKILL.md states in one line.

## Q1: mark the deterministic steps for scripting

   **Then walk the ordered steps and mark the DETERMINISTIC ones for scripting.** As you enumerate each use case's steps, flag every step that is mechanical — same inputs always produce the same correct output (e.g. parsing, counting, formatting, validating, regex, date/string munging, JSON shaping, writing a structured row/file, enumerating files with an exclude list — the list is illustrative; the test is the criterion just stated, not membership in it). Those are candidates to **ship as a bundled `scripts/` helper with a stated input→output contract**, NOT prose the executor re-derives (and re-derives slightly differently) every run — "code is deterministic; language interpretation isn't." Leave genuine *judgment* steps as prose (examples — not an exhaustive list: is this a real bug? does this fix preserve intent? which category applies?). The deterministic test above is the decider: a step is scripted iff it meets the same-input→same-output criterion; any step that does not (whether or not it resembles the judgment examples) stays prose. Record the marked steps as a checklist (e.g., inline in the session as "deterministic steps: [step1, step2, …]") that you consult at "Write the three root files" — hold it using a visible note in your response (the primary mechanism for all captured values in this workflow) or `productivity:memory-management` if available — so the deterministic ones land in `scripts/` in the FIRST draft. (This is the design-time complement to the reactive "bundle repeated work" rule under "Improving the skill" — catch it at design, not after N eval runs each re-improvised it. Category-2 Workflow-Automation skills hide the most such steps — see `references/build-planning.md`.)

## Q5: preferences and domain expertise

5. **What standing PREFERENCES should this skill always honor, and what DOMAIN EXPERTISE should it embed?** A skill's whole value is teaching Claude something once instead of re-explaining it every conversation — and "something" is exactly three things, not one: the *process* (the steps, captured in Q1), the user's *preferences* (formatting, tone, conventions, tools to prefer or avoid — the things the user keeps correcting Claude on), and *domain expertise* (the gotchas, rules-of-thumb, and hard-won knowledge a non-expert wouldn't know). Ask for all three. Preferences and short rules go into the SKILL.md body; substantial domain knowledge goes into a `references/<domain>.md` file the skill loads as needed. (A useful threshold: if the domain knowledge is more than ~10 rules or multi-sentence explanations, or forms a reference section the executor would load selectively rather than always, extract it to a reference file; a few short bullet points that always apply can stay inline.) A skill that captures only the steps, omitting preferences and domain knowledge, silently fails the "teach once" promise.

## How intent answers feed README.md and frontmatter

**Intent answers feed README.md + frontmatter.** Q1 → `## What this skill does` (use-case quadruples as bullets) + `## How to invoke` (use the Q1 trigger phrase as the natural-language trigger; use the end-result as the purpose description; construct the worked example from trigger → first ordered step → end result). Q2 → `## How to invoke` trigger phrases. Q3 (expected output format) → the skill's stated output contract in the SKILL.md body (not a distinct README section). Q4 → `## Intent`. Q1 triggers and Q4 trade-offs → `## When to use / When NOT to use` (the "Use when" bullets come from the Q1 use-case triggers; the "Don't use when" bullets come from what Q4 says the skill trades away or leaves out and from any near-miss alternatives the marketplace check surfaced, each pointing at the better tool). Q5 → SKILL.md body + `references/<domain>.md`. Q6 → decision on whether to set up `evals/evals.json` (not a README section). Q7 → `metadata.tier`/`intended-audience` (not a README section). (`allowed-tools` frontmatter comes from the Interview "Which tools are needed" scoping question below, not from a Capture-Intent Q.) The README is mandatory (`references/readme-template.md`).

## Decide Step 1: marketplace check

**Step 1 — Marketplace check** (mandatory before every new build). Invoke `marketplace-discover` as a Skill tool, passing the captured intent + research as its argument substitution (a prose string — at minimum name the target domain, the key action verbs from Q1 triggers, any tool/integration constraints from the Interview "Which tools are needed" answer, and the primary end-result; these are minimums, not a rigid template — write naturally. When Q1 answers are in the structured quadruple form {name, trigger, ordered steps, end result}, combine name + trigger + end result into natural-language prose; add domain constraints from Q5.). If the user says they already ran the check, do not invoke `marketplace-discover`: take the outcome they report as this step's result and route by it (the user's words, such as "no suitable existing skill, build a new one", pick the path); the timestamp rule for this case is under "Marketplace timestamp capture". If `marketplace-discover` is unavailable (the skill is not installed) or returns an error, skip to Step 2 (Attribution category) and proceed on Path 4 — no check ran, so capture no marketplace timestamp and write no `checked-marketplace:` line. If it returns zero results, the check ran: proceed to Step 2. The check reads the live marketplace catalog and presents ranked recommendations.

- If a top recommendation is a strong match (a skill whose documented capabilities and trigger phrases closely align with the user's stated use case — one the user would likely adopt as-is or with minor configuration) and the user chooses to install it, run the install via `marketplace-discover`'s direct-install step and exit. **You took Path 1; you're done here.** If the user declines to install or evolve a strong match, proceed to Path 3 when they want to take part of it, otherwise to Path 4 directly. If the user neither accepts nor explicitly declines (e.g. asks a follow-up question or defers), answer the follow-up and then re-present the choice — wait for an explicit accept or decline before routing to a path.
- If the user wants to evolve an existing installed skill that matches the need, switch to `references/improve-existing-skill.md` (start at Step 1. Pre-edit cold trace of that file). **You took Path 2; that reference takes over the workflow** and runs to its own completion (it ends with its own trace/ship handoff) — control does not return to the "Decide" step, except for the attribution-category question (SKILL.md "Step 2 — Attribution category") when the installed skill has no HISTORY.md, which `references/improve-existing-skill.md` Step 4 (Version and lineage rules) handles. Path 2 also runs the comparison of SKILL.md's "Running and evaluating test cases" section (the eval viewer, grader and aggregator steps are shared infrastructure, not Path-4-only), with the `old_skill` baseline read from the snapshot (`references/eval-run-procedure.md` Step 1 (Spawn each test case's runs)), so every improve run measures the edited skill against the old version.
- If the user wants to take part of someone else's skill or pattern (from `marketplace-discover`'s adapt answer, or named by the user), you are on Path 3: follow SKILL.md "Path 3, adapt", which holds its steps.
- Otherwise proceed to Step 2. **You're on Path 4.** (This covers all non-strong-match cases — weak matches, no results, or error from the marketplace check. The user-confirmation requirement differs by which sub-case you are in: a **declined strong match** needs NO further confirmation (the user already decided) — proceed to Path 4 directly; a **weak match** DOES need a confirm — name the near-misses to the user in one line ("I found some related skills but none are a strong match: [names]; shall I build a new one?") and wait for their go-ahead before building new; **no results / error** needs no confirm — proceed silently. So the discriminator is the marketplace result you actually got, and only the weak-match sub-case pauses for a confirm.)


## Marketplace timestamp capture

**Capture** the marketplace-check timestamp now (only when the check ran, including zero results; not when `marketplace-discover` was unavailable or returned an error). When the user reports an earlier check, the timestamp is the one the user states, written as `checked-marketplace: <their timestamp> (reported by the user)`; if they state none, write `checked-marketplace: (reported by the user, time not given)`; **write it to HISTORY.md** when that file is scaffolded at "### Write the three root files" below (same capture-now/write-later pattern as Q1 use-cases and Step 3 author identity — HISTORY.md does not exist yet). Hold the value as a visible response line (e.g. "marketplace timestamp: 2026-05-31T11:27") — the value spans a context boundary; use `productivity:memory-management` as a supplement for extended sessions. **To retrieve**: scan your prior responses for the label. If prior responses are unavailable (compaction / new session) and `productivity:memory-management` is also unavailable, ask the user to re-provide the timestamp before writing HISTORY.md. **When re-entering a build where HISTORY.md already exists**: skip if it already has a `checked-marketplace:` line. The value goes as a `checked-marketplace: <Runtime>` line in the Lineage notes so re-triggers don't re-ask. Format: a plain text key-value line (e.g., `checked-marketplace: 2026-05-31T11:27`) placed as the first line directly under the `## Lineage notes` heading — its own line, above the free-form prose, separated from the prose by a blank line — in the HISTORY.md markdown body (not YAML frontmatter). The Lineage notes section is the `## Lineage notes` freeform prose section defined in `references/history-template.md` — it is part of the HISTORY.md body, after the YAML frontmatter block. (`<Runtime>` = ISO-8601 UTC now, format `YYYY-MM-DDTHH:MM` — e.g. `2026-05-31T11:27`.) The value is **free-form** — write it bare and unquoted; no script parses it (the only consumer is the human-readable re-entry check "does a `checked-marketplace:` line already exist," a substring read), so the exact form is not load-bearing beyond starting the line with `checked-marketplace:`. (It's build-process provenance, not a runtime-contract field — it lives in HISTORY.md, not SKILL.md frontmatter.)
