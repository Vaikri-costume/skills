# Description optimization: full procedure

Moved out of SKILL.md. Run after creating or improving a skill, when the user wants better triggering.

The description field in SKILL.md frontmatter is the primary mechanism that determines whether Claude invokes a skill. After creating or improving a skill, offer to optimize the description for better triggering accuracy.

### Step 1: Generate trigger eval queries

Create 16–20 eval queries — a mix of should-trigger (8–10) and should-not-trigger (8–10), totaling in that range. Save them as JSON; this file is the trigger-eval set:

```json
[
  {"query": "the user prompt", "should_trigger": true},
  {"query": "another prompt", "should_trigger": false}
]
```

Each query text must be unique: `run_eval.py` scores results by query text, so two items with the same query become one result scored against only one item's `should_trigger`, and `scripts/validate_eval_set.py` rejects the set.

Queries must be realistic — what a Claude Code or Claude.ai user would actually type. Concrete, specific, with detail (file paths, job context, column names, company names, URLs, a bit of backstory). Mix lengths and casual/formal/typo registers. Focus on edge cases.

Bad: `"Format this data"`, `"Extract text from PDF"`, `"Create a chart"`
Good: `"ok so my boss just sent me this xlsx file (its in my downloads, called something like 'Q4 sales final FINAL v2.xlsx') and she wants me to add a column that shows the profit margin as a percentage. The revenue is in column C and costs are in column D i think"`

- **should-trigger (8-10)**: vary phrasing (formal/casual), include cases without explicit skill/file names, throw in uncommon use cases and cases where this skill competes with another but should win.
- **should-not-trigger (8-10)**: near-misses are most valuable — same keywords/concepts but actually need something different. Avoid obviously-irrelevant negatives like "write a fibonacci function" for a PDF skill; they don't test anything.

### Step 2: Review with user

Present the eval set to the user for review using the HTML template:

1. Read the template from `<skill-creator-ccvw-path>/assets/eval_review.html` (where `<skill-creator-ccvw-path>` = `~/.claude/skills/skill-creator-ccvw`) using the `Read` tool
2. Replace the three placeholders in the string (use the `Read` tool result as a string, substitute the values, then `Write` the modified content to a temp path — use `<scratch_dir>/eval_review_<skill-name>.html` as the temp path, where `<scratch_dir>` is `python3 scripts/skill_config.py get scratch_dir` or, if empty, a fresh `mktemp -d` directory):
   - `__EVAL_DATA_PLACEHOLDER__` → the JSON array of eval items (no quotes around it — it's a JS variable assignment), with every < character in it written as the six characters backslash, u, 0, 0, 3, c in a row with no spaces (the JSON unicode escape for the less-than character; the viewer builder does the same), because the array sits inside a script block and a query containing a closing script tag would otherwise end it (JSON reads that sequence back as the less-than character)
   - `__SKILL_NAME_PLACEHOLDER__` → the skill's name
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → the skill's current description
3. Write to a temp file (e.g., `<scratch_dir>/eval_review_<skill-name>.html`) and open it: `open <scratch_dir>/eval_review_<skill-name>.html` (macOS) or `xdg-open <scratch_dir>/eval_review_<skill-name>.html` (Linux). To detect the OS: run `uname` — `Darwin` = macOS, otherwise attempt xdg-open. If xdg-open exits non-zero or no browser opens (e.g. WSL without a display manager), use the fallback: tell the user the file path and ask them to open it in their browser.
4. The user can edit queries, toggle should-trigger, add/remove entries, then click "Export Eval Set"
5. The file downloads to `~/Downloads/eval_set.json` — always run `ls -t ~/Downloads/eval_set*.json | head -1` to identify the file to use (on bash/zsh the shell expands `~` to an absolute path before passing the glob to ls, so the output is a full absolute path, usable directly as an argument to subsequent commands; if only one file matches, `ls -t` returns it directly; if multiple exist from repeated downloads, it returns the newest by mtime)
6. Once the download is confirmed, remove the temp review file (nothing else cleans it up, so it would otherwise persist across every skill-creation run): `rm -f <scratch_dir>/eval_review_<skill-name>.html`. When `<scratch_dir>` is the fresh `mktemp -d` directory this step created (no scratch_dir configured), also remove that now empty directory: `rmdir <scratch_dir>`. A configured scratch directory is left in place. In both commands `<scratch_dir>` is the literal absolute path with the placeholder already filled in, never a shell variable (the SKILL.md "Hard rules" rule that begins "Eval and scratch files go only").

This step matters — bad eval queries lead to bad descriptions.

### Step 3: Run the optimization loop

Tell the user: "This will take some time — I'll run the optimization loop in the background and check on it periodically."

Copy the eval set identified in Step 2 (the `~/Downloads/eval_set*.json` you located with `ls -t`) into the workspace as `<workspace>/trigger-opt/eval_set.json` (create the `trigger-opt/` dir with `mkdir -p` first, then `cp "$(ls -t ~/Downloads/eval_set*.json | head -1)" <workspace>/trigger-opt/eval_set.json`), then **validate its shape before launching the loop** — a malformed eval set otherwise crashes `run_loop` mid-run, after the background job has started and you've spent time reviewing:

```bash
python3 scripts/validate_eval_set.py <path-to-trigger-eval.json>  # = <workspace>/trigger-opt/eval_set.json
# exit 0 = shape valid (proceed);
# exit 1 = two cases:
#   (i) valid JSON but invalid shape, a duplicate query, or empty set → parse stdout JSON, read errors[], fix, re-run;
#   (ii) any uncaught OSError from p.read_text() (permission-denied, network filesystem disconnect, etc.) → Python traceback on stderr
#        (stdout is empty; no JSON to parse). Recovery: read the traceback to identify the specific OS error — check file permissions, file accessibility, or network connectivity as appropriate, and re-run.
#        Check the calling shell's stderr for the traceback. (validate_eval_set.py is called directly, not via nohup, so stderr goes to the terminal.)
# exit 2 has two sub-cases:
#   (a) not-found or not-a-file → stderr only (message: "ERROR: not found: <path>"); the check is p.is_file(),
#       so a directory, broken symlink, or missing file all produce this exit. Read the path from stderr.
#       Recovery cases: (i) wrong path → correct the path and re-run; (ii) file not yet generated
#       (user hasn't exported the eval set from the HTML viewer yet) → direct the user to click
#       "Export Eval Set" in the description-optimization viewer (Step 2), then re-run after download;
#       (iii) broken symlink → the symlink target no longer exists; re-export or re-save the eval set file at that path directly;
#       (iv) any other falsy-path condition not covered above → use `file <path>` to inspect the path type and fix accordingly.
#       Note: a permission-denied file exits 1 (see exit-1 case (ii) above), not exit-2.
#   (b) not valid JSON → prints a JSON *object* to stdout: {"valid": false, "errors": ["not valid JSON: <details>"]}
#       Parse the stdout JSON object, read the errors[] array inside it for the specific parse error, then fix the file.
# Branch on the exit code FIRST (0, 1, or 2), THEN on stdout content within that exit code: at exit 0/1, check WHICH case — if stdout has JSON, parse it (cases 0 and 1(i)); if stdout is EMPTY (exit 1(ii) uncaught OSError traceback), skip JSON parsing and check stderr. At exit 2 check whether stdout has JSON (sub-case b) or is empty (sub-case a). Note: exit-1 case (i) also produces stdout JSON with `valid: false`, but the exit code (1 vs 2) distinguishes it from exit-2 case (b) — branch on exit code, not just stdout content. Any exit code outside {0,1,2} is a shell/environment error (127=command not found, etc.) — check that Python is on PATH and the script is accessible. The JSON warnings[] (present on exit 0/1) flags
# class balance outside 8-10/8-10 and unexpected keys — two distinct types with different implications:
# (1) class-balance: ADVISORY for ratios, proceed unless you want more balance. One exception: each class needs at least two queries,
#     because run_loop puts at least one query of each class in the held-out test set; a class with one query leaves no train query,
#     so the loop ends as all_passed without testing any, and that result means nothing. Add queries to that class first.
# (2) unexpected-key: indicates extra fields on eval items; the keys are ignored by run_loop but may
#     signal a schema mismatch worth investigating before trusting the eval results.
```

Then run the loop in the background:

```bash
# run from the skill-creator-ccvw directory (package module — needs the skill root as cwd);
# background it + redirect to a log so you can tail progress while it runs
nohup python -m scripts.run_loop \
  --eval-set <path-to-trigger-eval.json> \
  --skill-path <path-to-skill> \
  --model <model-id-powering-this-session> \
  --max-iterations 5 \
  --results-dir <workspace>/trigger-opt \
  --verbose \
  > <workspace>/trigger-opt/loop.log 2>&1 &
```

Use the model ID from your system prompt (the one powering the current session) so the triggering test matches what the user actually experiences. This is the one model choice the SKILL.md "Hard rules" rule that begins "Dispatch every eval helper" does not govern: that rule covers dispatched helper agents, while `--model` drives the `claude -p` subprocess calls of `run_eval.py` and `improve_description.py`, whose result is only meaningful on the model that will actually decide whether the skill triggers. The trigger score is only clean when the skill being tuned is not also installed under the same name with another description, or when the installed copy is the one being tuned: `run_eval.py` isolates only the project directory, so an installed copy stays visible to `claude -p`, and a consult of it counts as a trigger of the candidate description because a trigger is any `Skill` or `Read` call naming the skill ("How skill triggering works" below). For the same reason no trigger query should name a file or folder whose name contains the skill's name: `run_eval.py` matches that name as a plain substring of a `Read` path, so reading report.pdf scores as a trigger of a skill named pdf.

While it runs, periodically (every 30–60 seconds) `tail -n 20 <workspace>/trigger-opt/loop.log` to give the user updates on which iteration it's on and what the scores look like. Stop tailing when you see "Results saved to:" or a Python traceback in the log, or when the process exits. Note: `loop.log` receives both stdout and stderr (via `2>&1`), so it contains mixed content — per-iteration progress lines, the final `Results saved to: <subdir>` line (stderr), and the full JSON result blob (stdout) at the very end. To find the timestamped results subdir after the run completes, `grep "Results saved to:" <workspace>/trigger-opt/loop.log` rather than parsing the log by eyeball. If the tail shows a Python traceback or the process exits non-zero (instead of the per-iteration progress lines), the loop died — most often an eval-set shape error that slipped past `validate_eval_set` (which checks shape only, not the deeper failure modes). (A `claude -p` auth/model failure in the improvement step does not raise a traceback: the loop catches it, prints `Error during description improvement` to `loop.log`, and exits with an `exit_reason` beginning `improve_description crashed` — see Step 4 "Apply the result".) Stop and apply no `best_description`, except in state (4) below. The single rule for whether `results.json` exists: it is written only after `run_loop()` returns and its post-return write step completes. That yields exactly four states, distinguished by (traceback?) × (results.json present?): (1) **traceback in loop.log** + results.json absent → crashed mid-run → apply nothing, diagnose. (2) **no traceback + results.json present** → clean return (includes the degenerate `--max-iterations 0` case, where results.json holds best_description = original_description, and the caught improvement-step failure) → read it and check exit_reason. (3) **no traceback + results.json absent** → the process exited before the write, in one of two ways told apart by whether loop.log holds an `Error:` line: a pre-run exit (`Error: 'claude' CLI not found on PATH`, `Error: Pre-flight check timed out`, `Error: Pre-flight credential check failed` or `Error: No SKILL.md found at`, printed before any iteration line and before the results directory is created), or, with no `Error:` line, a process killed after `run_loop()` returned but before the write completed → apply nothing; for an `Error:` line, fix what that message names and then re-run with the same arguments; with no `Error:` line, re-run with the same arguments. (4) traceback in loop.log + results.json present → the loop finished and `results.json` was written, and then writing the final HTML report failed (the traceback names the report write, and no `Results saved to:` line follows it) → the results are valid: read `results.json` in the newest timestamped subdirectory under `<workspace>/trigger-opt/`, check exit_reason as in (2), and tell the user the final report was not written. So "did the loop write results.json" is never ambiguous: branch on the traceback-and-presence pair above. To surface the error to the user, `tail <workspace>/trigger-opt/loop.log` and find the error that is mixed into the log: common root causes include `claude -p` auth/model failure, eval-set shape errors, `"Error: No SKILL.md found at {skill_path}"` (wrong --skill-path — this exits non-zero WITHOUT a Python traceback; the actual path is substituted for `{skill_path}` in the output; grep for the prefix `"Error: No SKILL.md found at"` not the full literal string, printing the error string directly to stderr which the nohup redirect captures in loop.log; if you see this string at the top of loop.log with no iteration lines, correct the --skill-path and re-run), and malformed SKILL.md frontmatter (ValueError from scripts/utils.py `parse_skill_md()` — check SKILL.md for missing `---` delimiters). If the loop produced `exit_reason: "unknown"` cleanly (e.g., --max-iterations 0), there is no traceback — check the arguments and re-run with the correct values.

This handles the full optimization loop automatically. It splits the eval set into 60% train and 40% held-out test, evaluates the current description (running each query 3 times to get a reliable trigger rate), then calls Claude to propose improvements based on what failed. It re-evaluates each new description on both train and test, for up to 5 iterations (5 evaluations and at most 4 description rewrites, because the last iteration evaluates and stops). It opens a live-updating browser page immediately at start (auto-refreshes as iterations run) and writes the final static report to the same file when done — no second browser open. With `--results-dir` (as in the launch above) that file is report.html in the timestamped results subdirectory, not a file in the system temp directory. It returns JSON with `best_description` — selected by test score rather than train score to avoid overfitting. The loop **always prints the full JSON output to stdout** (unconditionally). Because the documented launch uses `nohup … > loop.log 2>&1`, stdout is redirected into `loop.log` alongside stderr — the JSON blob appears at the very end of loop.log. Because `--results-dir` is passed in the launch command above, it additionally persists `results.json` (containing `best_description`, `exit_reason`, and per-iteration scores) + logs to a **timestamped subdir** under `<workspace>/trigger-opt/` and prints `Results saved to: <that subdir>` to stderr — when `--results-dir` was passed, read `best_description` from that `results.json` (preferred — avoids parsing the log blob); **if you invoke run_loop.py without `--results-dir`**, read `best_description` from stdout JSON directly — but this only applies to non-background invocations where you can capture stdout; for the documented nohup launch, always use `results.json` (no file is written without `--results-dir`; if the stdout content was not captured, re-run with `--results-dir`) — and apply the same `exit_reason` guard: check exit_reason in the JSON first; if `"unknown"`, treat it as a loop-launch failure and apply nothing. The only valid exit_reason values are `"unknown"`, `"all_passed (iteration N)"`, `"max_iterations (N)"`, and `"improve_description crashed on iteration N: <error>"` — these four are the only values run_loop.py emits; any other value is a signal something is wrong (see Step 4 "Apply the result" for full handling). If the loop returns without completing an iteration (`--max-iterations 0`), `exit_reason` will be `"unknown"` and `best_description` will be the initial starting description — treat that as a loop-launch failure, not a real optimization result. (An early failure, a traceback before the results write or a pre-run `Error:` exit, writes no results.json at all.) Note: if the eval-set JSON is malformed (failed to pass validate_eval_set or was modified after validation), run_loop.py crashes immediately at load before any iteration progress lines — you'll see only a single JSONDecodeError traceback at the top of loop.log with no iteration lines; fix the eval-set JSON and re-validate before re-launching. If instead you see an OSError traceback (e.g. FileNotFoundError, PermissionError), the eval-set file is missing or inaccessible at the path passed to `--eval-set` — verify the file exists and is readable, then re-launch.

### How skill triggering works

Understanding the triggering mechanism helps design better eval queries. Skills appear in Claude's `available_skills` list with their name + description, and Claude decides whether to consult a skill based on that description. The important thing to know is that Claude only consults skills for tasks it can't easily handle on its own — simple, one-step queries like "read this PDF" may not trigger a skill even if the description matches perfectly, because Claude can handle them directly with basic tools. Complex, multi-step, or specialized queries reliably trigger skills when the description matches.

How the eval harness *measures* a trigger: a run counts as **triggered** when the model consults the skill at any point within the per-run time limit (`--timeout`, default 30 seconds, which the launch command in Step 3 above does not override) — invoking the `Skill` tool, or `Read`ing a path, with the skill's name in it (other tools such as Bash or AskUserQuestion do not end the scan); a run that ends, or reaches the time limit, without such a consult scores **not-triggered**. The per-query "trigger rate" (3× per query by default) is the fraction that triggered. So eval queries should be substantive — simple one-step queries won't trigger skills regardless of description quality, so they don't test anything meaningful.

### Triggering signals from real use

The optimization loop above tunes against a synthetic eval set; real use surfaces signals the eval set missed. Watch for both directions and feed them back into the description (re-run the loop with the new real-world queries added):

**Under-triggering** — the skill doesn't load when it should. Signs: the user manually enables it, asks "why didn't the skill fire," or re-phrases to get it to trigger. Remedy: make the description more pushy and specific — add the real phrasings users tried, name the file types/contexts, lean into "use whenever…" — then re-run the optimization loop ("Step 3: Run the optimization loop" under "Description Optimization") with those phrasings added to the eval set (or, for a one-off, hand-edit the description and re-check with the zero-cost probe below). Under-triggering is the more common failure (Claude under-triggers by default).

**Over-triggering** — the skill loads for unrelated queries. Signs: the user disables it, or it fires on near-miss topics it shouldn't own. Remedies, in order of preference. These three levers address the causes of over-triggering — try them in order. If none resolves it, the issue is the description's domain scope itself, not a missing fourth lever; rethink the scope first:
1. **Negative-trigger clause** — add an explicit exclusion: *"Do NOT use for [X] (use [other-skill] instead)."* The most targeted fix.
2. **Narrow the domain** — replace a broad verb ("processes documents") with the specific one ("processes PDF legal contracts for clause review").
3. **Clarify scope** — state the boundary the skill operates within ("for online payment workflows, not general financial questions").

(`scripts/improve_description.py` may incorporate negative/exclusion clauses when proposing improvements.) **Zero-cost probe.** Ask Claude: *"When would you use the [skill-name] skill?"* — cheap sanity check that the description reads as intended.

**Post-deploy.** When the skill is in real use and you hit a query it mis-handled (fired when it shouldn't, or missed when it should), re-enter this optimization loop with that query added to the eval set. Description tuning is never "done" — real failures are the best eval queries.

### Step 4: Apply the result

First check `exit_reason`. The only values `run_loop.py` emits are: `"unknown"` (no iterations ran — loop-launch failure), `"all_passed (iteration N)"` (all *train* queries passed on iteration N — held-out test queries are not consulted for this exit, so check `best_test_score` in `results.json` before reporting success), `"max_iterations (N)"` (hit the limit — partial optimization, apply best result), and `"improve_description crashed on iteration N: <error>"` (the `claude -p` improvement step failed — no traceback; `results.json` is written with `best_description` from the iterations before the failure). If it's `"unknown"`, no iteration ran (`--max-iterations 0`): there is no traceback and results.json IS written, with best_description = original_description. Apply nothing (the description was not optimized; `--max-iterations 0` is the intentional case, any other cause means checking the launch command). A crash never leaves an `"unknown"` results.json: a traceback in loop.log before the results write, or a pre-run `Error:` exit, means results.json is absent (the four states under "Step 3: Run the optimization loop" in "Description Optimization"): apply nothing and diagnose from loop.log, where the traceback or `Error:` line names the root cause. For `"improve_description crashed on iteration N: <error>"`: apply nothing, report the error text to the user, and diagnose the `claude -p` auth/model failure it names before re-running. For `"all_passed (iteration N)"` or `"max_iterations (N)"` (match via startswith: `"all_passed"` or `"max_iterations"`) — the only two non-failure values the script emits — take `best_description` (the four values listed are exhaustive in the current implementation — the list is closed; encountering any other value is a signal that something is wrong: apply nothing, report the unexpected value to the user, and re-run the loop after verifying the eval-set shape and launch arguments are correct (an unexpected value is handled by this rule for unrecognised values, not by the `"unknown"` rule above).) from the `results.json` the loop wrote — to find the timestamped subdir path, `grep "Results saved to:" <workspace>/trigger-opt/loop.log` (as described in Step 3) — if this returns empty despite a successful exit_reason (e.g. process was killed before that line printed), the subdir still exists under `<workspace>/trigger-opt/`; list it with `ls -t <workspace>/trigger-opt/` and use the most recent timestamped directory. Note: the directory is created by run_loop.py `main()` BEFORE `run_loop()` is called, so even a crash that occurred in the first iteration would leave the directory present without a `results.json` — check that `results.json` exists inside the directory before reading it. Then read `best_description` from that subdir's `results.json` and update the skill's SKILL.md frontmatter. Show the user before/after and report the scores. (Note: `results.json` also contains a `final_description` field — this is the last description the loop tried, not necessarily the best; always use `best_description`, not `final_description`, when applying the result. The fields in `results.json` are: `exit_reason`, `best_description`, `original_description`, `final_description`, `best_score`, `best_train_score`, `best_test_score`, `iterations_run`, `holdout`, `train_size`, `test_size`, `history` — each is described in the "results.json" section of `references/schemas.md`. Note: `best_test_score` is `null` when no holdout test set was used (`holdout=0` or empty test set) — check for null before displaying to the user.)
