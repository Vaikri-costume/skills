# Running and evaluating test cases: full procedure

Moved out of SKILL.md. SKILL.md holds the short version and the helper commands; this file holds the full gotchas for Steps 1 to 5. Where a helper script now does a step, the helper wins and the inline recipe below is the fallback for runtimes without Python.

This section runs straight through Steps 1–4 (including giving the user the viewer URL at the end of Step 4) without pausing; the one intended stop is the beginning of Step 5, where you wait for the user to tell you they're done reviewing the viewer — don't abandon the eval mid-run before then. This section's paired with-skill/baseline runs + centralized-ledger workspace ARE the eval mechanism — they produce the `benchmark.json` the viewer and recommendations payload depend on, which a generic testing skill won't. **Agent tool dependency is intentional** (a body-level Claude extension gets only an advisory lint warning at this tier; the rule is in `references/lint-details.md`) — parallel subagent dispatch is the core mechanism for independent with-skill/baseline comparison runs; both Claude Code and Cowork (the `claude-users` tier targets) support it. Claude.ai adaptations that work without subagents are in `references/runtime-adaptations.md`.

Treat the benchmark pass-rates and timing/token numbers as **aspirational rough benchmarks, not precise thresholds** — aim for rigor, but expect an element of judgment. A skill that passes 9/10 assertions isn't necessarily worse than one at 10/10 if the qualitative outputs are stronger. Read the numbers alongside the human review, not instead of it.

**Tool/MCP-dependent skills.** When the skill under test makes MCP or tool calls, a triggering test isn't enough — include at least one test case that exercises a real call and confirm it *succeeds* (not just that the skill loaded). If a call fails during testing, first isolate MCP-setup-vs-skill: confirm the server is connected, check auth/scopes/OAuth, and try the call directly outside the skill — if it fails there too, the defect is the MCP setup, not the skill.

**Workspace location (CCVW fork — read this first).** ALL eval outputs — iteration directories, skill snapshots, trigger-eval JSONs — go under a centralized ledger, not beside the skill. `<workspace>` is defined once, in SKILL.md "Running and evaluating test cases" (the configured `eval_workspace` plus `/<skill-name>`) — create it on first use with `mkdir -p` on that path.

**Set `<workspace>` that way before reading further** — every command in Steps 1–5 uses it; substitute actual values for `<skill-name>` and `<N>`. Build the directory tree lazily (`mkdir -p` on demand); organize by eval iteration (`iteration-1/`, `iteration-2/`, etc.) and per test case (eval's descriptive name). Never write eval artifacts into the skill's own tree — keeps `~/.claude/skills/` clean and prevents skill-tracer's file enumeration from picking up workspace dirs. (Exception: `<skill-path>/evals/evals.json` lives in the skill's source tree intentionally — it is the skill's eval definition file, versioned with the skill source (though excluded from the packaged `.skill` per Step "Test cases"); it is not a run artifact.)

### Step 1: Spawn each test case's runs (with-skill AND baseline) in the same turn

**Session-log marker (only when the profile sets `session_log_dir`; see SKILL.md "Personal settings"):** append one line at the start of each iteration, before dispatching its runs, `**[HH:MM:SS] SKILL:skill-creator-ccvw RUN:<skill-name>-iter<N> STEP:iteration-<N>**` to `<session_log_dir>/session-log-YYYY-MM-DD.md`. When the key is unset or `off`, write nothing. Non-blocking.

For each test case, spawn two subagents in the same turn — one with the skill, one without. **This is load-bearing for comparison correctness**: same-turn dispatch prevents the orchestrator from seeing run 1's output before dispatching run 2; sequential dispatch would let run 2's prompt be influenced by what run 1 produced, breaking the independence the comparison depends on. (Finishing around the same time is a secondary benefit.)

To run with the skill, render the prompt with `python3 scripts/render_prompt.py --kind with_skill --var skill_path=... --var task=... --var input_files=... --var run_dir=<workspace>/iteration-<N>/eval-<name>/with_skill/run-1 --var outputs_wanted=... --var scratch_dir=...` (the scratch directory SKILL.md "Personal settings" describes) and dispatch it. For every `--kind` in this file, pass the same `helper_model` value as the model setting of the Agent dispatch itself: the template's "Use the model" line is text the started agent reads, and it cannot change the model that agent runs on. The template (`references/dispatch-prompts/with_skill.txt`) carries the framing line, the Sonnet instruction, the no-names rule and the exact `## Eval Prompt` transcript heading the viewer parses. To get the task and input_files values when recovering mid-build, read them from the eval entry (its prompt and files fields; input_files in this skill's own evals) in `<skill-path>/evals/evals.json`. Use the descriptive eval name in paths, never the integer id.

Variables each `--kind` needs, all passed as `--var key=value` (every kind also takes `helper_model` and `scratch_dir`, which `scripts/render_prompt.py` fills from `scripts/skill_config.py` when not passed; it exits 1 naming any value that is missing, an empty `scratch_dir` included, and it refuses a forbidden term only in values that do not hold paths, the path keys being listed in the `scripts/render_prompt.py` docstring): with_skill: skill_path, task, input_files, run_dir, outputs_wanted. Take `input_files` from the eval entry's files list, or pass the word none when it has no files, and take `outputs_wanted` from the entry's expected_output text (this skill's own evals have no expected_output: there `outputs_wanted` is the output folder the prompt names, the skill_out folder inside the run folder). The script always refuses the configured author identity in non-path values; pass --forbid <term> (repeatable) to add further terms, such as names the prompt must not contain. baseline: skill_name, task, input_files, run_dir, outputs_wanted, and optionally baseline_source (empty unless improving). grader: skill_creator_path, expectations, transcript_path, outputs_dir, and optionally inspection_hint. analyst: skill_creator_path, iteration_dir, skill_path. `skill_creator_path` is this skill's own install directory (the folder holding its SKILL.md and `agents/`); `iteration_dir` is `<workspace>/iteration-N`.

**Baseline run** (same prompt, but the baseline depends on which mode you are in — create vs improve was already decided at SKILL.md "Decide: install, improve, adapt, or build"; use that to pick the bullet and dir name):

**Baseline isolation is instruction-only, not sandboxed — treat every baseline run as unverified until checked.** The baseline subagent is a normal general-purpose dispatch: it keeps full filesystem access (Read/Glob/Bash/Skill/ToolSearch) for the whole session, including `~/.claude/skills/` and the Skill-tool listing that names the skill under test in its own description. Nothing at the harness level prevents it from finding and reading the skill anyway (by browsing `~/.claude/skills/`, grepping for the skill's name, or invoking the Skill tool directly) — "no skill path in the prompt" is a request, not a restriction the subagent is mechanically held to. There is also no independent transcript of the baseline subagent's own tool calls available to the orchestrator afterward: the parent session JSONL records only the Agent dispatch (`tool_use`) and its final returned text (`tool_result`) — never the subagent's internal Read/Glob/Bash calls. So the only mitigation available without breaking the Agent-tool/Cowork-compatible dispatch model (Workflow's per-agent journal.jsonl is not an option here — see the "Agent tool dependency is intentional" note above) is the self-reported, instruction-based check below. Treat a clean check as harm-reduction, not proof.
- **Creating a new skill**: no skill at all. Render `--kind baseline` with `run_dir` ending `without_skill/run-1` and `baseline_source` empty. The template carries the hard constraints (no path containing `/skills/` or the skill name apart from its own `run_dir` and input files, no `SKILL.md`, no Skill-tool use for it) and the `## Isolation Check` requirement. WHY the blanket `/skills/` ban: the baseline must not stumble onto the skill under test, or its snapshot, through the shared skills tree; the template has no exception for a sibling skill, so a baseline never reads one: a task that depends on a sibling skill's behaviour gets that behaviour in its input files instead, and `--allow` (below) only covers a sibling skill's name or path that the task text itself mentions and the baseline echoes in its transcript.
- **Improving an existing skill**: the old version, the cycle's snapshot at `<workspace>/skill-snapshot/`. Iterations never create, replace or touch the snapshot, whatever their number or whether the session was resumed; they only read it. `references/improve-existing-skill.md` Step 3 (Draft changes preserving intent) is the only place that creates or replaces it, and holds the rule for an existing one. Render `--kind baseline` with `run_dir` ending `old_skill/run-1` and `baseline_source` set to `- Work only from the skill snapshot in <workspace>/skill-snapshot/ (read its SKILL.md); this snapshot is the one exception to the constraints below`. WHY a snapshot: the orchestrator edits `<skill-path>` in place across iterations, so a baseline pointed at the live path would read the improved version and the comparison would collapse. The snapshot does not stop the baseline reading the live skill, so the same constraints apply with the live `<skill-path>` and its name forbidden.

**After the baseline run returns, before trusting the comparison:** run `python3 scripts/check_isolation.py --transcript <baseline run-1>/transcript.md --skill-name <name> --run-dir <baseline run-1>`. Exit 1 means contaminated (or no `## Isolation Check` section) and exit 2 means the transcript file is missing; on either, discard that run's outputs and grading and re-dispatch it, noting the redispatch in the benchmark notes as sub-step 3 (Do an analyst pass) of "Step 4: Grade, aggregate, and launch the viewer" describes. With `--run-dir` the script counts both kinds of failure per run and sets `cap_reached` at 3: stop then and ask the user, rather than dispatching a fourth time. Pass `--allow <substring>` for a path the task text itself hands the baseline, such as an input folder or a sibling skill's name or path that the task mentions (an input SKILL.md path is otherwise a hit; this only stops the transcript being flagged, it does not let the baseline read a `/skills/` path), and for an improve-mode baseline pass `--allow <workspace>/skill-snapshot` so reading the snapshot is not flagged (an allowed substring also covers the rest of the path it starts, such as the snapshot's SKILL.md). For iteration 2+ the baseline does not change: a fresh `without_skill` run in create mode, and in improve mode `old_skill` run against the cycle's snapshot (`<skill-path>` is edited in place and no step snapshots it again, so there is no previous-iteration baseline). Use only the four recognised names (`with_skill`/`new_skill`, `without_skill`/`old_skill`), because `aggregate_benchmark` matches the delta by name.

Each run lives in its own `<config>/run-1/` directory — `outputs/`, `transcript.md`, `grading.json`, and `timing.json` all sit under `run-1/`. `aggregate_benchmark` discovers runs only at `<config>/run-*/` and skips any config dir lacking a `run-*` child, so the `run-1/` layer is required (not optional). The viewer's Outputs tab badges exactly four config-dir names — these four and no others get a badge: treatment side is `with_skill` (default) or `new_skill` (an accepted alias of `with_skill`: the improve-mode command below passes `with_skill` with `old_skill`, and `new_skill` with `old_skill` works the same); baseline side is `without_skill` (create-mode) or `old_skill` (improve-mode). The Benchmark tab colours each config's rows by the badge rule where the name is recognized (baseline names get the baseline colour) and by sorted position otherwise (first config = treatment colour). The aggregator accepts any config dir name that has a `run-*` child — so custom names aggregate, but they get no Outputs-tab badge and the delta falls back to alphabetical order with a warning (see gotcha (a) under sub-step 2 "Aggregate into benchmark" of "Step 4: Grade, aggregate, and launch the viewer"); use the four recognized names.

Create the iteration tree and every `eval_metadata.json` with the helper: `python3 scripts/eval_workspace.py --workspace <workspace> --iteration <N> --evals <skill-path>/evals/evals.json --configs <names>`, with `--configs with_skill,without_skill` in create mode and `--configs with_skill,old_skill` in improve mode (the default is the create-mode value, which would leave an unused `without_skill/` folder per eval that the viewer shows as an empty run). It writes `eval-<name>/eval_metadata.json` (`eval_id` as a JSON integer, `eval_name`, `prompt`) at the `eval-<name>/` level, makes `<config>/run-1/outputs/` for each config, and refuses duplicate or string ids and an eval that already exists in the iteration. Ids are unique within an iteration and may repeat across iterations. Use `--only 0` for the one-item pilot (which iterations run one: SKILL.md "The iteration loop"); once the pilot is graded, build the rest with the remaining ids (for example `--only 1,2`), because a full re-run is refused while eval 0 exists in the iteration. The order is: build eval 0, run its two runs through Steps 1 to 3 and grade them (sub-step 1, Grade each run, of "Step 4: Grade, aggregate, and launch the viewer"); then build the remaining ids, run Steps 1 to 3 for them and grade them; then run Step 4 sub-steps 2 to 6 once over all evals, so the pilot alone never goes through aggregation, the analyst pass or the viewer.

### Step 2: While runs are in progress, draft assertions

Don't just wait for the runs to finish — you can use this time productively. Draft quantitative assertions for each test case and explain them to the user. If expectations already exist in `evals/evals.json`, review them and explain what they check.

Good assertions are objectively verifiable and have descriptive names — they should read clearly in the benchmark viewer so someone glancing at the results immediately understands what each one checks. Subjective skills (writing style, design quality) are better evaluated qualitatively — don't force assertions onto things that need human judgment.

Update `<skill-path>/evals/evals.json` (its `expectations`) with the drafted checks — this is the skill's own eval definition file at the skill root; the grader reads these via the orchestrator: at sub-step 1 of Step 4 ("Grade, aggregate, and launch the viewer"), the orchestrator reads `expectations` from this file and includes them in the grader dispatch prompt. The viewer later renders the *graded* outcomes from each run's `grading.json`, not `evals.json`. Also explain to the user what they'll see in the viewer — both the qualitative outputs and the quantitative benchmark.

### Step 3: As runs complete, capture timing data

Capture the harness's `total_tokens` and `duration_ms` for each run as its task-completion notice arrives, and write them at once: `python3 scripts/write_timing.py --run-dir <workspace>/iteration-<N>/eval-<name>/<config>/run-1 --total-tokens T --duration-ms D`. This is the only chance to capture them. A value you cannot find is left out and written as 0; the harness's field names vary by version, so read them however your harness exposes them.

Gotchas for reading the numbers: zeros in `timing.json` are averaged into `time_seconds` (a failed run shows near-zero time), but a zero `total_tokens` is replaced by grading.json's `execution_metrics.output_chars`, so a failed run's token column shows characters, not tokens. `aggregate_benchmark` reads `time_seconds` from grading.json first (executor plus grader) and timing.json second (executor only), so the metric can mix meanings across runs. It reads `total_duration_seconds`, never `duration_ms`.

### Step 4: Grade, aggregate, and launch the viewer

Once all runs are done (in every command below, `iteration-N` is a **placeholder for the literal current-iteration integer** — substitute the actual number per the rule in the Workspace-location paragraph above; a literal `iteration-N` directory won't exist and `aggregate_benchmark` exits with `Directory not found`):

1. **Grade each run** — spawn a grader subagent per run, all in the same turn since the runs are independent, when subagents are available (Claude Code / Cowork), or grade inline on runtimes without them (Claude.ai). If a grader subagent fails mid-iteration (partial grading done — at least one `grading.json` already exists in the iteration, regardless of which dispatch number failed), finish remaining runs inline for that iteration: scan `<workspace>/iteration-N/eval-*/*/run-1/` for directories missing `grading.json` — those are the remaining runs needing grading. If the filesystem scan itself fails (read error), default to grading all runs inline to be safe. If the VERY FIRST grader dispatch fails before any grading.json exists, grade all runs for that iteration inline. Each run's grading.json is written independently, so switching modes mid-iteration is acceptable as long as every run's grading.json ends up with the same field contract. Inline grading requires the same `grading.json` field contract — `summary{pass_rate,passed,failed,total}`, `timing{total_duration_seconds}`, per-expectation `text`/`passed`/`evidence` — as the grader subagent produces. `references/runtime-adaptations.md` (its Claude.ai specifics section) restates the same contract and points to schemas.md for the full shape — consult `references/schemas.md` for additional detail. Either way, **read `agents/grader.md` first** (to understand the grader's contract and required inputs; the rendered grader prompt, `references/dispatch-prompts/grader.txt`, points the worker at `agents/grader.md` and supplies the three inputs below, and the orchestrator does not paste the brief into it), then use its three data inputs: `expectations` (the eval's checks from `evals/evals.json` — that file has a top-level `evals[]` array; for a multi-eval skill, index into it and select the entry whose `id` field (the field name in evals.json) matches the `eval_id` value (the field name in eval_metadata.json) in this run's eval_metadata.json — these are different JSON key names on different objects that hold the same logical integer — then read that entry's `expectations` array; full structure in `references/schemas.md`), `transcript_path` (the `transcript.md` the run wrote to `<config>/run-1/`), and `outputs_dir` (`<config>/run-1/outputs/`). Include these as named fields in the grader's dispatch prompt text, e.g.: `"expectations: [...], transcript_path: /path/to/transcript.md, outputs_dir: /path/to/run-1/outputs/"`. **Before dispatching the grader**, check the outputs saved to `<config>/run-1/outputs/` to identify any non-text formats. If `outputs/` is empty (no files were written), note it in the grader dispatch ("no output files exist") and grade on transcript content only; if the transcript also indicates no substantive output, grade all expectations as failed and note the empty output in the evidence. If `transcript.md` itself is absent (a killed/failed executor subagent — the same failure mode `timing.json` handles with zeros at Step 3), do not dispatch the grader for that run; write a `grading.json` directly with all expectations `passed: false` and evidence "run produced no transcript (executor subagent failed)", so the run still aggregates as a failure rather than blocking the iteration. **For non-text outputs** (PDFs, images, spreadsheets, binary files, Office documents like .docx/.pptx, and any non-plain-text format), the grader dispatch must ALSO hand the grader the inspection tools/instructions it needs to open them — for example, include "use the Read tool to read the file" in the grader's dispatch prompt for files the model can read directly (images, PDFs); for spreadsheets, Office documents, or binary formats, include a conversion command or path to a helper script in the dispatch prompt. "Providing" a tool means including the instruction in the dispatch prompt text — the grader agent has access to the same tools the orchestrator has; the instruction enables the grader to use them. `agents/grader.md` assumes its prompt supplies these and is told not to trust the transcript alone; a grader given only the three data inputs has no way to read a non-text output. Write `grading.json` to the run directory — `<config>/run-1/grading.json`, the sibling of `outputs/` — whether you spawned a subagent or graded inline. (A dispatched grader writes it there itself: per `agents/grader.md` it derives the run directory as the parent of the `outputs_dir` you pass — `{outputs_dir}/../grading.json` — and likewise reads `timing.json` from that same parent. So of the grader's inputs you pass all three data inputs named above (`expectations`, `transcript_path`, `outputs_dir`) in the dispatch prompt, but you do NOT additionally pass the grading.json output path or the timing.json path — those two the grader derives from `outputs_dir` itself.) The grading.json expectations array must use the fields `text`, `passed`, and `evidence` (not `name`/`met`/`details` or other variants) — these three field names are **one contract across all three consumers** (the grader emits them, `aggregate_benchmark` validates them, the viewer renders them), so don't rename them in any one place. (A grader that *succeeds* but writes wrong field names is not caught here at sub-step 1 — it surfaces at sub-step 2, where `aggregate_benchmark` emits `Warning: expectation … missing required fields` and you re-dispatch that run's grader. You do not need a separate field-validation pass at sub-step 1; the aggregate warning is the catch.) For checks that can be verified programmatically, write and run a script rather than eyeballing it — scripts are faster, more reliable, and can be reused across iterations. (`grading.json` is the full per-run record, of which consumers read a subset: the viewer surfaces `summary` + `expectations`; `aggregate_benchmark` reads `summary`/`expectations`/`execution_metrics`/`timing` and folds `user_notes_summary` into each **run's** per-run `notes` field (runs[].notes in benchmark.json — distinct from the top-level benchmark.json["notes"] field which the analyzer fills via the merge step); `claims` stays in the file as a human-facing verification record; `eval_feedback` — the grader's eval-critique — is consumed by the recommendations payload in sub-step 4 of this same Step 4, below.)

2. **Aggregate into benchmark** — run the aggregation script:
   ```bash
   # run from the skill-creator-ccvw directory so the skill root is the cwd
   # (~/.claude/skills/skill-creator-ccvw/ — substitute the real path for python -m commands)
   # (run_loop.py and package_skill.py require -m because they import from scripts.*; aggregate_benchmark.py uses -m for consistency but has no cross-script imports)
   python -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <name> --skill-path <path-to-skill> --model <model-id-powering-this-session>
   ```
   Produces `benchmark.json` and `benchmark.md` with pass_rate, time, tokens per configuration (mean ± stddev + delta). Pass `--model` so `metadata.executor_model`/`analyzer_model` carry the real model id (omit it and they stay a `<model-name>` placeholder). To derive the model ID: look for it in the system prompt header, the session info, or the harness environment — in Claude Code it appears as the session model name; use the exact identifier string the API accepts (e.g. `claude-sonnet-4-20250514`); `runs_per_configuration` is the largest number of runs any one eval has for a configuration (1 with the `run-1/` layout), not the total across evals. The viewer pairs configurations by grouping on each run's `configuration` field, so you do NOT need to hand-order the runs array. **Three gotchas:** (a) `delta` is computed as primary − baseline, where primary/baseline are matched BY NAME against a known vocabulary — `with_skill`/`new_skill` as primary, `without_skill`/`old_skill` as baseline (config discovery is alphabetical via `sorted(eval_dir.iterdir())`, but the delta calculation does not trust that order — it looks up the two roles by name instead of by position). Any combination of the four recognized names gives a correctly-signed delta regardless of which one sorts first alphabetically. The two config columns next to it, in the `benchmark.md` summary table and the viewer's Benchmark tab, still follow alphabetical order, so in improve mode the table reads Old Skill, With Skill, Delta: Delta is always with_skill (or new_skill) minus without_skill (or old_skill), whichever column comes first. Only custom config-dir names outside that vocabulary fall back to the old alphabetical-positional behavior, and the script prints a `Warning:` to stderr when it does — if you see that warning, read the per-config means directly rather than trusting the delta sign, or rename your config dirs to the recognized vocabulary and re-run. (b) The script exits 1 if the `<workspace>/iteration-N` directory does not exist (stdout: `Directory not found: …`); fix: substitute the correct path and re-run; for all other paths it exits 0 even on partial data, unless it stops with a Python traceback (three cases, told apart by the last `aggregate_benchmark.py` line in the traceback: (1) the write of `benchmark.json` or `benchmark.md` fails with an OSError such as PermissionError — check disk space and directory permissions; (2) a `run-*` directory with a non-integer suffix like `run-abc/` or a bare-hyphen suffix `run-` triggers a ValueError in `int(run_dir.name.split('-')[1])` — rename or remove the offending directory by its literal absolute path, with every placeholder already filled in (e.g. `mv <workspace>/iteration-<N>/eval-<name>/<config>/run-abc <workspace>/iteration-<N>/eval-<name>/<config>/run-1` or `rm -rf <workspace>/iteration-<N>/eval-<name>/<config>/run-abc`), then re-run aggregate_benchmark; check that run directory names follow exactly `run-<N>/`; note that `run-1-extra` silently parses as run 1 without crashing (split gives index 1 = "1") so it won't produce a ValueError but will be misidentified — avoid extra hyphens too. Note: `eval-*` directory names use an equivalent int() parse (the eval-index parse in `aggregate_benchmark.py`) but with a `try/except ValueError` that silently catches it and falls back to `eval_idx` — so `eval-chart-formatting/` without an eval_metadata.json is safe; only run-* names are unprotected; (3) any other traceback, such as an OSError while reading or an AttributeError, means a file the script reads could not be read or holds valid JSON of the wrong shape: when the traceback's line reads a run's `grading.json` (for example one that is not an object, or has a null timing or summary field), re-run that run's grader as for the `Warning:` lines below, then re-run aggregate_benchmark; when it reads another file (a run's `timing.json` or an eval's `eval_metadata.json`), report the traceback and that file to the user.) It runs in the foreground, so its stdout (the `Warning:` lines, interleaved with the `Generated:`/`Summary:` output) comes back to you directly in the command result; scan it for `Warning:` lines and act on each type distinctly: `Warning: grading.json not found in {run_dir}` → the grader never ran for that run; re-run the grader subagent. `Warning: Invalid JSON in {grading_file}` → the grader produced malformed output; re-run the grader. `Warning: expectation in {grading_file} missing required fields (text, passed, evidence): {exp}` (the actual message includes the malformed expectation dict) → the grader used wrong field names; fix the grader dispatch or the output format and re-run. The correct action: re-dispatch the grader subagent for only the affected run (identified by the file path in the warning message `{grading_file}`); do not manually edit benchmark.json or grading.json. After fixing, re-run aggregate_benchmark. Bound: after three failed grader re-dispatches for one run (the same cap as the isolation check above), grade that run inline as sub-step 1 describes and re-run aggregate_benchmark once more; if its grading.json still draws a warning, stop and ask the user. (The malformed entry is **included** in result["expectations"] despite the warning, NOT dropped — the current benchmark.json already contains the malformed expectation; after fixing grading.json and re-running aggregate_benchmark, the new benchmark.json will have the corrected expectation.) (c) If the directory exists but has no `eval-*/` subdirs, the script exits 0 but prints `No eval directories found in … or …/runs` (`…` is shorthand for the actual benchmark_dir path values; grep for the prefix `"No eval directories found"` — the actual output uses real path values, not the `…` shorthand) and emits an **empty** benchmark — that means the wrong dir, or the runs weren't saved; treat it as a setup error, not a valid zero-result — `grep "No eval directories found"` in the command output to confirm this is the condition, then check that the path is correct and runs were saved to `iteration-N/eval-*/` subdirs, and re-run. Manual generation: see `references/schemas.md`.

3. **Do an analyst pass** — read the benchmark data and surface patterns the aggregate stats hide. Render the analyst prompt (`python3 scripts/render_prompt.py --kind analyst --var ...`; it passes exactly the three Mode B inputs, so the analyzer cannot drift into Mode A) and dispatch it; it writes `<workspace>/iteration-N/analyst-notes.json`, a JSON array of observation strings (non-discriminating assertions, flaky evals, time/token tradeoffs). Then merge: `python3 scripts/merge_notes.py --iteration-dir <workspace>/iteration-N`. The script refuses a missing or malformed file, a non-array, and an empty array when `benchmark.json` has no `runs[]`; on any refusal fix the cause (re-run aggregate_benchmark, re-dispatch the analyst) and merge again. An empty array with a non-empty `runs[]` is a valid zero-observation result. On runtimes where the analyzer is skipped (`references/runtime-adaptations.md`) leave `notes` empty. To record an orchestrator note in the benchmark (a redispatched baseline, runs made in series), append one string to the array in the analyst-notes file after the analyst writes it and before you merge: aggregate_benchmark resets benchmark.json's notes on every run and merge_notes.py replaces them with that array, so a note written anywhere else is lost, and after any later re-aggregation you merge again, appending the note again if the analyst rewrote the file.

4. **Author the recommendations payload** — write `<workspace>/iteration-N/recommendations.md` per `references/recommendations-template.md` (three sections: did well / failed at / recommended next iteration; bullet counts are minimums — more is better, every observation saves an iteration cycle). Fold in each `grading.json`'s `eval_feedback` (the grader's eval-critique: weak/non-discriminating assertions, outcomes no assertion covers) when present — `eval_feedback` is optional (the grader omits it when it finds no issues), so if absent from a grading.json, skip that run's contribution to eval suggestions. If grading.json itself is absent for a run (the grader never ran), re-run sub-step 1 grading for only that run, then re-run sub-step 2 (aggregate) and sub-step 3 (analyst pass and merge, appending again any note you had added) before proceeding, because aggregate_benchmark skipped that run and resets the notes — then fold in its eval_feedback if present. To fold: write recommendations.md first per the template (the three sections — did well, failed at, recommended next), THEN append a `## Eval Quality Recommendations` section for eval_feedback content (the heading contains "recommend" so the viewer renders its bullets in the **"Recommended next iteration"** sidebar bucket — this is expected behavior, not a separate section; note the viewer takes every line that starts with `- ` or `* ` (after trimming indentation, so nested bullets become flat items) and files it under the most recent matched `## ` heading; a `###` subheading does not start a new bucket, so bullets under it land in the preceding `##` bucket — write flat top-level `- ` bullets directly under the `## ` heading); for each grading.json where `eval_feedback` is present, extract its `suggestions[]` (each has `reason` and optionally `assertion` (when the suggestion relates to a specific expectation) — some suggestions about uncovered outcomes have no `assertion` field) and `overall` field and append as flat top-level `- ` bullets, one per suggestion, each prefixed inline with the eval name — `- <eval-name>: <suggestion>` (use `eval_name` from `eval_metadata.json` if available, otherwise the directory basename `eval-<descriptive-name>`). That critique is actionable input for the next iteration's evals, and this payload is its consumer.

5. **Launch the viewer** (`<skill-creator-ccvw-path>` is this skill's own install directory — `~/.claude/skills/skill-creator-ccvw`):
   ```bash
   nohup python <skill-creator-ccvw-path>/eval-viewer/generate_review.py \
     <workspace>/iteration-N \
     --skill-name "my-skill" \
     --benchmark <workspace>/iteration-N/benchmark.json \
     --recommendations <workspace>/iteration-N/recommendations.md \
     > <workspace>/iteration-N/viewer.log 2>&1 &
   echo $! > <workspace>/iteration-N/.viewer.pid   # persist the PID to a file — shell variables do NOT survive across the user-review turn boundary
   ```
   **Server mode (default):** After launching, read `<workspace>/iteration-N/viewer.log`. The server startup prints `  URL:       http://localhost:<port>` (with a two-space indent and `URL:` prefix) — `grep "  URL:" <workspace>/iteration-N/viewer.log` to extract the URL line, then strip the exact prefix `  URL:       ` (two spaces + `URL:` + seven spaces) to give the user the URL — or use `sed -n 's/^  URL: *//p' <workspace>/iteration-N/viewer.log` to extract just the URL directly without counting spaces (portable; the `-P` option of `grep` needs GNU grep and BSD grep on macOS rejects it). If the grep returns nothing — the server is still starting — retry: `sleep 2 && grep "  URL:" <workspace>/iteration-N/viewer.log`; the URL line appears after the server binds to its port (repeat a few times if needed). An invalid-option error from `grep` is not a slow start; use the portable form instead. Common failure outputs to watch for in `viewer.log` (all failure messages go to stderr which the `2>&1` redirect captures into viewer.log; this list covers the most likely cases but is not exhaustive — any Python traceback from an unhandled error also lands there; for any unlisted traceback: read it to identify the error type, diagnose the root cause in generate_review.py or its dependencies, fix and retry). **Exception:** if the `nohup` command itself fails to start Python (Python not on PATH, import error), viewer.log may be empty or missing. To diagnose: re-run the viewer launch command WITHOUT `&` (foreground mode) to see the error directly on your terminal; alternatively, check if Python is on PATH with `which python`/`which python3`. If only `python3` is available, substitute `python3` for `python` in the launch command and re-run. `Error: {workspace} is not a directory` (wrong workspace path — the pattern uses the actual path value, not a literal `<path>`), the bare `No runs found in {workspace}` (runs not saved — no `Error:` prefix on this one; the actual path is substituted for `{workspace}` in the output, not the literal string; grep for the prefix `"No runs found in"`), or a Python traceback — all cause the viewer to exit before starting. For workspace/runs errors: fix the path or verify runs were saved, then re-run. **Note on port handling:** the script first tries to kill any process listening on the default port and then binds it, so when the default port was occupied the URL line normally shows the default port again; only if the port is still in use after that kill attempt does it fall back to an ephemeral port (port 0) — no manual retry needed; the URL line in viewer.log always shows the port actually bound. A Python traceback from a port-related OSError only occurs in the extreme case where the OS refuses ALL port bindings; if you see such a traceback, wait for other processes to release ports and retry. The script picks a free port if the default is taken, so don't assume a fixed port. Note: generate_review.py unconditionally attempts to kill any existing process on the default port before binding — if another unrelated process is on that port, it may be terminated. **Static/headless mode (`--static`, used in Cowork):** Run the script without `nohup`/`&` (it exits immediately) and capture stdout:
```bash
output=$(python <skill-creator-ccvw-path>/eval-viewer/generate_review.py \
  <workspace>/iteration-N \
  --skill-name "my-skill" \
  --benchmark <workspace>/iteration-N/benchmark.json \
  --recommendations <workspace>/iteration-N/recommendations.md \
  --static <workspace>/iteration-N/review.html)
```
The script prints (to stdout) `\n  Static viewer written to: <path>\n` — note the leading newline before the two spaces in the raw output; `grep` splits on newlines so the grep match line is `  Static viewer written to: <path>` (two leading spaces, no leading newline). Strip `  Static viewer written to: ` (two spaces + label + space) to extract the path — or use `echo "$output" | grep "Static viewer" | sed 's/  Static viewer written to: //'` (portable; a `grep -oP` form needs GNU grep and BSD grep on macOS rejects it; this sed depends on a two-space indent that is a bare string literal in generate_review.py's static-mode success print, with no formal API contract; if the indentation changes the sed would fail silently — so **verify the extracted path is non-empty before handing it to the user; if it is empty, fall back to the absolute `--static` path you passed into the command**, which is the same file). Note: the `sed`-based form returns the whole rest of the line, so a `--static` path containing a space is extracted intact. **Pass an absolute path for `--static`** (e.g., `<workspace>/iteration-N/review.html`) so the extracted path is directly usable by the user without needing the current working directory. If the command exits 1, check stderr for the failure message (errors always go to stderr in both modes; in server mode they are captured in viewer.log via 2>&1, while in static mode they appear on the shell stderr distinct from the stdout success line): `Error: {workspace} is not a directory` → fix the workspace path and re-run; `No runs found in {workspace}` → verify runs were saved and re-run; any other Python traceback → diagnose and fix the root cause. (These two non-traceback messages are the named exit-1 conditions; any Python traceback — including an OSError from the `--static` write path (disk full, permission denied) — is the third category: read the traceback type, fix the underlying cause (permissions, disk space, path validity), and re-run. A non-traceback stderr message that does not match either named pattern indicates an unexpected error — inspect the script for the new error path.) Give the extracted file path to the user to open in their browser. For iteration 2+, also pass `--previous-workspace <workspace>/iteration-<N-1>` where N is the current iteration integer (the same N used in `iteration-N` throughout this section). Headless environments and Cowork-specific viewer behaviour: see `references/runtime-adaptations.md`. Use `generate_review.py` — don't write custom HTML. (Note: `run_loop.py` internally uses a separate `generate_html` from `scripts/generate_report.py` for its live-updating browser progress page — that is a different function from the eval-viewer's `generate_review.py`; the executor does not call either directly.)

6. **Tell the user** the viewer is open and what it shows — two tabs (Outputs, Benchmark) plus a Recommendations sidebar; `references/viewer-ui.md` has the full user-facing message template and navigation reference, and what the Outputs tab leaves out when a run's output is a folder. (The Recommendations sidebar is silently absent if `recommendations.md` headings don't contain the viewer's keywords. The viewer uses keyword substring matching — a heading is matched if it contains "well", "fail", or "next"/"recommend" anywhere in the heading text. If absent despite the file existing: verify each heading contains one of those keywords — not exact names.)

### Step 5: Read the feedback

When the user tells you they're done, read `<workspace>/iteration-N/feedback.json` — **server mode only**: the server writes this file to the workspace on POST; in static/Cowork mode the browser downloads feedback.json to the user's Downloads folder rather than POSTing to the server, so `<workspace>/iteration-N/feedback.json` does not exist — see `references/runtime-adaptations.md` "Cowork specifics" section, **Feedback flow.** paragraph for where to read it. (if the file does not exist in server mode — the user may have submitted but a write error occurred — ask them to re-submit; if re-submit is not possible, collect inline feedback: ask what they liked and what they'd change for each eval run, and record their responses as `{"run_id": "…", "feedback": "…"}` entries — these substitute for the missing feedback.json in the next revision step):

```json
{
  "reviews": [
    {"run_id": "eval-chart-formatting-with_skill-run-1", "feedback": "the chart is missing axis labels", "timestamp": "..."},
    {"run_id": "eval-table-extraction-with_skill-run-1", "feedback": "", "timestamp": "..."},
    {"run_id": "eval-form-filling-with_skill-run-1", "feedback": "perfect, love this", "timestamp": "..."}
  ],
  "status": "complete"
}
```

Empty feedback *on an individual run* (a run's feedback string is empty) means the user typed no comment on that run — the viewer does not record which runs were opened, so treat it as no complaint (the user thought it fine or skipped it; ask if it matters). When the user clicked "Submit All Reviews", the file has one entry per run, with an empty string for runs without a comment. A `reviews` array that is entirely empty (`"reviews": []`) is what the viewer leaves after the user dismissed the done dialog with "OK" having typed no comment on any run (its auto-save rewrites the file with only non-empty comments and `"status": "in_progress"`), so it means no feedback was typed, not that the viewer failed to display the runs; ask the user whether they meant the runs to pass as they are. `"status": "complete"` is set browser-side by `viewer.html` when the user clicks "Submit All Reviews" — in server mode the browser POSTs to the server (the server is a pass-through; it writes whatever the browser POSTs); in static/Cowork mode the browser downloads a feedback.json file directly without any POST (see `references/runtime-adaptations.md`). Either way, the status field is always set browser-side. If `status` is `"in_progress"`, the user either is still reviewing (auto-save fires 800ms after the last keypress — a debounce, not a repeating interval) OR has already submitted and clicked "OK" on the done dialog (the viewer resets status back to `"in_progress"` on dismiss). To distinguish: if the user has told you they're done AND status is `"in_progress"`, treat it as submitted — check the reviews content rather than the status. Proceed as if status were `"complete"`: use the reviews content to author the improvement plan. If `status` is absent (unusual — produced only by a partial POST or manually-written feedback.json), the user hasn't submitted yet (re-ask them). A feedback.json written manually or from a partial POST will not have `status: "complete"` even if reviews are populated. Focus your improvements on the test cases where the user had specific complaints.

Kill the viewer server when you're done with it (**server mode only — skip this step in static/Cowork mode where no server was started and no `.viewer.pid` file was written**). Read the PID back from the `.viewer.pid` file written at launch (a shell variable would not survive the wait for the user's review, which spans separate Bash calls):

```bash
kill "$(cat <workspace>/iteration-N/.viewer.pid)" 2>/dev/null
```
