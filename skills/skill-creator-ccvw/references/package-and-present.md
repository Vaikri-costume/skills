# Package and present

Moved out of SKILL.md. Build-time local delivery only; publishing is skill-publisher's job.

Check whether you have access to the `present_files` tool (it is available if it appears in your toolset; if uncertain, attempt a no-op invocation and proceed based on whether it succeeds or returns a tool-not-found error). If you don't, skip the packaging presentation but tell the user: "The skill is ready — install it from `<path-to-skill-directory>` using skill-publisher or by running `python -m scripts.package_skill <path> <workspace>` to create a .skill file." If you do, package the skill and present the .skill file to the user:

```bash
# run from the skill-creator-ccvw directory (package module — needs the skill root as cwd)
python -m scripts.package_skill <path/to/skill-folder> <workspace>
```

After packaging, direct the user to the resulting `.skill` file path so they can install it. The script prints `✅ Successfully packaged skill to: <path>` and exits 0 on success — capture the script's stdout and grep it: `output=$(python -m scripts.package_skill <path> <workspace>); echo "$output" | grep "✅ Successfully packaged skill to:"` — then strip the prefix `✅ Successfully packaged skill to: ` from the grep result to extract the path: `echo "$output" | grep "✅ Successfully packaged" | sed 's/✅ Successfully packaged skill to: //'`. If stdout is empty and the command exited non-zero (import error or Python not found), check stderr directly: the error would be a Python traceback with no `❌` prefix (the script prints multiple lines before the success line). Always pass the second argument, the output directory (`<workspace>` as SKILL.md "Running and evaluating test cases" defines it, or the scratch directory): without it the script writes the `.skill` file into the current working directory, which by the launch convention above is the skill-creator-ccvw source tree, and the SKILL.md "Hard rules" rule that begins "Eval and scratch files go only" keeps scratch output out of a skill's own tree. It exits 1 with the following prefixes — these are all current error output forms in the script: `❌ Validation failed: …` (quick_validate failed first — fix the frontmatter and re-run, not retry; note: this error also prints an advisory second line `   Please fix the validation errors before packaging.` without a ❌ prefix — that line is informational only). Other error exits also exit 1: skill folder not found / path not a directory / SKILL.md missing each print `❌ Error: <description>` (the `❌ Error:` prefix); a zip/archive failure prints `❌ Error creating .skill file: <exception>` (different prefix — scan for this too). For path/structure errors (`❌ Error: …`): fix the path or verify the skill directory structure, and re-run. For archive failures (`❌ Error creating .skill file: …`): check disk space, output directory write permissions, and that the output path is not a directory — then re-run.

This packager is a **build-time local-delivery convenience** — it zips the freshly-built skill (any tier) for immediate local install. It is *not* the distribution/release packager. When the user wants to **share or publish** the skill (tier transition, attribution/security/portability gates, version bump, PR), that's `skill-publisher`'s job — suggest running it rather than treating this `.skill` as a release artifact.
