# skill-publisher

## What this skill does

The **ship** phase of the build → trace → ship ecosystem. After skill-creator-ccvw builds a skill and skill-tracer finds its bugs, skill-publisher makes it release-ready: polishes the prose, audits CCVW compliance, runs the tier-transition checks appropriate to the target's audience, teaches the README how to install and use the skill, versions it, packages it, and opens a GitHub PR when there's an upstream to PR to.

Each phase suggests the next; skill-publisher is terminal — it produces a shippable artifact (and optionally a PR URL).

---

## When to invoke

- Slash command: `/skill-publisher <skill-name>` or `/skill-publisher <absolute-path>`
- Natural language: "ship skill X", "publish X", "release X", "make a PR for X", "package X for the marketplace"
- **Proactively** after skill-tracer converges on a skill the user intends to share — suggest the ship phase.

---

## Prerequisites

The target skill must exist as a directory containing at least a `SKILL.md`. Best results when it also has `README.md` (intent) and `HISTORY.md` (provenance) — skill-publisher works in degraded mode if HISTORY.md is absent (see Step 1). The orchestrator needs `Read`/`Edit`/`Write` on the target, `Agent` for the cold CCVW audit, `Bash` for lints + packaging + git, and `Skill` to invoke `simplify`. (skill-tracer is recommended but not required — its `stage_cold_prompts.py` is the canonical staging path for the Step 3 audit prompt; `references/audit-prompt.md` carries a substitute-by-hand fallback when skill-tracer is absent.)

---

## Runtime constraint — top-level invocation only

skill-publisher requires `Agent` to dispatch the cold CCVW Word/Spirit audit (Step 3). `Agent` is available only in the top-level Claude session — never from inside a nested Agent call. If the orchestrator detects it's a subagent (Agent unavailable), stop and tell the user: "skill-publisher must run from the top-level session; nested Agent dispatch is not available here."

---

## The ledger

skill-publisher records its work at `~/.claude/skill-publisher-ledger/<skill>.md` — one file per target skill, accumulating across ship runs. Format spec: `references/ledger-format.md`. The ledger's Phase column values are POLISH / AUDIT / TIER / PACKAGE / PR (not skill-tracer's TRACE/SIMPLIFY/PORT-AUDIT — different skill, different phases). Recovery across compaction uses an `in-flight::` marker + atomic-write protocol; the action-keyword set (one per workflow step), marker format, and recovery rules are in `references/recovery-protocol.md`.

## Workflow

### Step 1 — Resolve target + read state

**First action: capture `<Runtime>`** = current UTC `YYYY-MM-DDTHH:MM` (run `date -u +%Y-%m-%dT%H:%M`) — capture it before the recovery check below, because that check makes tool calls; one timestamp is then reused VERBATIM (the identical `YYYY-MM-DDTHH:MM` string) for every in-flight marker and ledger row this run, so recovery rule 4's marker read-back matches (the Capture-invocation-state block below restates the full state set, including `<Runtime>`). **Then load `references/recovery-protocol.md` in full.** The in-flight marker check that follows requires it. (Forward note, fully specified in `references/recovery-protocol.md` rule 4 loaded just below — recovery rule 4 (`addressing run-N`) resumes at Step 5's addressing after the marker check, bypassing the *interactive* target-read block below; but Step 5 itself first re-resolves the target path + tier and re-runs Steps 3-4 cold to rebuild the cluster set, per recovery-protocol.md rule 4 — it does not skip the audit/tier re-derivation. This is the one exception to the "every invocation" rule for the interactive read only.) After loading, **first, if the invocation argument is a relative path (neither a bare name nor an absolute path), reject it and ask the user to re-invoke — do this before any ledger lookup, so a traversal path is never used as `<skill>`.** Otherwise, check for an in-flight marker in `~/.claude/skill-publisher-ledger/<skill>.md` (use the invocation argument as `<skill>` for this initial lookup — the SKILL.md frontmatter `name` field is authoritative and will be cross-checked in the target-resolution step below). If the ledger file does not exist (first-ever ship for this skill): run `mkdir -p ~/.claude/skill-publisher-ledger/` in Bash, then use the Write tool to create `~/.claude/skill-publisher-ledger/<skill>.md` with the standard header from the **Header template (new ledger)** section of `references/ledger-format.md`; start Run 1. If the file exists but cannot be read (permission error or encoding issue): USER-PAUSE — report the exact path and error; do not proceed until the user resolves the file. If the file exists, is readable, and carries an in-flight marker: run the matching recovery rule. If the line is present but unparseable (matches `in-flight::` but fails the `<Runtime> <action> run-N` format, or names an unrecognized action keyword): apply recovery-protocol.md's unknown-keyword fallback (treat as `addressing`) AND surface the malformed marker to the user before continuing — do not guess silently. If the file exists, is readable, and carries no in-flight marker, consult **recovery rule 7** (authoritative in `references/recovery-protocol.md` — the brief gloss here defers to that rule): if prior rows exist, rule 7 determines whether the prior run completed or crashed; if the ledger has no data rows, start Run 1.

**Capture invocation state** (do now, before any tool call that changes time):
- `<Runtime>` = the UTC timestamp captured as the First action above — reused for every in-flight marker and ledger row this run; never re-derived per step.
- `<N>` = the Run number determined from the ledger state above (Run 1 for first-ever ship; highest-existing-run + 1 for a fresh run; current in-flight run number for a resumed run). Retain both values in conversation context throughout the run.

(Convention used throughout this skill: **"warn"** means emit a one-line message in your response text this turn — visible to the user — not a session-log entry.)

Resolve the target: bare `<name>` → `~/.claude/skills/<name>/`; absolute path → use directly. A relative path (e.g. `../other-skill`) matches neither rule — ask the user to re-invoke with a bare name or absolute path. Verify SKILL.md exists. The resolved absolute skill-root path is bound to `<target>` and used verbatim in every downstream script command (Steps 4/8/9/10); later steps never re-derive it from the raw invocation argument. The target's SKILL.md frontmatter `name` field value is `<skill>` — used in all session-log markers (Steps 2–9) and the ledger path `~/.claude/skill-publisher-ledger/<skill>.md`. (If the frontmatter `name` differs from the invocation argument used for the initial ledger lookup, surface a warning and use the frontmatter value — it is authoritative. If a provisional ledger was created/read at the invocation-argument path during the initial lookup, move it to the frontmatter-name path before writing any rows — or, if it already holds prior-run rows, USER-PAUSE to reconcile — so the recovery marker and this run's rows do not split across two ledger files.)

Read the target's three root files into in-memory state:
- **SKILL.md** — the runtime workflow being shipped. (No separate in-memory label needed — the executor follows it step by step and does not retain it under a named variable.)
- **README.md** — read the `## Intent` section into `<target-intent>` (used by the polish pass to preserve intent; if README.md is absent OR present without a `## Intent` section, warn and set `<target-intent>` to the target's SKILL.md `## What this skill does` section as fallback — both cases take the same fallback).
- **HISTORY.md** — read the YAML frontmatter (version, category, author, inspirations) + changelog. (Fields accessed by name in later steps — `version`, `category`, `author.primary`, `author.history`, `inspirations` — no separate in-memory label needed; reference them by field path when steps use them.) **If HISTORY.md is absent → degraded mode**: prompt the user once for an attribution category (A/B/C/D) or 'skip', then either scaffold a minimal HISTORY.md (on a valid A/B/C/D answer) or ship locally (on 'skip'). Retain the answer as `<attribution-answer>`. The full prompt text, case-insensitive re-ask, the closed minimal-field set, the category-letter / `infer_category` behavior, the `author.primary` AskUserQuestion, the "not attribution-complete" caveat, and the `license`-is-a-SKILL.md-field note are in `references/changelog-format.md` "Degraded-mode HISTORY.md scaffold". **Skip-branch consequences (control-flow downstream steps depend on):** on 'skip' (or default-to-skip), no version bump (no prior version); Step 9 still runs but opens **no upstream PR** (offering the no-upstream hosting-branch option instead); run Step 8 packaging as normal (`.skill` for shared tiers; personal-tier unpackaged). (Steps 6–7 and Step 10 carry their own degraded-mode handling — see those steps; this list is not exhaustive.)

Determine the **audience tier** from `metadata.intended-audience` (one of `personal` / `claude-users` / `model-agnostic`). This drives Step 4's checks and Step 8's packaging. (`portability_lint.py` keys on `metadata.tier` when `--tier` is omitted — both fields normally carry the same value, but if they diverge on the target, display a warning to the user stating both fields and their current values (e.g. "`metadata.tier: personal` but `metadata.intended-audience: claude-users`") — both must carry the same tier value per the CCVW spec (WHY: `portability_lint.py` reads `metadata.tier` when `--tier` is omitted — a divergence means the lint validates against the wrong tier value, yielding incorrect pass/fail results); ask the user which tier to treat as authoritative for this ship run before running Step 4. Steps 2 and 3 (polish and audit) do not depend on the tier value and can proceed while the user decides; the divergence question must be resolved before Step 4 entry — concretely, resolve it BEFORE issuing Step 4's first command (the portability_lint frontmatter gate), since that gate needs the authoritative `--tier`; if the user has not responded by the time Step 4 is about to begin, do not run the gate — re-ask the question and wait for a valid answer, then run the gate with the user-chosen authoritative tier (a valid answer names which field is authoritative — acceptable forms: `metadata.tier`, `metadata.intended-audience`, or the tier value itself such as `claude-users`; if the user names a tier value matching NEITHER field's current value, treat that as choosing that value as authoritative for this run and pass it as `--tier`).)

### Step 2 — Polish pass (mandatory)

**Session-log marker (first action of this step):** `echo "**[$(date +%H:%M:%S)] SKILL:skill-publisher RUN:<skill> STEP:polish**" >> "${HOME}/.claude/session-logs/session-log-$(date +%Y-%m-%d).md"` — substitute the actual target skill name for `<skill>`. Non-blocking. **Then write in-flight marker (second action of this step)** (per atomic-write table in `references/recovery-protocol.md`): write `in-flight:: <Runtime> polish run-<N>` to the ledger header (insert after the `# Ship ledger — <skill>` title line if absent; replace any existing `in-flight::` line in place).

**Load `references/polish-pass.md` now (third action of this step, after the echo and the in-flight marker write)** — it owns the full simplify invocation procedure, 4-agent pass, Targeted Reversal, and regression handling. Then invoke the `simplify` skill on the target's SKILL.md + README.md to remove phrasing entropy (use the Skill tool — the invocation guidance is in `references/polish-pass.md`). Apply every finding with consolidation + intent awareness (preserve `<target-intent>`; don't simplify away load-bearing WHY content — a WHY is load-bearing when removing it would leave a rule undefended: the reader could not tell from context why the rule exists or why it must be that specific form; a comment that merely elaborates without defending a constraint is editorial, not load-bearing). Record each polish edit as a POLISH-phase ledger row, numbering clusters with the per-Run `C<n>` sequence (C1, C2, … continuing across POLISH/AUDIT/TIER/PACKAGE/PR within this Run, per `references/ledger-format.md`). The append form (Step 5 has the full spec) is `append_ledger.py append <ledger> --runtime <Runtime> --round <N> --phase POLISH --cluster C# --root-cause '...' --address '...' --flags '...'` — run `python3` as the literal command word, not via a shell variable (see `references/ship-checklist.md`). The publisher writes only FIX/STRENGTHEN/USER-PAUSE addresses (never would-*, which append_ledger also accepts only for skill-tracer verify-only parity). WHY record them: the POLISH rows make the polish pass auditable in the same ledger as the audit/tier work, and let a post-compaction resume see which edits already landed.

After polish, check the SKILL.md body size: if it exceeds ~5,000 words (~500 lines) after polishing, flag it — the polish pass is the moment to push detail into `references/`, and an over-long SKILL.md taxes every session the skill loads in. Surface as a POLISH cluster (FIX = move a section to a reference; or STRENGTHEN/USER-PAUSE if the length is load-bearing). The 5,000-word ceiling rationale lives in `references/polish-pass.md`.

After polish, suggest the user re-run `/skill-tracer <skill>` if the polish made substantial edits (optional, user-chosen — chained by suggestion). Polish can introduce regressions the way any edit can; a verification trace catches them. Don't block on it.

### Step 3 — CCVW Word/Spirit audit (cold dispatch)

**Session-log marker (first action of this step):** `echo "**[$(date +%H:%M:%S)] SKILL:skill-publisher RUN:<skill> STEP:audit**" >> "${HOME}/.claude/session-logs/session-log-$(date +%Y-%m-%d).md"` — substitute the actual target skill name for `<skill>`. Non-blocking. **Then replace in-flight marker**: write `in-flight:: <Runtime> audit run-<N>` (replacing the Step 2 `polish run-<N>` marker in place, per atomic-write table).

Dispatch one cold audit Agent against the skill-creator-ccvw reference spec. The full audit prompt body, reference-skill resolution (skill-creator-ccvw → skill-creator → plugin-dev/skill-development fallback chain), mtime capture, and ABORTED handling live in `references/audit-prompt.md` (moved here from skill-tracer — this audit used to be tracer's Step 9); load it now and follow its procedure to stage + dispatch the audit Agent. Collect GAP blocks; label this set `<audit-gaps>` for reference in Step 5. Assign each GAP a sequential ledger flag ID in output order: the first GAP is `G1`, the second `G2`, etc. (plain `G<n>` codes, no hyphen — distinct from TIER sub-families `G-PORT*`, `G-ATTR*`, `G-COWORK*` which always carry a hyphenated segment). This numbering applies only when at least one GAP is found — a zero-GAP audit produces no G-codes (see the zero/non-zero handling at the end of this step). Retain these ID assignments in the in-memory `<audit-gaps>` set — annotate each GAP block with its assigned G-code in your reasoning context; no write to disk at this point. Verify the result ends with a `No gaps found` or `No of gaps found:: N` trailing line — if the trailing line is absent, first check whether the result begins with `ABORTED`; if so, follow `references/audit-prompt.md`'s ABORTED handling rather than treating it as malformed. If the trailing line is absent AND the result does not begin with `ABORTED`, treat it as malformed and re-dispatch the audit Agent (initial dispatch + up to 2 re-dispatches = 3 dispatches total; if the 3rd dispatch is still malformed, USER-PAUSE — ask the user whether to provide a manual audit result or skip the audit; if the user provides a manual result treat it as the audit output; if the user declines, treat it as zero GAPs, note the audit skip in a ledger row (Phase=AUDIT, `--cluster <next C# in this Run's sequence — C1 if no prior clusters this Run, else continuing the POLISH/AUDIT numbering>`, `--root-cause 'audit declined by user'`, `--flags 'audit-skipped'`, `--address 'USER-PAUSE (audit declined; treated as zero GAPs)'` — `--root-cause` is also required, so include it; this satisfies append_ledger's required args), then proceed to Step 4) following audit-prompt.md's staging + dispatch procedure (already loaded above) — a re-dispatch re-stages the same single audit prompt against the current target state (there is no multi-file list to rebuild: the publisher dispatches one cold audit, not a trace fan-out); after a successful re-dispatch, apply the zero/non-zero-GAP logic at the end of this step (zero GAPs → proceed to Step 4; non-zero → each GAP is an AUDIT-phase cluster) to the new result. If the audit returns zero GAPs (`No gaps found`), proceed to Step 4. Each GAP becomes an AUDIT-phase cluster addressed per `references/ship-checklist.md`'s FIX/STRENGTHEN/USER-PAUSE rules.

This is the "is it CCVW-compatible in word and spirit?" gate — the publisher owns it now, not the tracer. A skill can be bug-free (tracer-clean) but still violate CCVW conventions; this audit catches that before release.

### Step 4 — Tier-transition checks (per audience tier)

**Session-log marker (first action of this step):** `echo "**[$(date +%H:%M:%S)] SKILL:skill-publisher RUN:<skill> STEP:tier**" >> "${HOME}/.claude/session-logs/session-log-$(date +%Y-%m-%d).md"` — substitute the actual target skill name for `<skill>`. Non-blocking. **Then replace in-flight marker**: write `in-flight:: <Runtime> tier run-<N>` (replacing the Step 3 `audit run-<N>` marker in place, per atomic-write table).

**Before any tier checks: verify vendored scripts are in sync.** Run `python3 ~/.claude/skills/skill-publisher/scripts/check_vendored_sync.py` (exit 0 = in sync). On a non-zero exit, **address each finding INLINE now, before running the tier lints** — running them against a stale vendored copy validates the wrong code. Re-copy DRIFT / VENDORED_MISSING from canonical and USER-PAUSE on CANONICAL_MISSING, then re-run until exit 0. Still record each as a TIER row in Step 5's ledger, but perform the re-copy here. Full case + exit-code handling (DRIFT / CANONICAL_MISSING / VENDORED_MISSING, multi-file sequencing, exit 2, unreadable-file crash → USER-PAUSE): `references/tier-transition-checks.md` "Vendored-sync checks".

Run the checks appropriate to the target's `metadata.intended-audience`. The per-tier bullets below summarize the check set; `references/tier-transition-checks.md` is the authoritative full spec — if the two ever differ, follow tier-transition-checks.md.

**Frontmatter-validity gate (claude-users+ — runs first, blocking).** Before the tier-specific checks, run the deterministic frontmatter gate:

```bash
python3 ~/.claude/skills/skill-publisher/scripts/quick_validate.py <target>; echo "exit:$?"
python3 ~/.claude/skills/skill-publisher/scripts/portability_lint.py <target> --tier <tier> > /tmp/skill-publisher-lint-out.json; echo "exit:$?"   # canonical temp file the reuse rule below reads
```

**Capture exit codes:** the Bash tool does not preserve shell state across calls, so append `; echo "exit:$?"` to each command where the exit code drives a branch (e.g. `python3 … quick_validate.py <target>; echo "exit:$?"`). Read the `exit:N` line from stdout to determine pass/fail before acting on the output.
Capture the `portability_lint.py` JSON output to the canonical temp file (`python3 ~/.claude/skills/skill-publisher/scripts/portability_lint.py <target> --tier <tier> > /tmp/skill-publisher-lint-out.json; echo "exit:$?"`); reuse it for the per-tier checks below when the tier matches (re-read with `cat`), or re-run with the correct `--tier` if they differ. Read the two gate scripts differently: `quick_validate.py` prints a **plain-string** message ("Skill is valid!" or the first error) and signals pass/fail only via its **exit code** (0 = valid, 1 = invalid) — branch on the exit code, do NOT parse its stdout as JSON; `portability_lint.py` prints **JSON** (keys `ccvw_mandatory_missing`, `tier_violations`, `would_fail_at_tiers`, …) — note it exits 1 on ANY non-empty findings (the normal collect-findings case), NOT as a hard gate-fail like quick_validate's exit 1; the block decision keys on `would_fail_at_tiers` membership, not its exit code. **A finding blocks the target's own tier if and only if the authoritative tier (resolved in Step 1) appears in `would_fail_at_tiers`** — "blocks" means blocks ship (address in Step 5), not halt Step 4; keep collecting all tier findings into an in-memory `<tier-clusters>` list, which Step 5 addresses alongside `<audit-gaps>`. The temp-path / reuse rationale, the full output-key list + error-key case, the `would_fail_at_tiers` plain-strings + `blocks_tier "(warning)"`-suffix mechanics, and the always-block vs informational rules are in `references/tier-transition-checks.md` "Interpreting portability_lint.py output".

A non-zero `quick_validate.py` exit is a **blocking TIER finding** (frontmatter doesn't parse or violates a hard rule). **Arg-count gotcha:** `quick_validate.py` also exits 1 on a usage error (not exactly one argument) — pass exactly `<target>` and confirm from stdout which exit-1 cause occurred — a frontmatter check prints a specific frontmatter error (e.g. "No YAML frontmatter found"); an arg-count usage error prints `Usage: …`. (`Skill is valid!` prints ONLY on exit 0, never on exit 1.) `portability_lint.py`'s structural checks (every tier) add registration-correctness blockers — `name` == folder basename, no reserved `claude`/`anthropic` prefix, no XML-tag-shaped `<...>` frontmatter content (a prompt-injection surface — see `references/security-checks.md` "Frontmatter prompt-injection surface"), main file named exactly `SKILL.md`, and plan-code leakage (a `tier_violations` finding, not a `quick_validate.py` one). The full hard-rule + structural blocker lists (both non-exhaustive — see the script sources) and the registration-correctness WHY are in `references/tier-transition-checks.md` "Frontmatter-validity gate". Each is a blocking TIER cluster at any **shared** tier; personal skips the gate (next bullet).

- **`personal`**: skip Step 4 entirely (including the frontmatter gate). Personal skills aren't shared; no portability/Cowork/cross-runtime checks apply.
- **`claude-users`**: run all of —
  - `portability_lint.py --tier claude-users` (no user-specific paths)
  - **Cowork-compatibility check** per `references/cowork-compatibility.md` (viewer auto-launch, headless `--static` mode, feedback-via-download, TodoList reminders — the Cowork-runtime adaptations). Both Claude Code lint AND Cowork check must pass.
  - `attribution_lint.py` (HISTORY.md complete + LICENSE present whenever `author.history[]` is non-empty; exit 1 with `would_fail_attribution_check` present → a real attribution failure (the value is `true` on every such exit 1); exit 1 with an `{error}` key and no `would_fail_attribution_check` → HISTORY.md absent, the degraded/backfill path, per tier-transition-checks.md) followed by `spdx_check.py <target>` (frontmatter `license` is a recognized SPDX/OSI id — advisory at Step 4, run `spdx_check` WITHOUT `--require`; attribution_lint has no `--require` flag, so this applies to spdx_check only; the hard `--require` gate runs at PR time)
  - Security check per `references/security-checks.md` (credentials, injection, broken access control — runs once here at ship time; `security_scan.py` exit 0 = no code findings; exit 1 = candidate findings; exit 2 = path/permissions error — fix and re-run; also read the `unreadable_files` array in the JSON — if non-empty the scan is incomplete even on exit 0, so review those files manually and record a TIER cluster so the gap isn't silently skipped)
  - **MCP-dependency declaration** (always run `mcp_deps.py <target>` — it self-reports N/A on exit 0 when the skill calls no `mcp__*` tools, so no separate "does it call MCP?" pre-check is needed): verify the README install section + `metadata.mcp-server` name the MCP server(s) the installer must connect (run `mcp_deps.py <target>`: exit 0 = no MCP calls (N/A) or every called server declared; exit 1 = undeclared server(s); exit 2 = SKILL.md not found / usage error). Per `references/tier-transition-checks.md`. An MCP-enhancement/multi-MCP skill that doesn't declare its server ships broken-on-arrival for anyone but the author. (Why either README or `metadata.mcp-server` suffices, and the per-server flagging rule: `references/tier-transition-checks.md` check 5.)
- **`model-agnostic`**: all `claude-users` checks PLUS —
  - `portability_lint.py --tier model-agnostic` (no Claude extensions)
  - `compatibility: agentskills.io@1.0` frontmatter verification
  - cross-runtime install-surface note (user-confirmed list of runtimes tested)

(The five vendored scripts — `quick_validate`/`portability_lint`/`attribution_lint` from skill-creator-ccvw, `render_ledger`/`append_ledger` from skill-tracer — are listed with their canonical sources and the one-intentional-difference rule in `references/tier-transition-checks.md` "Vendored-sync checks"; each drift is a Step-5 TIER cluster re-copied from its canonical source.)

### Step 5 — Address findings

**Session-log marker (first action of this step):** `echo "**[$(date +%H:%M:%S)] SKILL:skill-publisher RUN:<skill> STEP:addressing**" >> "${HOME}/.claude/session-logs/session-log-$(date +%Y-%m-%d).md"` — substitute the actual target skill name for `<skill>`. Non-blocking. **Then replace in-flight marker**: write `in-flight:: <Runtime> addressing run-<N>` (replacing the Step 4 `tier run-<N>` marker in place, per atomic-write table).

**Before beginning cluster addressing:** verify `<target-intent>` is available in context. If not (compaction resume via recovery rule 4 skips Step 1), or if in any doubt: re-read the target README.md `## Intent` section from disk, or use the target SKILL.md `## What this skill does` as fallback — re-reading from disk is always safe. Likewise verify `<N>` (the Run number) and `<Runtime>` are set; if a recovery-rule-4 resume skipped the Step 1 Capture block, re-derive `<N>` from the ledger's highest Run value (resuming the in-flight run keeps that number — see recovery-protocol.md "Run number determination") and recover `<Runtime>` from the in-flight marker's timestamp field (`in-flight:: <Runtime> addressing run-N`), or re-capture current UTC if the marker is unreadable — `<Runtime>` feeds the `--runtime` argument of every append. Rule 4 re-runs Steps 3-4 to rebuild the cluster set, which need inputs the bypassed target-read block normally captures: re-resolve the target SKILL.md path (from the invocation argument → `~/.claude/skills/<skill>/`, or the recorded path) and re-read the target's `metadata.intended-audience` tier before re-running those steps.

For every cluster in `<audit-gaps>` (Step 3) and `<tier-clusters>` (Step 4) — the AUDIT + TIER clusters — decide and act: FIX (change the artifact), STRENGTHEN (the artifact is correct, add a WHY), or USER-PAUSE (intent-ambiguous — ask). The full address-decision rules live in `references/ship-checklist.md`; load it now. Use `<target-intent>` to inform FIX-vs-USER-PAUSE: a fix that would violate the README's stated Intent is a USER-PAUSE.
