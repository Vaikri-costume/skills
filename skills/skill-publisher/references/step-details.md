# Step details

Detail moved out of `SKILL.md` toward the ~5,000-word ceiling the polish pass enforces on target skills (`references/polish-pass.md`). Each block is the original SKILL.md text, verbatim, for the step named in its heading; `SKILL.md` keeps the summary and points here. Where a block and a more specific reference (`tier-transition-checks.md`, `packaging.md`, `changelog-format.md`, `ledger-format.md`) differ, the specific reference wins.

## Readiness mode (Step 1)

**Readiness-mode exit (if `<mode>` is `readiness`).** Skip Steps 2–9 entirely. The tier is already determinable from the SKILL.md frontmatter resolved above. **If `metadata.tier` and `metadata.intended-audience` diverge** (the same condition the Step-4 entry resolves): readiness mode skips Step 4, so resolve it here instead — pass the user-authoritative tier explicitly as `readiness_report.py <target> --tier <tier>` (ask the user which field is authoritative if they have not said), rather than letting `readiness_report.py`'s `detect_tier` silently prefer `intended-audience`; surface the divergence in your response. Otherwise run `python3 ~/.claude/skills/skill-publisher/scripts/readiness_report.py <target>` — it executes all cheap deterministic gates from `references/readiness-gates.md` and prints a human-readable verdict (green/yellow/red, each gate's result, and a 'will/won't complete at `<tier>`' line). **Exit codes:** 0 = green/yellow, 1 = red (blockers) — for both, print the output verbatim; **exit 2** = usage/path error (SKILL.md not found, or tier still undeterminable) — the script printed an `ERROR:` line to stderr and no verdict; relay that error and tell the user to fix the path / pass `--tier`, do not report a green/yellow/red verdict that was never produced. **Write no ledger rows, no in-flight markers, no version bump.** The ledger file is not opened. Readiness mode is fully read-only. Exit after printing.

## Step 4 gates

The JSON goes to the canonical temp file `/tmp/skill-publisher-lint-out.json` (reuse it for the per-tier checks when the tier matches — re-read with `cat`; re-run only on a tier mismatch). Two gates, read differently: `quick_validate.py` signals pass/fail by **exit code only** (0 valid / 1 invalid — its stdout is a plain string, not JSON); `portability_lint.py` prints **JSON** (`ccvw_mandatory_missing`, `tier_violations`, `would_fail_at_tiers`) and exits 1 on ANY findings (not a hard gate-fail), so the block decision keys on `would_fail_at_tiers` membership, not its exit code. The one load-bearing rule to hold here: **a finding blocks the target's own tier iff the authoritative tier (Step 1) appears in `would_fail_at_tiers`** — "blocks" = address in Step 5, not halt Step 4; collect all tier findings into `<tier-clusters>`. The output-key list, error-key case, the `would_fail_at_tiers` plain-strings + `blocks_tier "(warning)"`-suffix soft case, and the always-block-vs-informational rules are in tier-transition-checks.md "Interpreting portability_lint.py output" (loaded above).

A non-zero `quick_validate.py` exit is a **blocking TIER finding** (frontmatter doesn't parse / violates a hard rule; note it also exits 1 on a usage error, so pass exactly `<target>` — `Skill is valid!` prints only on exit 0). **Exception — exit 3 = PyYAML not installed**: the validator could not run at all (an environment gap, not a skill defect) — tell the user to `pip install pyyaml` and re-run; do **not** raise a TIER cluster against the skill's frontmatter. `portability_lint.py`'s structural checks add registration-correctness blockers — `name`==folder basename, no reserved `claude`/`anthropic` prefix, no XML-tag-shaped frontmatter content (a prompt-injection surface), main file named exactly `SKILL.md`, plan-code leakage. The full hard-rule + structural-blocker lists, the exit-1 arg-count-vs-frontmatter disambiguation, and the registration-correctness WHY are in tier-transition-checks.md "Frontmatter-validity gate" (loaded above). Each is a blocking TIER cluster at any **shared** tier; personal skips the gate (next bullet).

- **`personal`**: skip Step 4 entirely (including the frontmatter gate). Personal skills aren't shared; no portability/Cowork/cross-runtime checks apply.
- **`claude-users`**: run all of —
  - **Portability** — reuse `/tmp/skill-publisher-lint-out.json` from the frontmatter gate above (it ran `portability_lint.py --tier claude-users`); only re-run if the gate used a different tier. (No user-specific paths.)
  - **Internal-link integrity** (`link_check.py <target>`: exit 0 = clean; exit 1 = findings — read the JSON with `--json`; exit 2 = SKILL.md not found / usage error). The JSON carries three finding kinds — `broken_links`, `dead_scripts`, and `unreadable`. Each **broken link** (a cited `references/*.md` / `scripts/*.py` / `assets/*` path that does not resolve on disk — the skill's own polish pattern can orphan one) is a **blocking** TIER cluster: the executor would try to load a missing file. Each **unreadable** file (a cited file that exists but could not be read — a permission/encoding fault) is **also blocking**: the link scan is incomplete, so a clean verdict would be a false negative — surface it and resolve the file before shipping (mirrors `readiness_report.py`'s `_gate_links`, which classifies `unreadable` as a blocker). Each **dead script** (a `scripts/*.py` nothing references or imports) is an **advisory** TIER cluster (dead code shipped to users — remove it or wire it in). Citations attributed to a sibling skill are auto-excluded, so a finding is genuinely this skill's. Per `references/tier-transition-checks.md`.
  - **Cowork-compatibility check** per `references/cowork-compatibility.md` (viewer auto-launch, headless `--static` mode, feedback-via-download, TodoList reminders — the Cowork-runtime adaptations). Both Claude Code lint AND Cowork check must pass.
  - `attribution_lint.py` (HISTORY.md complete + LICENSE present whenever `author.history[]` is non-empty; exit 1 with `would_fail_attribution_check` present → a real attribution failure (the value is `true` on every such exit 1); exit 1 with an `{error}` key and no `would_fail_attribution_check` → HISTORY.md absent, the degraded/backfill path, per tier-transition-checks.md) followed by `spdx_check.py <target>` (frontmatter `license` is a recognized SPDX/OSI id — advisory at Step 4, run `spdx_check` WITHOUT `--require`; attribution_lint has no `--require` flag, so this applies to spdx_check only; the hard `--require` gate runs at PR time)
  - Security check per `references/security-checks.md` (credentials, injection, broken access control — runs once here at ship time; `security_scan.py` exit 0 = no code findings; exit 1 = candidate findings; exit 2 = path/permissions error — fix and re-run; also read the `unreadable_files` array in the JSON — if non-empty the scan is incomplete even on exit 0, so review those files manually and record a TIER cluster so the gap isn't silently skipped)
  - **MCP-dependency declaration** (always run `mcp_deps.py <target>` — it self-reports N/A on exit 0 when the skill calls no `mcp__*` tools, so no separate "does it call MCP?" pre-check is needed): verify the README install section + `metadata.mcp-server` name the MCP server(s) the installer must connect (run `mcp_deps.py <target>`: exit 0 = no MCP calls (N/A) or every called server declared; exit 1 = undeclared server(s); exit 2 = SKILL.md not found / usage error). Per `references/tier-transition-checks.md`. An MCP-enhancement/multi-MCP skill that doesn't declare its server ships broken-on-arrival for anyone but the author. (Why either README or `metadata.mcp-server` suffices, and the per-server flagging rule: `references/tier-transition-checks.md` check 5.)
- **`model-agnostic`**: all `claude-users` checks PLUS —
  - `portability_lint.py --tier model-agnostic` (no Claude extensions)
  - `compatibility: agentskills.io@1.0` frontmatter verification
  - cross-runtime install-surface note (user-confirmed list of runtimes tested)

## Step 6

  - **Executability probe (after generating a `claude plugins install <org>/<repo>` command).** Only when the form resolved to a GitHub-registry command (skip for the manual-path-only and "installed locally" forms — there is nothing reachable to probe): run `python3 ~/.claude/skills/skill-publisher/scripts/install_check.py --repo <org>/<repo> [--marketplace-name <plugin-name>] --json` (pass `--json` so the result is the machine-readable object whose `repo.detail`/`catalog.detail` fields are read below — without it the script prints only human-readable lines; pass `--marketplace-name` only when the README documents a marketplace install, so the catalog entry is checked too). Read the exit: **0** = reachable, or `unverified` (gh/network couldn't confirm — degrade, no action); **1** = a confirmed problem (`repo: not_found`/`private`, or `catalog: absent` — the JSON `repo.detail`/`catalog.detail` says which) → **warning, NOT a hard block**: surface it to the user ("the derived install command points at a repo/entry that doesn't resolve: …") and let them decide (fix the source URL, or ship anyway — a repo not yet created is expected on a first ship that creates it in Step 9). Do not write a ledger row for an `unverified` result. (Mirrors `verify_ship.py`'s offline-degrade discipline — an unconfirmable check is never a failure.)

- **`## Sibling skills`** — auto-detect from HISTORY.md `inspirations[]` if present and non-empty (each inspiration is a sibling/source — an empty `inspirations[]` array counts as absent here, so don't emit an empty section); otherwise ask the user: `Which skills does this pair well with? (list names or descriptions, or skip)` — on a 'skip' answer, omit the `## Sibling skills` section and remove its placeholder (so the no-remaining-placeholder pass condition holds); otherwise use their answer to fill the section with one bullet per sibling: its name and a one-line description of how it pairs (source the pairing description from the HISTORY.md `inspirations[].pattern` field if present; if absent, read the sibling's SKILL.md `## What this skill does` section or README.md `## Intent` section if the sibling is installed locally at `~/.claude/skills/<sibling>/` (`<sibling>` = the `inspirations[].skill` field value); if not installed, use HISTORY.md `inspirations[].description` if present; if `skill`, `pattern`, and `description` are all absent (only a bare `source` URL), omit that sibling bullet rather than invent one — do not invent a pairing description without a source). (The HISTORY.md read into memory at Step 1 is still authoritative here — nothing between Step 1 and this step edits HISTORY.md; the version bump that writes it is Step 7, later — so use the in-memory copy; re-read from disk only if it was never retained.)

**Outcomes-first positioning (polish heuristic, not a hard gate).** While filling and polishing the README, check that the value-carrying copy (`## What this skill does`, the description) leads with the *outcome the user gets*, not the skill's internal structure. "Turns a folder of recordings into a tagged, searchable archive" beats "a folder of YAML frontmatter and Markdown that calls the transcription tool." If the copy describes mechanism instead of result, rewrite it toward the outcome — see the good/bad contrast in `references/polish-pass.md` "Outcomes-first positioning". (BUILD authored `## What this skill does` and `## Intent` at scaffold time; the publisher fills the install/sibling placeholders and polishes the whole thing for end-user clarity — it doesn't re-author intent.) When the target declares an MCP pairing in its frontmatter/HISTORY, also check the README carries a one-line MCP-plus-skill combined-value note ("the MCP connects Claude to X; this skill teaches the workflow on top"); add it if missing, skip if the skill has no MCP dependency.

## Step 7

The third signal (skill-tracer audit fixes; build before dispatch): run `python3 ~/.claude/skills/skill-publisher/scripts/tracer_changelog_rows.py <skill>` — it selects the CODE-REVIEW/TRACE/REVIEW FIX/STRENGTHEN rows from the skill-tracer audit ledger added **since the last ship** (cutoff = the ship manifest's timestamp), the bug-fix WHY + severity the diff and ship ledger don't carry. **Exit 0** → use its text block verbatim as the `[TRACER_LEDGER_ROWS]` slot. **Exit 1** (no tracer ledger for this skill) → fill the slot with the literal `none` (the changelog degrades to the two-signal form — no regression). One caveat before degrading: the script keys the tracer ledger on `<skill>` (the frontmatter `name`); if the skill was *traced* under a different name than its current frontmatter `name`, a real tracer ledger exists under the other key and exit 1 is a false negative — pass `tracer_changelog_rows.py <skill> --ledger ${XDG_DATA_HOME:-~/.local/share}/skill-tracer-audit-ledger/<traced-name>.md --manifest ~/.claude/skill-publisher-ledger/<skill>.manifest.json` to use it (`--ledger` makes the ledger's basename, not `<skill>`, key the ship manifest, so without `--manifest` the last-ship cutoff is lost and every historical fix is listed). This is read-only on the tracer ledger; the publisher never edits skill-tracer.

**Changelog sourcing.** If Step 7a produced a structured diff (`/tmp/skill-publisher-diff.json`, exit 0): **dispatch the cold changelog agent** per `references/changelog-agent-prompt.md` (**load it now** — it owns the slots (including `[TRACER_LEDGER_ROWS]` built above), the `BUMP:`/`CHANGES`/`DISCREPANCIES`/`ENTRY`/`CHANGELOG PROPOSAL COMPLETE`-sentinel return shape, and the reconciliation rule: union the changes (`diff-only` ones are real — keep them; `tracer-ledger` fixes name the specific bugs), `final_bump = max(agent_bump, ledger_bump, tracer_bump)`, ask the user only on a bump disagreement / non-`none` `DISCREPANCIES` / ambiguous level). Use its `ENTRY` + `final_bump` below. **No-published-state fallback** (no upstream / `no_published_state` / diff exit 1-2): skip the agent and source from the ledger rows alone (+ the `tracer_changelog_rows.py` fixes above if exit 0 + optional `<last-ship-tag>` git log + user description) per `references/changelog-format.md` "Sourcing the change summary". **Then, if a `changelog run-<N>` marker is present, remove it** (Step 7a wrote it only when an upstream resolved; the no-upstream path never did, so this is idempotent) — before the version bump.

In HISTORY.md: increment `version` (bind the pre-increment value to `<prior>`, the bumped value to `<new-version>`, and the chosen bump level to `<bump-type>` (patch/minor/major, for Step 9's pr-template) — `<prior>`/`<new-version>` feed Step 10's canonical comment; `<new-version>` also feeds `verify_ship.py --version`, and `<prior>` is what you write to `metadata.parent-version`) (semver — patch for fixes, minor for new capability, major for breaking changes; when this run's changes span more than one level — e.g. both a breaking change and a new feature — default to the **highest** level present (major > minor > patch; classify each addressed ledger row as fix/feature/breaking; a polish-only or all-USER-PAUSE run with no classifiable change is a patch). Ask the user only when the headline change's level cannot be told from the ledger rows). Append a changelog entry per `references/changelog-format.md`: date + new version + summary of what changed since the last ship (sourced from this run's ledger rows + the skill's git diff if available — to test availability (using the absolute `<target>` skill-root path resolved in Step 1, so `-C` points at the right repo regardless of current Bash cwd): `git -C <target> rev-parse HEAD 2>/dev/null && echo git-ok || echo git-unavailable`; if unavailable or the target is not in a git repo, source only from the ledger rows). Also update the target's SKILL.md `metadata.parent-version` to `<prior>` (Edit the `parent-version:` line in place — bare unquoted semver, no `v` prefix; or the literal `pre-versioned` when there is no prior version to supersede). **Degraded-mode handling** (the two Step-1 sub-paths — (a) attribution-declared: keep the scaffold's 1.0.0, write the initial-publish entry, add `parent-version: pre-versioned`; (b) user-skipped: skip Step 7 wholly) is in `references/changelog-format.md` "Step-7 degraded-mode handling".

## Step 8

- **`claude-users`**: `python3 ~/.claude/skills/skill-publisher/scripts/package_skill.py <target> --tier claude-users --output <scratchpad>/<name>.skill` → `.skill` archive installable on Claude Code AND Cowork (`--tier` is required). On exit 0 of the default `.skill` invocation (run it first), capture that invocation's JSON to the canonical temp file `/tmp/skill-publisher-package-out.json` (shell vars don't persist across Bash calls), then read `packaged` from it as the artifact path for Step 10's `--artifact` **and `archive_sha256` from it as Step 10's `--expected-digest`** (the SHA-256 of the archive bytes — `package_skill.py` also ships a per-file `SHA256SUMS` inside the package; see `references/packaging.md` "Content hashing"); for every exit code (0–4), the JSON-vs-argparse distinction at exit 2, and the temp-file capture mechanics, see `references/packaging.md` "package_skill.py exit codes" (reachable codes here are 0/1/2/4 — exit 3 is model-agnostic-only; exit 2 for a claude-users invocation occurs only as an argument-assembly bug, not an expected path, per packaging.md). State the artifact path in your response text so Step 10 can use it. For the Claude.ai web user, also note the zip-and-upload route (zip the skill folder → upload via **Settings > Capabilities > Skills**); `--format zip` produces that zip (the default `.skill` archive — not this zip — is the artifact fed to Step 10's `--artifact` / verify_ship). `package_skill.py` applies the exclusion rules + per-surface format spec in `references/packaging.md` (the ship ledger lives outside the skill tree, so it is never packaged).
- **`model-agnostic`**: package per `agentskills.io@1.0` standard → installable on any compatible runtime. Same JSON shape + exit-code handling as the claude-users branch, plus **exit 3** = model-agnostic conformance failure → PACKAGE cluster, address, retry (see `references/packaging.md` "package_skill.py exit codes"). On exit 0, extract `packaged` the same way and state it in your response text for Step 10's `--artifact`.

## Step 10

It checks the new `version` is in HISTORY.md frontmatter, the changelog heading for it exists, the package artifact exists at its path (omit `--artifact` for personal tier), the artifact's SHA-256 matches the `archive_sha256` captured at Step 8 (pass `--expected-digest <archive_sha256>`; a mismatch is a required-check FAILURE — the artifact on disk is not the one packaged), and the PR URL resolves (omit `--pr-url` if no PR). For shared tiers always pass `--expected-digest` (Step 8 captured it); omit it only for personal tier (no artifact). It also checks **changelog quality** — pass `--parent-version <prior>` so the new entry uses valid Keep-a-Changelog categories, every Removed bullet is marked `[interface]` or `[internal]`, and the SemVer bump is a clean single-level step (an `Added` entry needs ≥ minor, an `[interface]` removal needs major). A violation is always a required failure now (read the `changelog` object + `required_failures`; `--strict-changelog` is still accepted and does nothing). The same check runs BEFORE the PR with `--changelog-only` (SKILL.md Step 7). On a **pre-versioned** path (the degraded full-skip path, OR a present HISTORY.md carrying `parent-version: pre-versioned`) the bump check is **n/a by design** — omit `--parent-version` or pass the literal `pre-versioned`; the category checks still run, just not the bump-level step (it is not an enforcement gap). Full pre-versioned-at-verification semantics: `references/changelog-format.md` "Pre-versioned target".

**Replace the run-summary comment with the canonical form** (only after `verify_ship.py` exits 0, so a failed verification leaves the generated `Round N total` comment; version and PR URL are known from Steps 7 and 9). **First, branch on which comment form is already on the ledger for Run N** (so a recovery re-run of Step 10 never Edits a string that is no longer there): if the **canonical** `<!-- Run N total:` line is already present (Step 10 ran once before, e.g. a recovery resume) → it is final, leave it in place and skip to "Clean up temp artifacts"; elif the **generated** `<!-- Round N total:` line is present → do the Edit-replace below; else (NEITHER form present — a degraded-skip ship that wrote no close-round comment) → append the canonical line fresh. Only the middle branch runs the Edit-replace, so the `old_string` it searches for always exists.

For the Edit-replace branch: **recompute the counts across ALL Run-N rows** (the Step-5 `close-round` tally predates the PACKAGE/PR rows added in Steps 8-9) by a **read-only recount** — do NOT re-run `close-round` (it appends a second comment, which `references/ledger-format.md` forbids: replace, don't append). Tally directly from the ledger's Run-N data rows: `<X>` = the number of Run-N rows; `<F>`/`<S>`/`<P>` = the Run-N rows whose Address cell begins with `FIX` / `STRENGTHEN` / `USER-PAUSE` respectively (this bare-prefix tally matches `close-round`'s script count because the publisher never writes `would-*` addresses — see Step 5; were a `would-*` row ever present, the script would fold it into the same bucket while this recount would not). Then use Edit to find the ORIGINAL generated `<!-- Round N total: raw flags … — clusters … — addresses: … -->` line (the one emitted by `close-round` at Step 5 — substitute the actual run integer for `N`) and replace it, using the freshly recomputed counts, with:

Omit the flags that don't apply to this path (no `--artifact`/`--digest` for personal; no `--pr-url`/`--branch`/`--tag` when no PR was opened). On the **full-skip degraded path** (no version) write the manifest with `--version n/a`. Set `--merge-strategy-unknown` when the upstream may squash/rebase (the ship tag could dangle — see `references/github-pr-workflow.md`). A manifest write failure (exit 3 — I/O error; exit 2 is an argparse usage error, a bad invocation to fix) is surfaced but does not un-ship — the PR already landed; report it and continue. The PR check degrades to "unverified" (not a failure) when `gh`/network is unavailable — a missing tool won't fail a ship that otherwise landed; whenever verify_ship prints a `NOTE: PR check unverified ...` line to **stderr** (it can appear on exit 0 OR exit 1 — the PR-unverified state is independent of the required-check pass/fail), relay it to the user as informational, not a failure. A required-check failure means a prior step didn't complete — surface it rather than reporting success. **Full-skip degraded mode** (no HISTORY.md, hence no version): do not run `verify_ship.py` (it requires `--version`); instead, for shared tiers confirm the packaged artifact exists with a direct `[ -f <artifact> ] && echo ok` check — for personal tier there is no artifact, so skip the check entirely (a personal skill is neither packaged nor distributed, so there is no shipped artifact or version to verify-land — nothing to confirm).

## History scan

`scripts/history_scan.py <repo-url-or-path>` is read-only. It mirror-clones the repo into `--work-dir` (removed at the end), then scans (1) every added line of every commit on every ref, (2) every commit message, and (3) every author and committer identity (listed with commit counts). Kinds: `home-path`, `email`, `profile-term`, `profile-pattern`, `module-code`, `module-assessment`, `gendered-pronoun` (markdown only). Profile keys it reads: `personal_terms`, `personal_patterns` (case-sensitive regexes) and `scan_allowlist` (exact matches, or `path:<substring>` for a whole file such as third-party notices); placeholder names such as /Users/jane are always allowed. Output JSON has `repo`, `refs_digest`, `commits`, `authors`, `findings` (kind, match, file, first_commit, count), `message_findings`, `clean`. Exit 0 clean, 1 findings, 2 clone error.

A publish needs a clean report for the exact upstream: `github_pr.py --confirmed` exits 10 without one. `history_rewrite_plan.py` turns a report into replace rules and a mailmap plus the ordered commands; it runs no git. The rewrite and the force-push are the user's decision each time (typed yes for the exact findings list, mirror backup first). Author identity findings are fixed by the user's git config (a GitHub noreply address for future commits) and, for past commits, the mailmap in the plan.
