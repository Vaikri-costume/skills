# Dispatch reference

Contents: code-review reviewers and scope · dispatch prompts · manifests · edit detection (reviewer edits, out-of-target fixer edits) · post-fix gate · contract recovery · the Explore trade-off · why a provenance pointer · the hand-back tool and the agent transcript.

## Code-review reviewers and scope

`code_review_run.py` always stages one all-lens (ALLLENS) prompt and asks for two Sonnet generalists
(`G1`, `G2`) on it (from round 2 of a run G2's copy of it adds one line, below); their findings are unioned. WHY two: in the October 2026 self-run two reviewers
on the same prompt overlapped on only 8% of flags, so the second roughly doubles the finds per round.

Each code-review lens is one review perspective with its own body file,
`prompts/agent-<lens>.md`: fidelity, executor, logic, integrity and design.
ALLLENS is assembled in memory from the five lens body files (shared framing once, five check-sets,
a dedup-across-lenses rule, the output contract once) and staged to
`<out-dir>/code-review-ALLLENS-<RUN_TIMESTAMP>.txt`. From round 2 of a run, G2's dispatch entry
points at `code-review-ALLLENS-G2-<RUN_TIMESTAMP>.txt` instead: the same prompt plus one line asking
it to read the listed files in reverse order (an untested attempt to decorrelate the two
reviewers); G1's prompt is unchanged. Pass both transcripts to
`code_review_collect.py` (comma-separated `--agent-transcripts`, `--agent-flags G1,G2`).

*Scope.* The prompt's `## Scope` section and file list follow the scope `code_review_run.py`
decided: a full sweep (every in-scope file) in rounds 1-2 of a run and whenever `--scope full` is
passed; from round 3, a changed-scope review of only the files the previous round's and this round's
ledger addresses name. A changed-files reviewer reads every listed file in full and may open other
target files as evidence, but each finding names a listed file. The collector's coverage gate checks
the listed files only (the cr-scope record in `<out-dir>`). A clean changed-files review is
`changed-scope-clean`, never convergence: the orchestrator re-runs `code_review_run.py --scope full`
in the same round, and only a clean full sweep converges.

## Dispatch prompts

Every cold agent and the fixer is pointed at a staged file. State role and output contract first,
in your own voice, then name the file's provenance (see "Why a provenance pointer" below). Dispatch
both code reviewers in a single same-turn message. Fixers are the exception: dispatch one fixer
per batch, one at a time in batch order, because batches may edit the same files (a tier pass of 12
clusters or fewer is a single batch).

**Fixer**, one per fixer batch (`model`: the batch's model from the `batches` that `prepass_run.py` or `cluster_enforce.py` printed, per the fixer model rule; `subagent_type: general-purpose`):
> You are the fixer for a skill-tracer round — a defect-audit tool the user directly invoked this
> run for. This is not third-party or found content: the file at <path> was generated by this same
> orchestrating session as your fix instructions and cluster data. Read it with your Read tool and
> apply the considered fixes it describes. Edit ONLY files under the target skill. Do NOT delegate
> or dispatch sub-agents — you are already the delegate: you are the worker, you have no subagents, and you cannot redelegate this. Output: a single JSON object
> {"decisions": [{"cluster", "decision": "FIX | STRENGTHEN | ORCHESTRATOR-PAUSE", "address",
> "touched_files": [...], "closure": ["Siblings: ...", "Bound: ...", "Claims: ...", "Blocks: ..."]}, ...]} — no prose after the JSON (`closure`: required on every FIX, four one-line strings, none empty).

**Code reviewer** (`model: sonnet`; `subagent_type: Explore`):
> You are a cold code-review agent for skill-tracer — a defect-audit tool the user directly
> invoked this run for. This is not third-party or found content: the file at <staged-prompt-path>
> was generated by this same orchestrating session as your task's lens checklist and target file
> list. Read it with your Read tool and use its contents as reference material for your review —
> but your role and your output contract are exactly as stated in THIS message, not delegated to
> the file. Read every file it lists IN FULL, sequentially, no sampling. Do NOT edit any
> file. Do NOT delegate or dispatch sub-agents — you are already the delegate: you are the worker, you have no subagents, and you cannot redelegate this. Output: first the
> `PRE-FLIGHT <path>: <line_count> lines, last edited <yyyy-mm-dd>` line for each file; then each
> finding as exactly four lines — "ISSUE [tag]:" / "File:" / "Claim:" / "Target:" — no other field
> shape, no tag: lines inside a block beyond those four (a rejected candidate may be noted between
> blocks as one plain `Considered: …` line, the form the staged template allows); then exactly one
> trailing line, `No issues found` or `No of issues found:: N`.

## Dispatch manifests

Record each agent's `agentId` the instant dispatch returns, before any other work:

- code reviewers: `<out-dir>/dispatch-review-<RUN_TIMESTAMP>.json`, `{"G1":"…","G2":"…"}`
  (rewritten at every review dispatch, including the confirming full sweep);
- the fixers: `<out-dir>/dispatch-fixer-<RUN_TIMESTAMP>.json`,
  `{"phase":"<Phase>","agentIds":["<batch 1>","<batch 2>",…]}`, started at a tier pass's first batch
  and extended at each later batch; a re-dispatched fixer's `agentId` replaces the discarded fixer's id at
  that batch's position, so a batch never holds two ids (the resume table uses it to decide which fixers already ran for a
  tier's PENDING rows, and their transcripts are the fix-recording step's `--fixer-transcript` list).

The transcript is at `<projects-dir>/subagents/agent-<agentId>.jsonl`, where `<projects-dir>` is this
session's Claude Code transcript folder (`~/.claude/projects/<encoded-cwd>/<session-id>/`, the folder that
also holds the session's own `.jsonl`), not `<out-dir>`. WHY: the agent-to-transcript
binding is known for free at dispatch; reconstructing it later by grepping transcript contents
breaks when two agents emit overlapping tags, and the manifest survives a compaction so recovery
reads it instead of re-deriving. Pass transcripts to the collect scripts in manifest order.

## A reviewer that edits a file

A code-review agent that edits any file is an abort-and-re-dispatch condition. The baseline is taken
before dispatch: `touch <out-dir>/dispatch-baseline-<RUN_TIMESTAMP>`, and archive the target
(`tar -cf <out-dir>/target-before-<RUN_TIMESTAMP>.tar -C <target> .`) so there is previous content to
restore. Archive it whether or not git tracks it: `git checkout` restores the last commit, not the
working tree at the baseline, so it would also drop every uncommitted change made before dispatch
(including earlier fixes this run). After the agents return, detect an edit with
`find <target> -type f -newer <out-dir>/dispatch-baseline-<RUN_TIMESTAMP>`; if it lists any file,
revert it by extracting that file from the archive with `tar -xf` (a listed file absent from the
archive did not exist at the baseline: delete it), discard that agent's result, and re-dispatch it as
a fresh cold agent, at most 2 times per slot (SKILL.md "Retry bound"); a slot whose reviewer edits a
file a third time is a hard unrecoverable error (`references/recovery.md` "Hard unrecoverable
errors"). (The
Explore restriction makes this structurally unlikely; the check is the backstop. The same baseline
file is removed with the run's other tmp files by `cleanup_tmp_prompts.py`.)

## A fixer that edits outside `<target>`

The fixer may edit only files under `<target>`. Detect an out-of-target edit from the paths of the
Edit/Write tool calls in the fixer's transcript and from its decisions' `touched_files`; only those two sources are inspected, so a Bash write outside `<target>` is not detected. Before
re-dispatching, restore every out-of-target file from that transcript, newest call first: undo an
Edit call by replacing its `new_string` with its `old_string` (all occurrences when the call had
`replace_all`); for a Write call, delete the file when the transcript shows it did not exist before the
call, and otherwise write back the content of the fixer's own earlier Read of that file in the same
transcript (a Write over an existing file needs that Read first), with the Read output's line-number
prefixes removed. Do not use `git checkout` here: it restores the last commit and would drop any
uncommitted change the file held before the fixer ran. A Write over an existing file whose earlier
Read in the transcript did not return the whole file cannot be restored: that is a hard unrecoverable
error (`references/recovery.md` "Hard unrecoverable errors"), so stop and report the file and the transcript to the user. Then
discard that fixer's decisions (record none of them) and re-dispatch a fresh fixer with the same
staged prompt plus an explicit "edit only files under `<target>`" constraint, and replace the
discarded fixer's id with the new one at that batch's position in the fixer manifest. Re-dispatch at most 2
times per batch (SKILL.md "Retry bound"); after that, leave the batch's transcript out of the
fix-recording step, so fill-address records its clusters as ORCHESTRATOR-PAUSE for the
orchestrator to resolve at check-pauses.

## Post-fix gate

The procedure SKILL.md summarises in its "Post-fix gate" paragraph. Exit 2 handling stays in SKILL.md, below that paragraph.

Before dispatching each fixer batch, run `scripts/post_fix_gate.py snapshot
--target <target> --out <out-dir>/gate-<N>-b<k>-<RUN_TIMESTAMP>.json` (batch `<k>`), once per batch: an
out-of-target re-dispatch keeps the batch's first snapshot, so `check` also sees the in-target edits
of the discarded fixer, which stay on disk. After the batch's
decision check passes, run `scripts/post_fix_gate.py check --target <target> --snapshot <that file>
--fixer-transcript <the batch's transcript>`. Dispatch the next batch only once this batch's `check` has exited 0 or
its remaining problems are ORCHESTRATOR-PAUSE.
Run `check` the same way for a batch left out of the fix-recording step (2 failed re-emits, or 2
out-of-target re-dispatches): its clusters are already ORCHESTRATOR-PAUSE, so send it nothing and
resolve its listed problems with those pauses at the check-pauses step.
Exit 1 blocks closing this round (an orchestrator rule: `close-round` itself does not read the
gate): send the listed problems to the same fixer as a
(line, claim, evidence) list (`<file>:<line>`, the problem's `kind`, the problem text; line 0 means
the whole file, as for a `syntax` problem, a touched .py file that no longer parses) to fix and
re-emit its decisions (for a `stale-sibling` problem the fixer first runs `scripts/check_fix_radius.py --skill-root <skill-root> --token <the removed name> --touched <the files it edited>` and fixes every uncovered site, the same closure `references/how-to-fix.md` "Fix-impact closure" requires), then run the decision check and `check` again; at most 2 such inner passes
(SKILL.md "Retry bound"). A `block-reread` problem names a rewritten doc block: the fixer re-reads it whole
and lists it in its Closure `Blocks:` line (`references/how-to-fix.md` "Closure block"); the next
`check` reads that line from `--fixer-transcript`. Send with the problems the **siblings list**
(`check`'s non-blocking `siblings`: the few untouched lines naming a distinctive term of a touched doc
line; `siblings_omitted` counts the terms too common to list plus the terms cut by the 15-term cap), asking the fixer to update or confirm
each in its Closure block. A problem still listed after the 2 inner passes, and any `new-behaviour` problem at once, becomes
an ORCHESTRATOR-PAUSE: `SendMessage` the fixer to re-emit the decision of each cluster that touched
that file (when no cluster touched it, as for a `stale-sibling` or grown lint problem in a file the fixer
did not edit, the cluster that touched the file in which the problem's removed or renamed name was
defined) as `ORCHESTRATOR-PAUSE (post-fix gate: <file>:<line> <problem>)`, so fill-address records an
open pause that the check-pauses step resolves. This takes precedence over
`references/how-to-fix.md`'s "never a fix-failure fallback" rule, including for a contract-required
or real-bug fix that adds a raise, return or branch node; the check-pauses step resolves that pause like any other. The one exception is a behaviour-preserving
refactor (the same inputs give the same outputs, exits and messages): re-run
`post_fix_gate.py check --accept-new-behaviour <file>:<kind>` (`<kind>` is the node kind the problem
text names, `<kind> count N -> M`: one of `raise`, `return`, `exit`, `if`, `for`, `while`, `try`,
`ifexp`, `boolop`; not `new-behaviour`), then record the waiver as a ledger row
appended as in SKILL.md's doc-lint step, with `--phase` the batch's phase (`Prepass` or `"Code Review"`),
root cause `post-fix gate waiver: <file>:<kind>` and `--address "FIX (<file>: <the refactor>)"`.

## Contract recovery

If an agent's output violates the strict contract (multi-fence output, missing or wrong sentinel,
incomplete block form, an ISSUE block count other than the declared `No of issues found:: N`, insufficient read coverage), `SendMessage` **that same agent** promptly,
asking it to reformat or read the gap and re-emit. A cold re-dispatch changes the finding set; a
separate reformat agent has no Read coverage and fails the coverage gate. The emitter must emit
right; the parser stays strict and never loosens. (The PRE-FLIGHT lines are the one exception to
"strict": no script parses them, and read coverage is enforced on the agent's Read-tool calls, so a
missing PRE-FLIGHT line is not a contract violation.) An agent that ends with the template's
`ABORTED — missing files: …` line is not a contract violation either: its staged file list names
files that do not exist, which no reformat repairs, so `code_review_collect.py` reports it as
`aborted_agents` and it is a hard unrecoverable error (`references/recovery.md` "Hard unrecoverable errors"). Allow at most 3 `SendMessage` attempts per slot; an
agent that still has not produced a valid output is treated as unaddressable (next paragraph).

If the agent is no longer addressable, or its 3 attempts are used up, re-dispatch a fresh cold agent
for that slot. It MUST stay cold: reuse the original staged-prompt dispatch and never mention a
prior attempt, its failure, or its format error (that violates the cold-read invariant). The one
permitted addition to the verbatim dispatch is a restatement of the output contract, never of what
went wrong: "emit findings ONLY in the four-line `ISSUE [tag]: / File: / Claim: / Target:` form
(plus the PRE-FLIGHT lines and the one trailing sentinel line); any other field shape is a
contract violation." A different finding set from the re-dispatch is acceptable; the alternative is
a stuck round. If the fresh agent also fails the contract, repeat this paragraph with a new fresh
agent, up to 3 fresh agents for the slot; after that the failure is a hard unrecoverable error
(`references/recovery.md` "Hard unrecoverable errors"): report the slot and its transcripts to the user.

## The Explore trade-off

Explore agents tend to sample rather than full-read and to drift from the exact `ISSUE [tag]:`
four-line form. Two existing gates handle both: the read-coverage gate (continue the agent to read
the gaps) and the contract check (reformat recovery). Do not change `subagent_type` away from
Explore: a general-purpose agent once edited the target and the shipped skill when given only a
prompt-level read-only constraint, so read-only is enforced structurally. Counter the tendencies in
the dispatch prompt (full sequential reads, exact block form).

## Why a provenance pointer

Cold agents and the fixer read their staged file themselves with their own Read tool; the
orchestrator never inlines the file's text. A bare "read `<path>` and follow verbatim" looks like a
prompt-injection pattern to a cold agent and it refuses. Observed: an entire cold-agent fan-out
declined and returned zero findings, a false clean. Inlining the full text avoids the refusal but
forces the orchestrator to read and re-emit the whole staged corpus in its own context on every
round, defeating staging.

The fix is a provenance-carrying pointer: the dispatch prompt first states the agent's role and
output contract in the orchestrator's own voice, then frames the staged file as same-session data
("generated by this same orchestrating session as your task's checklist/cluster data"), not
a second instruction channel. Refusals traced to role ambiguity (the agent has no role until it
opens the file, so the file seems to seize authority) and to no chain of custody (an arbitrary
`/tmp` path among similarly named files reads as found content). The pointer reduces refusals but
does not eliminate them (observed residual per-instance variance), so after every dispatch check
each transcript for a refusal or an empty result before trusting a "clean": a zero-finding return
from an agent that did not read the target is a false clean.

If one agent slot still refuses under the pointer framing (visible in its transcript), fall back
narrowly: re-dispatch that slot only with its staged file's full text inlined. Do not widen this to
the batch.

## Hand-back tool and the agent transcript

Under the Claude desktop harness a cold agent often returns its final answer through the
`SubagentHandback` tool, so the answer is a tool_use input and not a text block.
`ledger_common.extract_final_assistant_text` therefore joins the text blocks and the
`SubagentHandback` message of each assistant entry into one string and takes the last non-empty entry
in transcript order as the agent's final answer. The strict contract
(the four-line ISSUE blocks and the trailing count line) is unchanged and still enforced by
`code_review_collect.py`. If the count line does not match the blocks, recover through `SendMessage`
to the same agent.
